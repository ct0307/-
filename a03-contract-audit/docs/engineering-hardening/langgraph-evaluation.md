# 契鉴审查链路与 LangGraph 引入评估

日期：2026-11-01（UTC；用户当地日期为 2026-10-31）。状态：基线分析与试点设计；尚未安装 LangGraph，尚未实现图编排。

以上状态记录第一阶段时点。用户随后批准实施；当前基础修复、独立环境安装和局部原型进展见 `docs/engineering-hardening/langgraph-pilot-acceptance.md`。下文保留原始实测与缺陷发现，不代表这些缺陷目前仍未修复。

## 决策

优先修复预算错误分类、窗口内部进度和逐条补充的调用开销，再在独立环境验证局部 LangGraph 编排。暂不全量迁移。

LangGraph 的候选价值是细粒度检查点、条件分支和人工中断恢复。它不能自动提高法律判断准确率，也不能自行减少已有逐条模型调用。仅把旧审查函数包装成一个图节点，无法解决本轮观察到的窗口内停顿。

## 实验边界

- 使用真实 FastAPI 上传、解析、提交审查和状态查询接口；在 TestClient 内运行，不涉及浏览器网络、前端渲染、生产队列压测。
- 使用现有模型配置 `gpt-6.1-sol`，通过用户已授权的兼容接口调用。密钥不写入报告和实验输出。
- 输入是 frozen_contracts_v3 代码合成合同，经清理、脱敏后重新排成原生 DOCX。构造分层不是人工法务金标；不包含扫描 OCR、原版 DOCX 版式验收。
- 每次运行新建隔离 SQLite 与存储目录，不读取业务合同，不修改业务库。只读复制官方公开法源：2 个法源、1329 条父法条、1339 个关联 law 切片。保留原审批元数据，不代表业务知识库全部内容。
- 证据验证配置为 `manual_only`。本轮不能据人工待核状态推断法律知识检索错误率，不能把待核风险计为已核实风险。
- 每单受控限制：300 秒软时限、单请求最多 60 秒、24 次审查 chat、600000 的保守预算。生产原配置为 1500 秒、120 次、3000000。预算使用 UTF-8 字节估算与供应商 token 的较大值，不是精确计费 token。
- 两个批量优化开关保持关闭；窗口并发配置为 2，但法务与财务首审本身顺序执行。
- 原计划两份；第一份覆盖不完整后按脚本规则停止扩样本，再单独运行第二份。退出码 0 只表示实验采集完成，不表示审查质量通过。

该样本在 571 ms 显示 reviewing/15%/parsing，到 107165 ms 才变为 45%；间隔 106594 ms。之后 213436 ms 达到 75%，215489 ms 到达终态。该进度停顿在第二份样本中再次出现。

两份合计 47 次真实 chat，均成功响应。F3-049 的构造分层为 baseline，但本次没有人工逐项金标，不能将其 19 条候选直接统计为 19 条误报。两份不同输入也不能作为优化前后 A/B；这里只比较现有链路在不同合成输入上的表现。

## 根因与改进优先级

| 优先级 | 发现及证据 | 改进方向 | 验收重点 |
|---|---|---|---|
| P1 | `workflow.py:69` 抛 AUDIT_BUDGET_EXHAUSTED，`review_pipeline.py:896` 将其映射为 INVALID_MODEL_OUTPUT；最小复现成立 | 打通协议、失败文案和前端展示中的预算耗尽机器码 | 不发新请求、不自动循环重试；保留部分结果和真实覆盖 |
| P1 | `auditor.py:159` 在窗口完成时更新进度；一个窗口内可能执行多轮发现和逐条补充 | 增加发现、补充、核验阶段事件及更新时间；显示实际完成数 | 长请求期间有真实阶段与心跳；不用计时伪造完成比例 |
| P1 | `review_pipeline.py:380` 对每个发现逐条补充；`collaboration.py:34` 角色首审顺序执行并共享总预算 | 在隔离基线上评估已有批量补充开关；预留各角色首审预算，限制单角色补充开销 | 不能以减少角色覆盖换取速度；批量失败仅重试失败项 |
| P2 | `BufferedWindowCheckpoint` 内存暂存、`window_repository.py:237` 窗口完成后发布 | 验证细粒度检查点、事件持久化和恢复 | 完成节点不重跑；区分响应落盘前后的失败窗口 |
| P2 | 19 项候选均需复核，manual_only 与公开法源快照限制了本轮解释能力 | 引入人工核验的少量评测集，逐项核对原文、法条、适用关系与误报 | 报告精确率/召回率之前必须先有合法来源和可靠标签 |
| P3 | 尚无图编排与原链路的受控对照结果 | 局部 LangGraph 试点后再决定依赖是否进入正式项目 | 收益可复现，失败路径与回退路径验证通过 |

错误分类复现：建立 `AuditBudget(max_calls=1)`，完成一次 reserve/settle；再次 reserve 得到 `AUDIT_BUDGET_EXHAUSTED`、retryable=false；传入现有 `WindowReviewer._map_error_code` 得到 `INVALID_MODEL_OUTPUT`。协议的 ReviewIssueCode 和失败文案也未包含预算耗尽码。该缺陷由静态代码与本地最小复现共同支持；尚未修复。

本例模型成功响应连续发生，外部调用耗时占主要部分。法务先执行及逐条补充具有明确成本，但两份合成样本不足以量化批量化或并行化的收益；扩大并行前还需验证数据库事务、预算公平性和供应商限流。

## 三种方案

| 方案 | 收益 | 成本与局限 | 建议 |
|---|---|---|---|
| 完善现有模块 | 直接修复预算文案、阶段反馈、批量与预算分配 | 细粒度恢复仍需自行维护 | P1 先做 |
| 局部 LangGraph 试点 | 对发现/补充分步落盘，按条件复核，验证人工中断恢复 | 新增依赖和双层状态协调；性能收益须实测 | P2 独立环境验证 |
| 全量替换任务与业务状态管理 | 编排形式统一 | 易破坏现有 generation、执行权、审批与发布门禁；复赛前收益不确定 | 暂不实施 |

## 依赖审计与安装范围

候选：`langgraph==1.2.19`、`langgraph-checkpoint-sqlite==3.1.3`。使用官方 PyPI 的只读 dry-run，保留项目 27 个现有直接依赖版本约束，解析为 40 个 wheel。24 个包在现有环境未安装，8 个候选版本与当前已安装版本不同；由于解析使用 `--ignore-installed`，这不等于这 8 个包必须升级。

全部 wheel 来源为 HTTPS `files.pythonhosted.org`，已记录 SHA-256；PyPI 与 OSV 对这 40 个版本的查询成功，未返回已知漏洞记录。这仅覆盖来源、哈希与公开漏洞记录，不等于完整源码安全审计。

传递依赖包含 LangSmith、SDK、sqlite-vec 等。拟安装到 `outputs/langgraph-evaluation-20261101/prototype-venv/` 独立虚拟环境，不改 `backend/.venv` 或正式 requirements。使用精确版本及哈希锁，关闭外部追踪；原型仅使用合成/回放数据。锁文件适用于本次 Windows/Python 3.13 环境，其他环境需重做解析与检查。
