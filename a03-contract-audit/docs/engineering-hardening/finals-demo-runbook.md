# 决赛演示操作与现场回退

## 会前准备

1. 使用比赛正式电脑与浏览器，检查前后端、模型连通、字体和投屏比例。预留至少一次真实审查的时间，提前完成演练。
2. 使用可公开的合成合同。上传后核对合同类型、部门与签订日期，明确点击日期确认；不把自动抽取值当作人工核验。
3. 提前启动一份真实审查，保留审查完成的样例和备用录屏。样例与录屏标注为“会前已完成”，不冒充现场生成。
4. 预备两名独立用户：责任人处理整改，另一专业账号复核。材料上传后确认正文可读，填写验收意见再闭环。
5. 打开协作页检查缺项清单：先逐项人工复核，再为需修改的风险补齐整改计划，最后填写终审意见、质量核验说明和冲突裁决。

## 建议演示顺序（按比赛实际限时裁剪）

| 用时 | 操作与说明 |
|---|---|
| 0:00—0:45 | 展示合成合同上传、类型与日期人工确认，并启动真实任务 |
| 0:45—1:30 | 说明待确认/空文件失败隔离；展示任务进度与刷新恢复 |
| 1:30—3:15 | 打开明确标记的会前已完成样例，查看风险原文定位、候选依据与待核验说明 |
| 3:15—4:45 | 人工确认一条风险，明确责任人、期限、措施与验收条件；查看已准备的整改材料和独立复核记录 |
| 4:45—5:30 | 展示终审前置条件与组件表单、报表及下载结果 |
| 5:30—结束 | 若现场任务已结束，返回显示真实结果；否则如实显示仍在处理，并用备用样例完成讲解 |

两次626字合成样本的真实审查分别约285秒和317秒，只作为现场安排依据。第二次确认签订日期后，15条候选风险已读取法规适用时点，但整体仍需人工复核。不要承诺每份合同均在固定时间内完成，也不要为追求速度关闭事实、日期或法规核验。

## 现场异常处理

| 现象 | 操作 |
|---|---|
| 模型仍在处理 | 保留任务，不反复点击启动；展示进度后切换已标记的会前样例 |
| 模型接口异常 | 显示真实错误，使用备用录屏；不切换伪结果冒充真实结果 |
| 整改材料无正文 | 在材料原文窗口点击“解析材料正文”；解析失败可重试，无需重新上传 |
| 终审缺整改任务 | 按清单进入合同审查，打开对应风险补齐整改计划，再刷新工作流 |
| 终审提示意见已变化 | 保留填写意见，刷新终审状态后重新核对；不要沿用未经确认的新快照发布 |
| 日期被校正 | 已有审查失效，按页面提示重新审查；当前报告排除旧风险与旧付款分析，历史整改留痕仍保留 |

## 法律结论与展示边界

候选风险、原文定位通过、依据核验通过和人工终审是不同状态。确认日期只补齐适用时点，不代表法律语义正确。待核验依据不能在讲解中写成权威结论；风险接受也不表示风险消除。

## 维护已知知识错误

当前两条旧错误的精确修订记录保存在 `backend/resources/known-rule-corrections.json`，含修改前后内容与法源。没有找到原先上传的TXT源文件，资源文件作为本次修订的受控来源；重新导入资料时应使用修订内容。

从backend目录执行，先预览再应用；数据库必须显式指定，默认不会写入：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.correct_known_knowledge --database storage/a03_dev.db
.\.venv\Scripts\python.exe -X utf8 -m scripts.correct_known_knowledge --database storage/a03_dev.db --apply
```

只修改来源、类别、原文完全匹配的两条旧错误；人工改过的内容不会被覆盖。修订保留审计，撤销旧审批并清除旧向量，由知识修订号刷新检索；专业人员仍需复核，重复执行不会重复修改。
