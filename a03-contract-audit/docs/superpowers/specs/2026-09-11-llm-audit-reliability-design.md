# 大模型合同审查可靠性设计

日期：2026-09-11  
状态：已批准实施

## 1. 问题与目标

模型已连通，但单文件审查把数分钟外部推理放在同步 HTTP 请求中。浏览器先超时，后端随后成功，用户看到假失败并重复提交。目标是让数据库中的持久任务成为唯一事实来源，使上传和审查具备幂等、恢复、错误分类和成本上限。

## 2. 方案选择

| 方案 | 结论 | 原因 |
|---|---|---|
| 只延长超时 | 拒绝 | 仍会受代理、浏览器和模型尾延迟影响 |
| 复用现有批次任务 Implementation | 采用 | 已有租约、重试、恢复和轮询，改动风险最低 |
| 引入完整工作流引擎 | 拒绝 | 当前规模下增加运维与迁移成本 |

## 3. 持久任务

单文件审查提交时创建一个只含一项的审查批次。`AuditBatchItem` 保存任务身份、状态、错误码、重试次数、租约和结果摘要；单文件和批量入口共享同一执行 Implementation。重复幂等键只有在请求指纹一致时返回原任务，否则返回冲突。

生产 Adapter 将任务提交给 Celery；本地 `AUDIT_ASYNC=false` 使用受限线程池执行同一任务函数，使 HTTP 快速返回且不要求开发机安装新依赖。进程重启后重新扫描 queued 或租约过期项。

## 4. 上传幂等

单文件上传记录内容 SHA-256、用户范围幂等键和存储路径。相同用户、相同幂等键、相同内容返回原合同；相同键但内容不同返回冲突。数据库提交失败必须清理本次新建文件。前端使用文件内容哈希生成稳定键，网络响应丢失后重新提交不会产生重复合同。

## 5. 推理与事务

模型 Adapter 默认携带输出 token 上限。审查运行先以短事务领取 generation，随后在不持有合同行锁的情况下解析和推理，最后以短事务校验 generation 并发布风险、合同状态和交叉验证摘要。较新的运行存在时，陈旧结果不得覆盖。

审计日志不再隐式提交；事务由调用用例显式拥有。模型失败映射为稳定错误码，日志记录执行 ID、阶段、耗时和 token，不记录合同正文、模型完整响应或密钥。

## 6. 前端行为

上传和审查请求均携带稳定幂等键。审查提交后页面轮询持久任务状态；刷新时从本地最小元数据恢复合同 ID 和任务 ID，再向后端对账。页面展示后端安全错误信息，不再把所有异常显示为权限错误。未知状态按失败关闭处理。

## 7. 验收

- 相同上传键不会创建重复合同；不同内容使用同一键返回冲突。
- 单文件审查始终创建持久任务项，重复提交不重复派发。
- 本地和 Celery Adapter 都执行同一任务逻辑。
- 模型请求包含输出上限；异步状态可恢复交叉验证。
- 陈旧 generation 不发布风险；模型调用期间不持有合同行锁。
- 前端覆盖正常、运行中、错误、刷新恢复和移动端显示。
- 相关测试、类型检查、构建和项目质量门禁通过。
