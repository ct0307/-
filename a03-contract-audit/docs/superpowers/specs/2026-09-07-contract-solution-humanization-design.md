# 《契鉴》项目详细方案去 AI 化改写设计

## 目标

在不改变项目事实、技术方案和验收边界的前提下，降低《契鉴_项目详细方案.docx》的 AI 生成感。前六章做语言层面的轻量修订，第七章重新组织表达，使全文更像参赛团队基于实际开发和测试形成的方案。

## 输入与输出

- 输入文件：桌面 `比赛材料提交包/契鉴_项目详细方案.docx`。
- 可追溯源稿：`docs/contract-solution/content-redesign/` 下七章 Markdown。
- 输出文件：桌面 `比赛材料提交包/契鉴_项目详细方案_人工润色版.docx`。
- 原 DOCX 保留，不覆盖、不改名。

## 改写范围

### 前六章

保留章节结构、图表、数据、引用和技术结论。逐段清理以下问题：

- 宣传式形容词和空泛价值判断；
- 机械的三段式、四段式排比；
- “不仅……而且……”“不是……而是……”等高频模板句；
- “闭环、赋能、确保、实现、形成、全面”等词的重复使用；
- 每段末尾重复总结或拔高意义；
- 为追求完整而堆叠的同义说明。

不把正式方案改成口语稿，也不随意加入第一人称。文字保持竞赛方案需要的正式程度，但优先使用具体动作、对象和结果。

### 第七章

第七章由“证明自己没有夸大”的说明方式，改为正常的项目验证与收尾叙述。建议结构为：

1. 验证范围；
2. 本地测试结果；
3. 赛题指标完成情况；
4. 尚待完成的实测；
5. 项目总结；
6. 参考文献。

删除或大幅压缩以下内容：

- 原稿及成稿 SHA-256；
- Git 提交基线和构建过程说明；
- PPT、视频等材料之间的制作分工；
- 多次重复的“不得写成达标”免责声明；
- 与测试报告重复的取证操作细节。

保留真实测试数量、已验证能力、待实测硬指标、外部条件和法律责任边界。状态表只保留评委判断完成度所需的信息。

## 事实边界

- 不新增客户案例、实际收入、市场份额或落地成效。
- 不把自动化测试写成真实 52 文件、OCR 准确率、PostgreSQL、Compose、OpenClaw/GPU 或能耗实测。
- 不修改法律来源、接口数量、测试数量和已有结果，除非仓库当前证据能够复核。
- 演示数据继续明确为演示数据，但只说明一次，不在各节反复提示。

## 实施方式

1. 从七章 Markdown 源稿统计高频 AI 句式和重复词。
2. 前六章逐段轻修，不改变标题层级、图片和表格顺序。
3. 重写第七章正文，合并重复表述并删除幕后制作记录。
4. 使用现有 `build_docx.js --profile redesign` 构建独立输出。
5. 对新旧文档进行章节、图片、表格和正文差异检查。
6. 将修订版逐页渲染为 PNG，检查分页、裁切、表格和目录。

## 验收标准

- 七个一级章节、图表和参考文献完整；
- 关键事实与证据状态不发生升级或失真；
- 第七章不再出现原稿哈希、提交基线和材料制作过程；
- 全文高频 AI 模板句显著减少，段落长短和句式有自然变化；
- DOCX 可正常打开，目录与页码可用；
- 每页渲染正常，无文字裁切、表格越界、缺图或异常空白页；
- 原文件保持不变，修订版使用独立文件名交付。
