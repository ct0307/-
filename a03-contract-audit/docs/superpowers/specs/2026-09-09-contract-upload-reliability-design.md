# 合同上传与解析可靠性修复设计

## 背景

三份文本型 PDF 经单合同上传入口逐次拖拽后，出现两类问题：部分文件已上传但解析失败，界面只显示通用错误；后续成功文件覆盖此前文件的页面展示。数据库确认文件未丢失，失败集中在 PDF 文本兼容字符、日志编码和单会话状态模型。

## 目标

- 包含 Unicode CJK 部首兼容字符的文本型 PDF 可以稳定解析。
- 日志输出失败不能中断合同解析。
- 前端明确区分上传失败、上传成功但解析失败、解析成功。
- 解析期间不允许再次发起单文件上传。
- 页面保留当前审查合同，同时展示本次上传记录并允许切换已解析合同。
- 合同原件、数据库和运行日志不进入版本控制。

## 非目标

- 不合并单合同与批量合同的后端接口。
- 不删除现有重复上传记录。
- 不改变合同审查、批次审查或历史记录的数据模型。
- 不对所有输入文本无条件执行可能改变法律符号的全量规范化。

## 方案

### PDF 解析

`pdfplumber` 提取后检查 U+2E80 至 U+2FFF 范围内的 CJK 部首和康熙部首字符。发现此类字符时，认为字体映射不可靠，优先使用已有 PyMuPDF 路径重新提取。只有 PyMuPDF 仍残留兼容字符时才进行局部 Unicode NFKC 规范化。现有空页 OCR 流程保持不变。

### 日志防护

后端日志初始化时将标准输出配置为 UTF-8；无法配置时使用安全替换策略。业务代码不得因控制台编码能力不足而失败。解析日志仍保留字段级摘要，不记录合同全文。

### 前端状态

单合同上传拆分为两个明确阶段：上传、解析。上传成功后创建本次记录；解析成功后记录状态为 `parsed` 并设为当前合同；解析失败则保留合同 ID 和后端错误，状态为 `parse_failed`，不显示绿色成功状态。

`audit-session` 增加仅存在于浏览器会话内的上传记录列表，不写入新的后端表。列表记录文件名、合同 ID、状态、错误及解析结果。用户可切换已解析合同作为当前审查对象。上传或解析进行中禁用单文件上传入口，避免并发覆盖。

### 错误展示

前端优先显示统一 API 客户端提供的中文 `error.message`。通用兜底文案仅用于没有可用错误信息的情况。错误记录在上传区持续可见，不能只依赖短暂 toast。

## 测试

- 后端：兼容部首检测、PyMuPDF 回退、日志输出不影响解析、普通 PDF 路径不回归。
- 前端 store：上传失败、解析失败、解析成功、禁止并发、切换已解析记录。
- 前端页面：持续错误说明、多记录同时显示、当前合同切换、忙碌状态禁用。
- 集成验收：三份真实 PDF 只在本地执行，不复制进仓库；确认两份原失败合同可解析，三份同时出现在本次记录中。

## 风险控制

- 不存储合同正文到前端记录，仅保存后端已返回的结构化要素。
- 不自动重试已失败上传，避免产生更多重复合同。
- 保持现有 API 契约兼容，降低其他页面回归风险。
