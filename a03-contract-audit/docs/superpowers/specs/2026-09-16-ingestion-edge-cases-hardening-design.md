# 合同导入边界问题加固设计

## 1. 背景

当前合同导入链路已经具备文件结构预检、加密存储、异步解析、合同类型建议和人工确认，但仍存在四类边界问题：

1. TXT 预检能够识别 GB18030，解析器却固定使用 UTF-8 容错解码，导致中文正文被静默丢弃；
2. 合同类型候选来自管理员字典，但正文语义信号仍写死在分类器中，新类型只能依赖精确标题；
3. `合同类型：采购合同` 等明示字段没有通用识别规则，只能偶然命中硬编码关键词；
4. DOCX 只读取段落和表格，纯图片或图片承载主要正文时不会进入 OCR，也不会在导入阶段准确提示原因。

这些问题分别影响正文完整性、类型识别扩展性和人工复核边界。本设计遵循现有原则：宁可降低自动覆盖率，也不能让残缺正文或未经校准的分类结果自动放行。

## 2. 目标

| 优先级 | 目标 | 验收方向 |
|---|---|---|
| P1 | TXT 预检与解析使用同一套严格解码逻辑 | GB18030 中文端到端无损；禁止静默吞字 |
| P1 | 图片型 DOCX 在导入阶段可靠进入人工复核 | 不以空正文或少量噪声继续自动处理 |
| P2 | 明示合同类型对全部管理员字典值生效 | 精确值成为高权重、可解释证据 |
| P2 | 合同类型正文信号由数据配置驱动 | 新增类型无需修改分类器源码 |
| P2 | 保持现有分类安全边界 | 未校准前自动就绪错误数保持为 0 |

## 3. 非目标

- 本期不安装 LibreOffice、OCR 新引擎或其他外部依赖；
- 本期不对 DOCX 内嵌图片执行自动 OCR；
- 本期不使用 LLM 执行合同类型分类或同步要素抽取；
- 本期不启用 `CONTRACT_TYPE_AUTO_READY_ENABLED`；
- 不修改合同审查算法、RAG 检索、风险生成或人工确认责任边界；
- 不以单元测试通过代替冻结合同集和真实格式样本验证。

## 4. 总体方案

```text
上传字节
  -> 文件结构预检
  -> TXT 共用严格解码 / PDF、DOCX 格式校验
  -> 加密存储
  -> 异步解析
       -> TXT 共用严格解码
       -> DOCX 原生文本 + 图片承载检测
  -> 文档质量门
       -> 正常：要素抽取与类型建议
       -> 图片型 DOCX：人工复核
  -> 类型证据聚合
       -> 明示字段
       -> 可信标题/文件名
       -> 配置化主交易信号
       -> 通用弱信号
  -> 待确认 / 就绪
```

核心决策是把“解码”和“类型证据”分别收敛到唯一实现，避免预检与解析、字典与分类器继续形成两套事实来源。

## 5. TXT 严格解码

### 5.1 共用接口

新增独立文本解码模块，由文件预检和正式解析共同调用：

```text
DecodedText
  text: str
  encoding: utf-8-sig | utf-8 | gb18030

decode_text_bytes(content: bytes) -> DecodedText
```

`validate_upload()` 负责调用该接口并验证文本有效性；`extract_document()` 对 TXT 再次调用同一接口取得正文。正式解析不能依赖上传请求中的内存返回值，因为合同可能经过加密存储、异步执行、进程重启或历史数据重新解析。

### 5.2 判定规则

1. 包含 UTF-8 BOM 时严格使用 `utf-8-sig`；
2. 无 BOM 时分别严格尝试 UTF-8 和 GB18030；
3. 只有一种解码成功时选择该编码；
4. 两种都成功时，优先选择控制字符更少、可打印字符比例更高、中文可读比例更高的候选；质量相同时优先 UTF-8；
5. 两种都失败时返回 `TEXT_ENCODING_ERROR`；
6. 解码后没有有效可打印内容时返回 `TEXT_EMPTY`；
7. 禁止使用 `errors="ignore"` 或 `errors="replace"` 形成正式正文。

候选质量判断只用于解决 UTF-8 与 GB18030 同时可解码的歧义，不进行语言模型推断，也不记录正文内容。

### 5.3 数据和日志

- 不新增明文正文数据库字段；
- 可在安全日志中记录编码名称、字节数、字符数和判定分支；
- 日志不得记录原始字节、正文片段、合同要素或本机绝对路径；
- 历史 TXT 在重新解析时自动受益，不需要数据迁移。

## 6. 合同类型规则数据化

### 6.1 数据模型

保留 `LookupItem` 作为合同类型字典，在其旁新增一对一规则配置表，避免向部门等通用字典项添加分类专用字段：

```text
contract_type_profiles
  id
  lookup_item_id              唯一外键，指向 category=contract_type
  aliases_json                受控别名数组
  positive_signals_json       主交易正向信号数组
  negative_signals_json       排除或降权信号数组
  enabled                     该类型的别名和正文语义规则是否启用
  version                     规则版本
  created_at
  updated_at
```

约束如下：

- 别名和信号去除首尾空白、空值和重复项；
- 单项长度和数组数量设置上限，避免超大规则拖慢导入；
- `LookupItem` 是否存在决定类型是否可选，`profile.enabled` 只控制别名和正文语义规则；
- 删除字典项时级联删除规则配置，但不改写历史合同记录中的类型字符串；
- 分类器只读取当前合同类型字典，并仅加载已启用的规则配置；
- 没有规则配置的新类型仍可通过精确标题和明示字段成为候选。

现有 `_TRADE_SIGNALS` 和 `_TYPE_FAMILY_ALIASES` 的有效内容通过迁移种入规则表。迁移完成并验证一致后，分类器不再以硬编码常量作为运行时事实来源。

### 6.2 管理接口

管理员维护合同类型时可同时维护：

- 类型名称；
- 常见别名；
- 主交易正向信号；
- 排除或降权信号；
- 规则启停状态。

接口必须验证规则归属、长度、重复项和空值。规则变更记录审计日志，但不得把合同正文作为规则样本写入日志。

本期前端只增加紧凑的规则编辑区域，不引入自动生成关键词或在线训练。

## 7. 明示类型识别

### 7.1 识别范围

仅在正文首部受控范围内识别下列形式：

```text
合同类型：采购合同
协议类型: 技术服务合同
文件类型：居间合同
```

字段值必须在当前合同类型字典中精确匹配，规范化仅包括大小写、全半角冒号和首尾空白处理。禁止模糊匹配未知值后自动新增字典。

### 7.2 权重和冲突

证据优先级为：

```text
明示字段 > 可信标题或文件名 > 配置化主交易信号 > 通用弱信号
```

明示字段是高权重候选，但不直接绕过人工确认。若明示类型与可信标题或强交易信号冲突，则：

- 保留双方候选和证据；
- 将置信度限制在自动确认阈值以下；
- `auto_ready_eligible=false`；
- 提示用户确认最终类型。

该规则防止合同正文中的描述性文字或恶意内容直接改变系统分类结果。

## 8. 图片型 DOCX 质量门

### 8.1 检测原则

DOCX 继续优先使用原生段落和表格解析。解析完成后同时统计：

- 有效正文字符数；
- 段落和表格块数量；
- `w:drawing`、`w:pict`、图片关系及 `word/media` 中的图片数量；
- 图片所在正文顺序位置；
- 是否只有小型装饰图、Logo 或印章。

当有效正文不足且存在承载正文的图片迹象时，返回：

```text
source = native
requires_review = true
review_reason = DOCX 疑似图片型文档，未提取到足够正文
```

该状态属于内容质量不足，不属于解析器技术失败。导入项进入 `awaiting_confirmation`，不得自动就绪。

### 8.2 误判控制

仅有 Logo、签章或少量插图时不能把正常 DOCX 判为图片型。判定需要同时满足：

1. 有效正文低于统一的完整性阈值；
2. 存在一个或多个达到最小面积或像素阈值的内嵌图片；
3. 原生段落和表格不足以构成可审查正文。

纯空 DOCX 没有图片时使用独立的“正文为空”质量原因，不伪装成图片型文档。

### 8.3 后续 OCR 边界

本期只检测并转人工。后续若引入自动 OCR，优先选择 LibreOffice 无界面模式将 DOCX 渲染为 PDF，再复用现有页级 OCR、超时、页数、像素和置信度门禁。该能力需要单独完成依赖来源、安全审计、容器体积、字体一致性和渲染准确率验证，不与本期修复捆绑。

## 9. 状态与错误处理

| 场景 | 结果 | 状态 |
|---|---|---|
| TXT 编码无法严格判定 | `TEXT_ENCODING_ERROR` | 导入失败，可修正文件后重试 |
| TXT 解码后无有效字符 | `TEXT_EMPTY` | 导入失败 |
| 图片型 DOCX 正文不足 | 固定人工复核原因 | `awaiting_confirmation` |
| DOCX 正文为空且无图片 | 固定正文为空原因 | `awaiting_confirmation` |
| 明示类型有效且无冲突 | 高权重建议 | 仍按全局 auto-ready 开关处理 |
| 明示类型与其他强证据冲突 | 多候选和冲突证据 | `awaiting_confirmation` |
| 新类型无语义规则 | 仅使用精确标题和明示字段 | 无可靠证据时待确认 |

现有审查阶段的短文本保护继续保留，作为纵深防御；导入阶段不能依赖它来弥补解析质量判断缺失。

## 10. 迁移与兼容

1. 新建 `contract_type_profiles` 表；
2. 为当前合同类型种入与现有硬编码等价的别名和主交易信号；
3. 分类器在迁移后只读取数据库规则；
4. 本地 SQLite 轻量迁移和生产 Alembic 迁移保持一致；
5. 历史合同不自动重分类，避免未经确认改变既有审查范围；
6. 管理员可手动重新解析或重新确认需要修复的历史 GB18030 TXT；
7. API 保留现有候选、置信度和证据字段，新增规则管理字段不破坏已有客户端。

## 11. 测试设计

### 11.1 TXT

- UTF-8、UTF-8 BOM、GB18030 均严格无损；
- UTF-8 与 GB18030 歧义样本按质量规则稳定选择；
- 不支持编码、NUL 字节、空白文本返回稳定错误；
- GB18030 经上传、加密存储、异步解析后正文一致；
- 预检和解析不得选择不同编码；
- 源码扫描确认正式 TXT 路径不存在 `errors="ignore"`。

### 11.2 合同类型

- 任意管理员字典值都能通过精确标题和明示字段成为候选；
- 新增“居间合同”及其配置化信号后可从正文识别；
- 没有规则的新类型不会凭空获得语义候选；
- 明示类型与标题一致时形成高权重证据；
- 明示类型与强交易信号冲突时强制待确认；
- 现有 14 类候选、排序和安全阈值不回退；
- 自动就绪开关关闭时自动就绪数保持为 0。

### 11.3 DOCX

- 纯图片 DOCX 标记人工复核；
- 大图正文加少量标题仍标记人工复核；
- 正常正文加 Logo 不误判；
- 正文、表格、图片混合 DOCX 保留原有段落和表格顺序；
- 空 DOCX 与图片型 DOCX 返回不同原因；
- 图片检测不解压超限归档，不绕过现有 ZIP 安全边界。

### 11.4 回归

- 运行导入预检、解析器、分类器、质量 API 和导入任务测试；
- 运行冻结 `50+2` 合同集静态校验和生产解析；
- 运行项目完整质量门禁；
- 未执行人工金标准分类评测时，不宣称自动分类准确率达标。

## 12. 验收标准

| 指标 | 验收要求 |
|---|---|
| GB18030 正文一致性 | 端到端字符完全一致 |
| 静默解码丢失 | 0 |
| 图片型 DOCX 错误自动就绪 | 0 |
| 正常 DOCX + Logo 误报 | 0，基于冻结测试样本 |
| 动态类型标题可达率 | 100% |
| 动态类型明示字段可达率 | 100% |
| 分类冲突自动就绪 | 0 |
| 现有冻结集高置信度错误自动放行 | 0 |
| 外部新增依赖 | 0 |

## 13. 实施顺序

1. 先建立 TXT 共用严格解码器并补端到端回归；
2. 增加 DOCX 图片承载检测和人工复核质量门；
3. 增加明示合同类型通用识别及冲突处理；
4. 新建类型规则表和管理接口，迁移硬编码信号；
5. 更新管理界面规则编辑能力；
6. 运行冻结集、相关测试和完整质量门禁；
7. 保持自动就绪关闭，待独立校准通过后另行决策。

该顺序先消除数据损坏和错误放行风险，再处理扩展性，避免数据库迁移或前端工作阻塞 P1 修复。
