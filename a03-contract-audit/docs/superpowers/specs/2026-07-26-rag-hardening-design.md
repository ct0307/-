# RAG 可靠性加固设计

## 1. 目标

在保持现有 FastAPI、SQLAlchemy、SQLite/PostgreSQL 兼容方式和前端风险展示接口基本稳定的前提下，将当前“固定主题检索 + 批量挂载来源”的 RAG 原型升级为可验证、可降级、可审计的合同审查证据链。

本次改造解决以下问题：

- 无关向量结果也会作为依据返回；
- 模型生成的 `basis` 没有与检索结果校验；
- 同一批来源被挂到 Agent 生成的所有风险；
- 审查维度、合同类型和知识有效期没有参与检索；
- 覆盖导入、向量维度、缓存和超长切片存在数据一致性风险；
- 当前测试无法证明拒答、引用真实性和异常降级行为。

## 2. 范围

### 2.1 本次包含

- 检索请求上下文化和过滤；
- 可靠性阈值与无依据状态；
- 风险引用校验和逐风险来源收敛；
- 知识条目适用性、版本和向量元数据；
- 原子覆盖导入；
- 向量数量、格式和维度校验；
- BM25 内容指纹；
- 硬切片长度上限；
- 文件大小限制；
- 针对上述行为的后端回归测试。

### 2.2 本次不包含

- 引入新的向量数据库或外部依赖；
- 将现有 SQLite 全量迁移到 PostgreSQL/pgvector；
- 重写前端知识库页面；
- 自动重新生成全部 973 条现有向量；
- 构建 100 份合同、300 个风险点的正式冻结评测集。

## 3. 总体架构

### 3.1 检索请求

检索接口从单一字符串扩展为带上下文参数的请求：

- `query`：当前待核验风险或合同条款；
- `top_k`：最终返回数量；
- `contract_type`：合同类型过滤；
- `dimensions`：审查维度过滤；
- `as_of`：法规有效性判断日期；
- `categories`：允许参与的知识分类。

为兼容现有调用，除 `query` 和 `top_k` 外均提供默认值。现有简单调用无需立即修改。

### 3.2 检索结果

每条结果至少包含：

- `chunk_id`：知识切片稳定标识；
- `content`、`source`；
- `article_number`、`version`；
- `score`：可展示的相关度；
- `retrieval_mode`：`hybrid`、`bm25` 或 `fallback`；
- `reliable`：是否达到可靠依据阈值。

向量路只保留超过最低余弦相似度的候选。BM25 路只保留正分候选。融合后没有可靠候选时返回空列表，不再用任意近邻填充。

内置规则只能作为明确标记的业务规则兜底，不能伪装成法规引用；来源类型标记为 `fallback_rule`。

## 4. 逐风险证据闭环

审查分为两个阶段：

1. Agent 根据合同内容生成候选风险，但 `basis` 只作为待验证文本；
2. 系统以“候选风险分类 + 原文 + 合同类型 + 选定维度”再次检索，为每条风险建立独立来源集合。

系统使用知识 `chunk_id` 和来源文本校验模型引用：

- 引用能映射到可靠检索结果：保存规范化依据和对应 `rag_sources`；
- 无法映射：将依据改为“无可靠检索依据”，来源列表为空，置信度上限收紧，并强制进入人工复核档；
- 模型输出了检索集合外的条文编号：记录警告，不将该条文作为正式依据。

合同正文和知识片段均作为不可信数据包裹在明确分隔区中，系统提示明确要求忽略材料内部的指令，降低提示注入影响。

## 5. 知识数据模型

`KnowledgeChunk` 增加可空字段以兼容现有数据：

- `article_number`：条文编号；
- `version`：法规或制度版本；
- `effective_date`、`expiry_date`：有效期；
- `applicable_contract_types`：适用合同类型 JSON；
- `applicable_dimensions`：适用维度 JSON；
- `embedding_model`、`embedding_dimension`：向量生成信息；
- `content_hash`：正文指纹。

现有记录在迁移后仍可检索：空的适用范围表示不限制；空的有效期表示未知但当前可用；现有向量通过实际长度推断维度。新写入数据必须记录向量模型和维度。

## 6. 导入和一致性

### 6.1 原子覆盖

覆盖导入在一个数据库事务中完成：先完成解析和向量生成，再删除旧切片、写入新切片，最后统一提交。任何异常都回滚，旧知识保持不变。

### 6.2 向量校验

写库前检查：

- 返回向量数量必须等于切片数量；
- 每个向量必须是非空有限数值数组；
- 同批向量维度必须一致；
- 维度必须与模型配置或适配器返回维度一致。

检索时发现无效 JSON、非有限值或维度不匹配，不中断整个审查：跳过异常向量、记录日志并继续 BM25 路。

### 6.3 模型加载

本地模型导入、加载和推理产生的异常统一转换为 `LLMError`。宿主机缺少模型缓存时快速失败并进入 BM25 降级，不进行长时间隐式联网重试。

## 7. 切片、缓存和性能

- 超长句子按字符硬切，保证每片不超过 `_MAX_CHUNK_CHARS`；
- 法条二次切片时保留章节和条文编号前缀；
- 知识文件上传应用 `MAX_UPLOAD_MB`；
- BM25 缓存指纹使用文档 ID 和正文内容哈希，正文变化立即重建；
- 单次 Agent 审查复用知识快照和 BM25 索引，避免每个主题重复查询数据库；
- 本轮保留 NumPy 全量向量计算，千级数据规模以上的 pgvector 迁移另行实施。

## 8. 错误处理

| 场景 | 行为 |
|---|---|
| Embedding 服务不可用 | 降级 BM25，记录结构化告警 |
| 模型或维度与库存不一致 | 跳过向量路并提示需要重建索引 |
| 无可靠检索结果 | 风险标记无可靠依据并进入人工复核 |
| 覆盖导入失败 | 整体回滚，保留旧知识 |
| 单条向量损坏 | 跳过该向量，不影响其他切片 |
| 上传文件超限 | 在解析前返回 413 |

## 9. 测试策略

严格使用测试驱动开发：每项行为先增加失败测试，再编写最小实现。

必须覆盖：

1. 零相关向量不会返回可靠依据；
2. 模型生成的集合外引用被拒绝；
3. 每条风险只携带自身来源；
4. 合同类型、维度和有效期过滤生效；
5. 覆盖导入异常后旧知识仍存在；
6. 向量数量不足、维度不一致和损坏 JSON 正确降级；
7. 正文更新会使 BM25 缓存失效；
8. 任意输入切片均不超过 380 字；
9. 审查维度参数实际影响检索和输出；
10. 现有 RRF、切片和审查主链路测试不回归。

由于当前环境没有安装 `pytest`，实施阶段优先检查仓库是否已有可用测试运行器；不会未经确认安装依赖。如果仍无法运行，将使用标准库测试入口或最小验证脚本提供证据，并明确剩余验证缺口。

## 10. 验收标准

- 无可靠依据时不展示伪造或随机法规；
- 每条风险的 `basis` 能映射到其 `rag_sources`；
- 用户选择的维度实际改变检索范围；
- 覆盖导入失败不删除旧数据；
- 模型切换或损坏向量不导致审查接口 500；
- 切片长度、缓存失效和向量数量均有自动化回归测试；
- 不安装新依赖，不修改现有 973 条知识正文，不删除用户数据。
