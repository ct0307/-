# 高拟真合成 50+2 冻结合同集 v2 设计

## 1. 目标与边界

v2 用于修复 v1 专业真实性终审发现的三项核心缺口：风险标签没有对应真实风险原文、条款冲突没有可比较的冲突值、法务修订稿没有真实 OOXML 修订结构。

v2 仍是无真实主体、个人、账号、签章和交易信息的合成测试集。它可用于企业产品预验收和回归测试，但不能替代授权脱敏企业合同，也不能在双人真人复核前称为正式金标准。

v1 的代码、输出和哈希保持不变。v2 使用独立包、独立编号和 `outputs/frozen-contracts-v2/`，不得覆盖 v1。

## 2. 方案选择

采用“人工设计原型 + 确定性结构化生成”的混合方案：人工定义起草风格、案例事实、实际风险条款和冲突对；程序负责确定性组装、格式渲染、扫描扰动、冻结和验证。

不采用直接修补 v1，因为会破坏冻结可信度；不采用 50 份完全手工文档，因为难以复现和维护。

## 3. 数据集构成

- 有效合同编号：`F2-001` 至 `F2-050`。
- 协议级异常：`X2-051-empty-corrupt.pdf`、`X2-052-spoofed.pdf.exe`。
- 补充异步失败样本：`S2-001-nonempty-corrupt.pdf`，不计入 50+2。
- 格式保持 14 DOCX、21 文本 PDF、15 扫描或混合 PDF，便于与 v1 做同口径比较。
- 继续覆盖采购销售、技术数据服务、业务外包、租赁、建设承揽、员工服务、保密知识产权、框架及补充协议 8 类业务。
- 至少 12 份超过 12 页、30 份包含业务附件、5 份三方合同、5 份合法缺失要素、6 份真实条款冲突、4 份真实法务修订 DOCX。

## 4. 起草风格

50 份合同分布到 12 种独立风格，风格与文件格式、业务类型分别建模：

| 风格 | 数量 | 特征 |
|---|---:|---|
| 采购方标准模板 | 6 | 验收、质保、扣款和供应商义务较重 |
| 供应商标准模板 | 5 | 责任限制、付款前置和交付例外较多 |
| 业务部门自拟草案 | 5 | 结构不齐、简称较多、附件引用较松散 |
| 法务修订稿 | 4 | 修订痕迹、批注和显式版本标记 |
| 示范文本改编稿 | 5 | 章节完整、通用与专用条款分层 |
| 在线订购条款 | 3 | 主页面、链接政策和订单参数组合 |
| 框架协议加订单 | 4 | 主协议无固定总价，订单确定交易要素 |
| 主合同加补充协议 | 4 | 后签文件只变更指定事项 |
| 项目专用条件 | 4 | 通用条件与专用条件并存 |
| 行业协会参考模板 | 3 | 行业术语、表格和操作规则明显 |
| 客户指定模板 | 4 | 客户内控条款、审批和审计权突出 |
| 短式订单合同 | 3 | 主要要素集中在表格和背面条款 |

每种风格必须拥有独立的章节选择、措辞习惯、义务倾向和附件类型，不能只替换标题或字段。

## 5. 案例模型

每个案例除六要素事实外，必须显式声明：

- `drafting_style`：起草风格。
- `document_state`：草案、修订、签署、扫描归档等状态。
- `risk_level`：`actionable`、`negotiated` 或 `baseline`。
- `risk_clauses`：实际条款原文、风险类型、倾向方、严重程度、审查理由和证据位置。
- `conflicts`：文件 A、条款 A、文件 B、条款 B、优先规则和预期生效值。
- `annexes`：附件名称、业务数据行、正文引用和版本信息。
- `revision_set`：删除文本、插入文本、批注内容、作者角色和接受修订后的预期文本。

风险分布固定为 28 份 `actionable`、14 份 `negotiated`、8 份 `baseline`。风险原文必须像合同义务，不得写成审查建议或风险说明。

## 6. 条款与附件生成

通用条款只作为可选模块。不同风格按案例选择、删减、重排和改写，允许现实中的条款缺失、交叉引用和立场不平衡。

长合同只能通过业务实质扩充，包括设备清单、价格表、工程量清单、实施计划、SLA、验收指标、数据目录、人员配置和交接清单。禁止使用重复的通用履约控制行凑页数。

6 个冲突案例必须分别在两个明确位置呈现不同值，例如正文交付期与附件排期不一致、主合同付款比例与补充协议不一致。验证器必须证明两个原文均存在，并依据优先规则给出预期生效值。

## 7. DOCX 修订结构

4 份法务修订稿必须同时满足：

- `word/settings.xml` 含 `w:trackRevisions`。
- `word/document.xml` 同时含 `w:ins` 和 `w:del`，修订内容来自 `revision_set`。
- 包含 `word/comments.xml`、关系声明及正文批注范围标记。
- 页面可见“法务修订稿”版本标记，不模拟真实公章。
- 保留修订文本与接受修订文本可分别提取，且二者存在预先声明的差异。

修订作者使用角色化合成标识，如“合成法务审核人 A”，不得伪装成真人复核人。

## 8. PDF 与扫描件

文本 PDF 保留可提取文本层。纯扫描 PDF 不保留文本层；混合 PDF 同时包含文本页和扫描页。扫描扰动使用固定参数，覆盖轻度倾斜、压缩、低对比度和页边阴影，不制造不可读样本。

OCR 缺失时必须记录 `OCRUnavailable`，不能将解析失败写成数据集失败，也不能安装未获批准的依赖。

## 9. 验证与 TDD

实现严格执行红、绿、重构循环。至少新增以下失败测试后再写生产代码：

1. 50+2 数量、格式和 12 种起草风格分布。
2. 28/14/8 风险等级分布及风险原文落盘。
3. 6 个冲突案例的两个冲突值、证据位置和预期生效值。
4. 4 个修订 DOCX 的 OOXML 修订、批注、关系和接受修订文本。
5. 附件内容与案例事实一致，长合同不存在通用重复填充。
6. 去除强制合成标记和签署占位后，任意两份全文相似度低于 0.85，同场景业务正文相似度低于 0.75。
7. 文件可打开、页数与画像一致、哈希唯一、隐私模式不命中。
8. v1 关键清单哈希在 v2 实施前后保持不变。

验证器不得只检查元数据标签，必须检查渲染后文件的实际文本、附件位置和 OOXML 结构。

## 10. 冻结与测试顺序

1. 审定 v2 画像、案例事实和条款原文。
2. 生成全部二进制文件并完成格式、语义和视觉检查。
3. 写入 SHA-256 冻结清单，生成器拒绝覆盖现有 v2 目录。
4. 冻结后才运行生产解析器和构造真值技术预评测。
5. 系统失败不得用于回改 v2；修改合同必须创建后续版本。
6. 环境具备令牌、Redis、Celery 和后端服务时再执行真实 50+2 API 批测。

## 11. 通过标准

| 验收项 | 标准 |
|---|---|
| 文件构成 | 50 valid + 2 invalid，补充样本独立 |
| 起草现实性 | 12 种风格达到固定分布，章节和措辞存在实质差异 |
| 风险真实性 | 28 份含可定位的实际风险原文，元数据与正文一致 |
| 冲突真实性 | 6 份均含两个实际冲突值及可执行优先规则 |
| 修订真实性 | 4 份 DOCX 同时通过 OOXML、文本差异和视觉标记检查 |
| 附件真实性 | 附件包含与业务事实一致的数据，不使用通用清单填充 |
| 冻结完整性 | 全部哈希唯一且匹配，v1 哈希不变 |
| 技术预评测 | 如实报告，不预设分数，不冒充正式准确率 |
| 企业验收边界 | 双人真人复核及授权脱敏真实合同外部验证仍为商用前置条件 |

## 12. 文件边界

版本控制中新增 `backend/evaluation/datasets/frozen_contracts_v2/` 和对应测试文件；不修改 `frozen_contracts_v1/`。生成合同、预测、截图和运行证据只写入被 Git 忽略的 `outputs/frozen-contracts-v2/`。
