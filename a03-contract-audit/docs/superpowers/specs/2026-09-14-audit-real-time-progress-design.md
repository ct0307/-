# 审查真实百分比进度设计

## 背景与目标

当前批次页每 1.5 秒轮询一次后端，但顶部进度只按 `completed / total` 计算。因此单份合同尚未到终态时，页面会长时间显示 0%，用户无法判断任务是否仍在工作、进行到哪个环节。

本功能为批量审查和单份合同提供可信的百分比进度。百分比必须由后端已完成的真实里程碑计算并持久化；刷新、断网重连和 worker 重试后仍能恢复。它表达“处理已推进到哪里”，不承诺剩余时间。

## 方案比较

### 方案 A：后端真实里程碑并继续轮询（采用）

后端在解析、窗口审查、证据核验、二次复核、结果校验和持久化完成时更新进度，前端通过现有批次接口轮询展示。

优点是数据可信、刷新可恢复、改动与现有架构一致；代价是需要数据库字段、迁移和审查管线的受控进度上报。

### 方案 B：仅按现有状态映射固定百分比

例如 `parsing=10%`、`reviewing=50%`、`validating=90%`。实现简单，但最长的 `reviewing` 阶段仍可能长时间不动，不能回答“审查到哪一份窗口”。

### 方案 C：前端按耗时平滑增长

视觉上连续，但进度与真实工作无关，遇到排队、重试或模型变慢时会卡在 99%，损害用户信任，因此不采用。

## 数据模型与接口

在 `AuditBatchItem` 增加两个持久化字段：

- `progress`：`0..100` 的整数，默认 0。
- `progress_stage`：稳定的机器可读阶段，用于前端映射中文文案。

阶段枚举为：

| 阶段 | 百分比范围 | 含义 |
|---|---:|---|
| `queued` | 0% | 等待 worker 领取 |
| `claimed` | 5% | worker 已领取并建立执行围栏 |
| `parsing` | 5%-15% | 读取、OCR 与结构化解析 |
| `reviewing` | 15%-75% | 法务/财务 Agent 按顶层合同窗口推进 |
| `verifying` | 75%-90% | 证据核验、冲突处理与二次复核 |
| `persisting` | 90%-99% | 结果校验与原子持久化 |
| `completed` | 100% | `done` 或 `review_required` 已持久化 |
| `failed` | 保留失败前数值 | 处理失败，不伪装为审查完成 |

`BatchItemOut` 返回 `progress` 和 `progress_stage`。`BatchOut` 增加后端计算的 `progress`，避免前后端各自实现一套聚合公式。

兼容历史数据时，读模型按状态提供保守回退值：排队 0、解析 5、审查 15、校验 90、成功终态 100、失败 0。迁移对现有记录使用同一规则回填。

## 进度计算规则

### 单项审查进度

进度只能由已完成的工作提高，必须满足：

- 单调不减。
- 非成功终态不得写入 100。
- 每次更新都限制在 `0..100`。
- 同值更新不写数据库，避免高频无效提交。
- 只有阶段完成或顶层窗口完成时更新，不按 token、秒数或内部小循环写库。
- 更新必须同时校验 `contract_id`、`audit_generation` 和 `execution_token`，过期 worker 更新 0 行并停止上报。

窗口审查段按实际计划工作量计算。以法务和财务两个 Agent 的顶层窗口为工作单元：

```text
review_progress = 15 + floor(60 * completed_units / planned_units)
```

`planned_units` 在进入窗口审查前确定；每个工作单元只有在结果通过协议解析并写入检查点后才计为完成。若没有窗口工作单元，完成审查编排后直接进入 75%。重试只重做当前未完成单元，不降低已持久化进度。

### 批次处理进度

顶部进度表达“整个批次还有多少处理工作未结束”，而不是“成功审查率”。每项贡献值定义为：

- `done`、`review_required`、`failed`：100，表示该项已结束处理。
- 活跃项：使用其持久化 `progress`。

```text
batch_progress = round(sum(item_contribution) / total)
```

失败数量继续由现有 `failed` 字段单独展示。这样部分失败批次可以到 100% 的“处理完成”，同时不会把失败说成审查成功。

## 执行链路

1. worker 成功领取批次项并提交 execution token 后上报 5%。
2. 文档解析和质量判断完成后上报 15%。
3. 审查编排器在每个顶层 Agent 窗口完成并检查点持久化后，上报 15%-75%。
4. 主审候选生成完成后进入 `verifying`；证据核验、冲突处理和二次复核按已完成子阶段上报 75%-90%。
5. 最终决策完成、准备持久化时上报 `persisting`，范围 90%-99%。
6. 结果与合同终态原子提交后，将成功项设为 100% 和 `completed`。
7. 失败时保留当前百分比，只把 `progress_stage` 设为 `failed`；自动重试重新领取后沿用已有百分比并恢复到对应执行阶段。

进度更新失败不得使审查本身失败，但必须记录不含合同内容的结构化日志。最终结果事务仍负责写入权威终态和 100%，确保不会出现“审查完成但进度永久停在 99%”。

## 前端交互

- 沿用现有 1.5 秒轮询，不增加 WebSocket 或 SSE。
- 顶部使用确定型进度条展示 `batch.progress`，旁边继续显示“已处理 X / Y”和失败数量。
- 每份合同显示自己的确定型进度条、百分比和阶段文案。
- 活跃状态使用正常主题色；成功终态显示 100%；失败项使用红色状态和失败前百分比，并显示现有错误原因与重试入口。
- 页面刷新后从批次详情恢复进度，不从 0 重新播放动画。
- 不显示预计剩余时间，不在两次轮询之间伪造增长。
- 空批次保持 0%，长文件名、阶段文案和操作区在移动端换行且互不遮挡。

## 并发与故障边界

- 所有中间进度更新沿用现有 generation/execution-token 围栏，防止旧 worker 覆盖新执行。
- 数据库更新使用条件式 `UPDATE progress = max(current, candidate)` 的等价实现，保证并发和重试下单调。
- 进度是观测信息，不参与审查质量决策，也不改变失败分类、重试次数或终态状态机。
- 客户端轮询失败时保留最后一次进度并显示查询错误；恢复轮询后以后端值为准。
- 历史记录和旧客户端不依赖新字段即可继续读取原有状态字段。

## 验收标准

- 正常路径：进度依次经过真实阶段，成功终态只在结果持久化后显示 100%。
- 多文件：活跃项的真实百分比会推动批次进度，首份合同未完成时不再固定为 0%。
- 失败路径：失败项保留失败前百分比、红色标记和错误原因；批次仍能表示所有项目已处理。
- 重试路径：进度不倒退，旧 worker 无法更新新一代任务，成功后到 100%。
- 恢复路径：刷新页面后恢复持久化百分比和阶段。
- 空状态：无批次时不显示误导性进度；零项目聚合结果为 0%。
- 响应式：桌面与移动端的百分比、阶段、文件名和操作按钮无溢出或遮挡。
- 回归：现有批次创建、轮询、失败重试、结果直达和单合同审查仍可用。

## 测试范围

- 后端单元测试覆盖里程碑映射、窗口工作量、单调更新、失败保留、重试和批次聚合。
- 后端 API 测试覆盖新字段、历史记录回退和成功终态一致性。
- 数据库迁移测试覆盖 SQLite 升级、回填和降级；PostgreSQL 条件更新通过 SQLAlchemy 方言兼容性检查。
- 前端测试覆盖类型、store 聚合使用后端值、单项阶段文案、失败样式和轮询恢复。
- 浏览器实测覆盖正常、空、失败、刷新恢复和移动端视口。
- 完成前运行后端/前端相关测试、类型检查、构建及项目完整质量门禁。

## 非目标

- 不提供预计剩余时间。
- 不展示 token 级或逐句流式输出。
- 不引入 WebSocket、SSE 或新的消息基础设施。
- 不改变审查结论、风险算法、失败分类和重试策略。
