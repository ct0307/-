# 证据驱动的合同审查优化设计

## 1. 背景

项目首先参加线上评审，入围后进入现场答辩。本阶段不以增加 Agent 数量或堆叠概念为目标，而是把现有法务、财务双 Agent 审查链路从“能够运行”提升为“可验证、可追溯、可降级、可做消融实验”。

当前实现已经具备以下基础：

- BM25、向量检索、RRF 融合和精确条号路由；
- 法务、财务双 Agent 及结构化共享上下文；
- 确定性财务计算和少量确定性风险规则；
- 原文核验、逐风险检索、支持关系校验和二次复核；
- 检索、证据、要素、性能和批处理评测框架；
- 前端风险证据、协同审查和人工复核界面。

主要缺口是：真实 Cross-Encoder 尚未接入运行链路；法规时点没有贯穿审查上下文；支持关系判断仍偏词面；确定性规则覆盖与治理能力有限；提示词与编排逻辑耦合；财务 Agent 读取法务结论后再首审，存在锚定和错误传播风险；真实专家金标不足，无法证明专业准确率。

## 2. 目标与非目标

### 2.1 目标

1. 建立证据驱动的 Agentic RAG 审查链路，每项风险均可回溯至合同原文、查询计划、知识来源、适用性判断、规则命中和最终决策。
2. 将法务、财务 Agent 改为独立首审、结构化交接和交叉复核，量化双方独立贡献与纠错价值。
3. 将确定性检查升级为可版本化、可测试、可审计的规则体系。
4. 将提示词从编排代码中分离，支持版本管理、回滚和 A/B 对比。
5. 保持现有 API 和主要用户流程兼容，通过少量前端联动展示经验证的后端能力。
6. 使用冻结数据集和消融实验说明各项优化的真实贡献，不以模型自报置信度作为质量证据。

### 2.2 非目标

- 不在本阶段增加更多专业 Agent。
- 不建设通用知识图谱或完整 GraphRAG 平台。
- 不在缺少真实评测证据时启动模型微调。
- 不重新设计前端导航、路由和主要页面布局。
- 不将合成数据测试表述为真实企业专业准确率。
- 不自动替代法务、财务人员作最终专业决策。

## 3. 总体架构

```text
合同文本与结构化要素
        |
        v
   AuditOrchestrator
        |
        +-- 法务 Agent 独立首审 --+
        +-- 财务 Agent 独立首审 --+
                                   |
                                   v
                           ClaimNormalizer
                                   |
             +---------------------+---------------------+
             |                     |                     |
             v                     v                     v
         RuleEngine           QueryPlanner        原文事实核验
                                   |
                                   v
                           EvidenceRetriever
                 精确条号 / BM25 / 向量 / RRF / 精排
                                   |
                                   v
                           SupportVerifier
              权威性 / 时点 / 适用性 / 支持 / 矛盾
                                   |
                                   v
                         CrossAgentReviewer
                 去重 / 交叉复核 / 冲突保留 / 裁决
                                   |
                                   v
                            RiskDecision
                 accepted / manual_review / rejected
                                   |
                                   v
                         现有 API、前端和报告
```

### 3.1 模块职责

| 模块 | 职责 | 明确不负责 |
|---|---|---|
| `AuditOrchestrator` | 调度、超时、进度、失败隔离和结果聚合 | 不包含具体提示词和专业规则 |
| `LegalAgent` / `FinanceAgent` | 发现各自专业范围内的候选风险 | 不决定法规来源是否可靠 |
| `ClaimNormalizer` | 将候选统一为结构化 Claim | 不增加合同中不存在的事实 |
| `RuleEngine` | 执行可复现的确定性规则 | 不做开放式法律推理 |
| `QueryPlanner` | 生成、分类和记录检索计划 | 不判断检索结果是否正确 |
| `EvidenceRetriever` | 召回、融合、精排和元数据过滤 | 不生成风险结论 |
| `SupportVerifier` | 判断依据是否支持、模糊或反驳 Claim | 不新增未经授权的依据 |
| `CrossAgentReviewer` | 去重、交叉复核和冲突识别 | 不静默覆盖专业分歧 |
| `RiskDecision` | 按明确策略确定发布状态 | 不使用模型自报置信度作决定 |

现有 `audit_contract()` 保留为兼容入口，逐步把内部职责委托给新模块，避免 API、异步任务和前端一次性迁移。

## 4. Claim 数据契约

Agent 第一阶段只生成候选 Claim，不直接决定正式依据和最终发布状态。

```json
{
  "category": "付款条件不明确",
  "dimension": "payment",
  "subject": "甲方",
  "action": "支付尾款",
  "condition": "验收完成",
  "consequence": "支付20%合同款",
  "quote": "验收完成后支付剩余款项",
  "clause_ids": ["C-18"],
  "missing_information": ["验收确认主体", "付款期限"],
  "review_targets": ["legal"]
}
```

Claim 必须满足：

- `quote` 能够在授权合同文本中定位；缺失型风险使用明确的缺失状态，不伪造引文。
- `clause_ids` 使用解析层稳定 ID。
- 主体、行为、条件和后果只描述原文事实；推断写入后续验证结果。
- `review_targets` 仅表达跨专业复核需求，不代表另一 Agent 已同意。
- Claim Schema 需要独立版本号，并在审查快照和模型调用记录中保存。

## 5. RAG 优化设计

### 5.1 查询规划

每条 Claim 生成可序列化的多查询计划：

| 查询类型 | 作用 |
|---|---|
| `exact_reference` | 检索明确出现的法条号或制度条款号 |
| `legal_issue` | 检索法律概念和规范要求 |
| `fact_pattern` | 检索与合同事实条件相近的依据 |
| `applicability` | 加入合同类型、法域和适用范围约束 |
| `absence_requirement` | 判断缺失内容是否属于法定或制度必备要求 |

查询计划记录原始 Claim、查询类型、扩展词、过滤条件、生成方式和版本。首轮证据不足时只允许根据失败原因重写一次：没有召回时扩展同义词；召回不适用时增加类型或时点约束；召回相关但不支持时改写为更具体的事实问题。第二次仍不支持则进入人工复核。

### 5.2 检索路由与融合

- 明确法条号优先走精确检索。
- 金额、期限、税率和账户等字面事实提高 BM25 权重。
- 同义表达和抽象法律问题提高向量召回权重。
- 多路结果使用可配置的加权 RRF 融合，并保留每一路排名。
- 缺失型风险不得因召回普通相关法条直接判为有依据。
- 跨条款风险的查询必须同时保留相关条款 ID 和结构化事实。

### 5.3 元数据硬过滤

排序前检查以下字段：

- 法域、发布机关和效力层级；
- 生效日期、失效日期和替换链；
- 合同类型和风险维度；
- 企业制度的适用组织和业务范围；
- 知识发布状态和版本。

`as_of` 优先来源于合同签署、生效或相关履行时点，并记录选择理由。无法确定适用时点时，来源可作为候选材料保留，但不得自动认定适用，风险进入人工复核。

### 5.4 Cross-Encoder 精排

定义稳定接口：

```python
class Reranker(Protocol):
    def score(self, query: str, documents: list[str]) -> list[float]: ...
```

实现包含真实 `CrossEncoderReranker` 和保持融合顺序的 `NoopReranker`。精排器采用批量评分，记录模型、版本、耗时、输入候选数、排序变化和降级原因。超时或不可用时保留 RRF 结果，不丢弃已召回候选，也不得将降级结果标记为真实精排。

模型及运行依赖在实施阶段单独选型；安装或升级外部依赖前必须说明用途、来源和供应链风险并获得确认。

### 5.5 父子分块

- 子块负责召回，保留条号、款项和局部语义。
- 精排后回填完整父法条或制度条款供支持关系判断。
- 同一父法条的多个子块合并，不重复占用 Top-K。
- 合同原文保留条款层级、表格、附件、补充协议和优先顺序关系。

## 6. 规则引擎设计

### 6.1 规则类型

| 类型 | 示例 |
|---|---|
| 完整性 | 主体、金额、签署日期或必要条款缺失 |
| 格式 | 税号、账号和日期格式异常 |
| 数值 | 付款比例、大小写金额和违约金计算 |
| 时间 | 签署、生效、履行、验收和付款日期冲突 |
| 跨条款 | 正文、附件和补充协议对同一事项约定不同 |
| 主体关系 | 收款主体与合同主体不一致 |
| 法定必要性 | 特定合同类型缺少法定必要内容 |
| 企业制度 | 付款或审批安排超过内部制度阈值 |
| 升级 | 高风险、证据冲突或解析质量低时强制人工复核 |

### 6.2 规则定义与执行

第一阶段采用 JSON 定义和 Python Handler，不引入复杂 DSL：

```json
{
  "id": "FIN-PAYMENT-TOTAL-001",
  "version": "1.0.0",
  "name": "付款比例合计检查",
  "category": "numeric",
  "agent": "finance",
  "dimensions": ["payment"],
  "contract_types": ["采购合同", "服务合同"],
  "severity": "high",
  "effective_from": "2026-01-01",
  "handler": "payment_total",
  "manual_review_on_unclear": true
}
```

统一输出包含规则 ID、版本、状态、风险等级、条款 ID、标准化事实、计算过程和原因码。规则按照解析质量、事实抽取、完整性与格式、数值与时间、跨条款、法规和制度适用、模型 Claim 交叉验证的顺序执行。

规则遵循以下边界：

- `not_hit` 不代表合同没有风险。
- `unclear` 不得被当作通过。
- 模型与硬规则冲突时进入人工复核，不允许模型覆盖规则。
- 企业制度与国家法律分开管理，不混用效力层级。
- 规则变更提升版本，并支持定位需要重新审查的历史合同。

### 6.3 首批规则

P1 覆盖付款比例与基数、金额大小写与币种、含税口径、收款主体、付款与验收/发票条件、关键日期逻辑、正文与附件冲突。P2 覆盖违约金计算与责任对称性、自动续期与单方解除、知识产权归属、争议解决冲突等需要更多语义辅助的规则。

## 7. 提示词与双 Agent 协作

### 7.1 独立首审和结构化交接

法务和财务 Agent 第一阶段并行独立审查，互不可见，避免锚定。完成 Claim 标准化后，仅交换 Claim、原文位置、确定性事实和复核问题，不共享自由推理过程。

法务 Agent 负责主体、授权、效力、权利义务、违约、解除、知识产权、保密、数据和争议解决，并向财务发送金额、账户和付款复核信号。财务 Agent 负责金额、币种、税率、发票、付款、结算、现金流和收款主体，并向法务发送主体、授权和责任失衡复核信号。

交叉复核后保留三类结果：双方一致；一方纠正另一方；无法消解的冲突。冲突不得通过多数投票或后执行者覆盖前结果解决。

### 7.2 提示词分层和版本管理

每次调用由安全层、任务层、专业 Rubric、动态上下文和输出 Schema 五层组成。提示词从编排代码移入独立注册表，记录：

- Prompt ID、语义版本和模板哈希；
- 模型、参数和供应商；
- 输入与输出 Schema 版本；
- 合同窗口、知识版本和规则版本；
- 解析状态、失败代码、Token 和耗时。

Few-shot 只使用少量经过专业确认的正确样本、难负样本、信息不足样本和证据矛盾样本。示例不得作为正式法规依据。

### 7.3 强制放弃机制

Agent 必须能够输出 `insufficient_information` 和受控原因码。原文无法定位、上下文不足、法规时点不明、Agent 冲突、规则冲突、文件优先级不清或证据只相关但不支持时，结果进入人工复核。

二次复核支持独立 `VerifierAdapter`，温度固定为零，只能使用授权证据，并允许输出 `unclear`。使用同一模型复核只能表述为一致性检查，不能宣传为独立验证。

## 8. 证据支持关系 V3

支持关系按以下顺序验证：

1. 原文真实性：Claim 引文能否在授权合同版本中定位。
2. 来源权威性：来源是否来自已发布、可信且可追溯的知识记录。
3. 时点和范围适用性：来源是否在相关时间、法域、组织和合同类型下适用。
4. 事实一致性：主体、行为、金额、日期和条件是否与 Claim 一致。
5. 语义关系：依据是直接支持、条件不足，还是明确反驳 Claim。

最终状态保持 `supported`、`unclear` 和 `contradicted`。确定性验证器先执行硬门禁；可选语义验证器只处理硬门禁通过但语义关系不明确的候选。任何语义模型都不能绕过无权威来源、错误时点或原文不存在等硬门禁。

## 9. 决策和异常处理

### 9.1 发布状态

- `accepted`：原文已核验、来源可信且适用、支持关系明确、没有未解决规则或 Agent 冲突。
- `manual_review`：证据不足、条件不明、存在冲突、解析质量不足或关键时点不明。
- `rejected`：原文事实不存在，或者授权依据明确反驳候选 Claim。

### 9.2 降级策略

| 异常 | 行为 |
|---|---|
| Embedding 不可用 | 降级 BM25 并记录原因 |
| 精排器不可用 | 保留 RRF 顺序，不丢弃候选 |
| 无可靠法规 | 风险进入人工复核，不生成法规 |
| Agent 输出非法 | 有限重试，失败后产生结构化问题 |
| 法规时点不明 | 标记适用性待确认 |
| 规则与模型冲突 | 保留双方结果并升级人工 |
| Agent 之间冲突 | 建立冲突组，不自动覆盖 |
| 部分窗口失败 | 保留已验证结果并标记未完成范围 |

所有降级写入审计日志和结果快照，前端和报告不得把降级运行显示为完整高质量审查。

## 10. 数据、API 和前端边界

### 10.1 持久化

根据现有数据模型复用程度，在实施阶段确定新增独立表或扩展现有字段。需要持久化的最小信息包括：

- Prompt、规则、Claim Schema 和验证器版本；
- 查询计划、检索尝试、路由排名和精排模式；
- 法规适用时点及选择理由；
- 规则执行输入摘要、计算结果和原因码；
- Agent 首次发现者、交叉复核者、纠正和冲突状态；
- 最终决策、决策原因和人工复核要求。

完整合同原文、完整提示词和敏感输入不重复写入普通日志，优先保存稳定 ID、哈希、版本和必要摘要。数据库变更使用 Alembic，并提供升级、降级和旧记录默认值测试。

### 10.2 API 兼容

保留现有 `level`、`tier`、`evidence_status`、`support_relation_status`、`original_text_verified`、`rag_sources` 和 `cross_checks` 语义。新增字段优先采用可选嵌套对象，旧客户端缺少新字段时仍能工作。

### 10.3 最小前端联动

不新增大型页面，主要扩展风险复核抽屉、双 Agent 协同页和证据报告：

- 展示原文、依据支持、法规适用和人工复核状态；
- 展示查询类型、召回方式、精排模式和知识版本；
- 展示规则名称、版本、输入值和计算过程；
- 展示首次发现 Agent、交叉复核 Agent、纠正和冲突状态。

页面必须保留正常、空、错误、降级和移动端状态。后端核心改造完成并验证前，不提前修改前端展示。

## 11. 评测与验收

### 11.1 消融矩阵

在同一冻结数据集、同一模型和同一参数下比较：

| 版本 | 能力 |
|---|---|
| V0 | 当前基线 |
| V1 | 独立双 Agent 和版本化提示词 |
| V2 | V1 加规则引擎 |
| V3 | V2 加 Cross-Encoder 精排 |
| V4 | V3 加支持关系 V3 |

数据划分为开发集、验证集和盲测集。盲测集冻结后不得参与提示词、规则或阈值调优。

### 11.2 指标

| 层级 | 指标 |
|---|---|
| 检索 | Recall@5、Precision@5、MRR、nDCG@5 |
| 风险 | 分类 Precision、Recall、F1 和高风险 Recall |
| 证据 | 三分类 Macro F1、错误自动接受率 |
| 协作 | Unique Contribution Rate、Claim Correction Rate、冲突率 |
| 可信性 | 虚构原文率、错误法规引用率、Unsupported Claim Rate |
| 工程 | 成功率、P50、P95、Token、降级率和恢复率 |
| 人工成本 | 自动接受率、人工复核率和单位合同复核量 |

硬性质量要求包括：虚构原文率为零；未授权法规引用率为零；过期法规错误自动采信为零；检索和决策轨迹完整率为 100%；精排不可用时仍能完成降级审查。其余阈值根据冻结金标基线和专业人员批准后确定，不预先虚构达标数值。

### 11.3 测试范围

- 单元测试：查询规划、过滤、融合、精排降级、每类规则、支持关系和决策映射。
- 集成测试：双 Agent 独立首审、结构化交接、跨专业冲突、部分窗口失败和审计持久化。
- 迁移测试：Alembic 升级、降级和旧记录兼容。
- 安全测试：合同文本提示注入、未授权证据引用、日志敏感信息和越权读取。
- 性能测试：批量精排、并发窗口、缓存命中、P50/P95 和 Token 成本。
- 前端测试：正常、空、错误、降级、移动端和刷新恢复。
- 项目验收：相关测试、类型检查、构建和完整质量门禁。

## 12. 实施批次

| 批次 | 内容 | 前端变化 |
|---|---|---|
| P1-A | 冻结基线；拆分后端模块；保持行为一致 | 无 |
| P1-B | Claim Schema；独立双 Agent；Prompt Registry | 无 |
| P1-C | 查询规划；法规时点；精排接口和降级 | 无 |
| P1-D | 规则注册表；支持关系 V3；决策策略 | 无 |
| P1-E | 消融评测；迁移验证；质量门禁 | 无 |
| P2-A | API 增加可选审计字段 | 前端类型小改 |
| P2-B | 风险抽屉、协同页和报告展示 | 局部修改 |
| P3 | 付款、验收、发票、违约及附件关系的轻量图 | 可选 |

每个批次独立提交、独立验证并保持可回退。不得将结构重构、模型接入、数据库迁移和前端改造压入同一个不可审查的大提交。

## 13. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 模块拆分引入行为回归 | 先冻结基线与契约测试，再做等价重构 |
| 精排模型依赖和供应链风险 | 选型前审计；提供 Noop 降级；不把模型缓存提交仓库 |
| 双 Agent 并行增加成本 | 维度路由、窗口裁剪、批量调用和 Token 预算 |
| 规则过度扩张造成误报 | 规则只处理可证明事实；保留 `unclear`；逐条金标测试 |
| 语义验证器产生错误确定性 | 硬门禁优先；验证器不能覆盖原文、权威性和时点失败 |
| 数据集泄漏 | 开发、验证、盲测严格分离并保存哈希 |
| 前端展示超前于后端证据 | 后端指标和字段稳定后再进行最小联动 |

## 14. 完成定义

本设计进入实施完成状态需要同时满足：

1. 所有新增模块具备清晰接口和独立测试。
2. 现有 API 和主要前端流程保持兼容。
3. V0 至 V4 消融结果可重复生成并绑定代码、数据、模型、提示词和规则版本。
4. 降级、冲突和不确定状态不会被展示成自动通过。
5. 完整质量门禁通过，并完成正常、空、错误、降级和响应式前端验证。
6. 未取得真实脱敏专家金标前，项目材料不宣称真实专业准确率达标。
