# 高拟真合成 50+2 冻结合同测试集设计

## 1. 目标

为 A03 企业合同合规审查系统建立一套可审计、可复现、无真实隐私信息的合成测试集，用于：

1. 验证 50 份有效合同同批提交、异步处理、刷新恢复和终态一致性。
2. 验证 2 份协议级异常文件被独立拒绝，不污染有效批次。
3. 验证 DOCX、文本型 PDF 和扫描型 PDF 的解析能力。
4. 生成六要素预测并执行准确率预评测。
5. 固化文件、清单、预测和运行证据的 SHA-256，支持复核与重复验收。

本测试集属于高拟真合成预验收数据，不得写成真实企业合同、真实业务样本或赛题最终真实数据验收证据。

本测试集采用“现实合同画像先行、系统盲测”的原则。样本结构、字段缺失、文件形态和风险分布先依据公开示范文本及企业合同常见流转形态冻结，再交给系统处理。不得读取当前解析正则、提示词或已知缺陷后，反向修改合同措辞以提高通过率。

## 2. 非目标

- 不使用真实企业名称、统一社会信用代码、个人身份信息、银行账号、签名或印章。
- 不复制任何真实已签署合同全文。
- 不以生成器已知答案冒充双人独立复核的人工金标准。
- 不要求每份合同都出现“甲方”“乙方”“合同金额”“合同期限”“付款方式”等当前解析器容易命中的标题。
- 不因为系统只统计六要素，就删除现实合同中的附件、订单、验收标准、税务、知识产权、数据处理、保险和通知送达等内容。
- 不在缺少 Docker、PostgreSQL、Celery、LLM 或硬件条件时虚构对应实测结论。
- 不修改生产接口语义，不为了让数据集通过而降低解析、批次或评测规则。

## 3. 数据来源、现实基准与标识

合同结构参考公开示范文本的章节组织和《中华人民共和国民法典》合同编的一般规则重新编写。所有主体、项目、金额和履约事实由固定种子生成，名称统一采用明显虚构的“之江测试”系列主体。

官方示范文本通常比企业实际归档文件更规范，不能直接当作现实分布。案例还必须施加企业流转形态：业务部门自拟条款、法务修改稿、供应商版本、附件报价、订单引用、补充协议、签署页回传、扫描归档和历史格式差异。所有变化均预先写入画像，不能在看到系统结果后追加。

### 3.2 现实合同判定标准

“接近真实”不等于排版漂亮或字段齐全。每份样本必须同时具备交易背景、主体角色、履行对象、价税或计价机制、履约流程、责任分配和签署/版本状态；整批样本还必须覆盖：

- 草案 Word、电子定稿 PDF、完整扫描 PDF、混合文本/扫描 PDF。
- 至少 4 份 Word 草案包含修订痕迹、批注或版本水印；正式评测同时记录“接受修订后文本”和解析器实际可见文本的差异。
- 双方、多方、委托方/受托方、采购人/供应商、出租人/承租人等不同角色命名。
- 总价、单价据实结算、框架无固定总额、阶梯计费和含税/未税价格。
- 主合同、采购订单、补充协议、技术附件、报价清单和验收单之间的引用关系。
- 字段明确、字段分散、附件优先、正文与附件冲突、合法缺失和签署页补充信息。
- 低风险常规模板与存在可识别法律/财务风险的非理想合同，而不是 50 份“标准答案合同”。

每份有效合同在封面或首段标注“合成测试样本，仅用于系统验收”，页脚包含案例编号。该标识不得进入合同要素字段值，也不得使用与真实机关公章相似的图样。

## 4. 样本构成

### 4.1 有效样本

| 现实业务组合 | 数量 | DOCX | 文本型 PDF | 扫描/混合 PDF |
|---|---:|---:|---:|---:|
| 采购、供货与销售 | 12 | 3 | 5 | 4 |
| 技术、软件与数据服务 | 10 | 3 | 4 | 3 |
| 运维、咨询、培训与业务外包 | 8 | 2 | 4 | 2 |
| 房屋、设备与场地租赁 | 6 | 1 | 3 | 2 |
| 建设、装修、监理与承揽 | 5 | 1 | 2 | 2 |
| 人力资源、保险与员工服务 | 4 | 1 | 2 | 1 |
| 保密、数据处理与知识产权 | 3 | 2 | 1 | 0 |
| 框架订单、补充协议与多方合作 | 2 | 1 | 0 | 1 |
| 合计 | 50 | 14 | 21 | 15 |

有效样本编号为 `FC-001` 至 `FC-050`。所有文件必须可打开、正文非空、格式与扩展名一致。合同正文原则上为 4 至 30 页，其中至少 10 份超过 12 页、至少 12 份包含附件或清单、至少 5 份为三方或多方文本、至少 5 份存在合法空值、至少 4 份与主合同或订单形成版本关系。禁止重复同一模板只替换标题、金额和主体。

### 4.2 异常样本

| 编号 | 文件 | 异常 | 标准 50+2 预期 |
|---|---|---|---|
| `FX-051` | `FX-051-empty-corrupt.pdf` | 0 字节损坏 PDF | HTTP 400 |
| `FX-052` | `FX-052-spoofed.pdf.exe` | 伪装扩展名 | HTTP 400 |

另生成一个不计入 50+2 清单的补充样本 `SX-001-nonempty-corrupt.pdf`。它用于验证“创建批次返回 202，解析阶段进入 failed，且可以重试”的异步失败路径，不能声明为协议级 4xx 样本。

现实接入还常见 `.doc`、OFD、图片、压缩包、加密 PDF、数字签名 PDF 和损坏 DOCX。它们不混入标准 50+2，以免改变既有验收口径；在 `supplemental/intake-compatibility/` 建立独立兼容性矩阵，验证系统是可解析、明确拒绝还是需要产品补齐。该矩阵只报告现状，不以“扩展名不支持”掩盖企业接入缺口。

## 5. 合同内容变化维度

每份合同必须包含与其交易类型相称的核心条款，但不强制采用统一章节或齐全的六要素。样本之间组合以下变化：

- 金额：固定总价、含税/不含税、暂估价、分项价款、中文大写与阿拉伯数字并列。
- 期限：明确起止日期、签署后若干日、里程碑期限、自动续期和无明确终止日。
- 付款：预付款、到货款、验收款、质保金、月结、按里程碑支付及发票前置条件。
- 主体：简称、全称、多方主体、委托方/受托方、采购人/供应商、出租人/承租人等表达；部分主体信息仅位于签署页或附件。
- 版式：正文段落、关键字段表格、跨页条款、页眉页脚、附件清单。
- 风险：单方解除、责任上限失衡、自动续期、逾期付款、知识产权归属、数据跨境、排他、模糊验收和争议管辖等。
- 文档质量：清晰文本、轻度压缩、扫描倾斜、低对比度、页边阴影和混合文本/扫描页。

变化必须按案例定义表显式声明，禁止依赖运行时随机数。扫描扰动使用固定参数，确保首次冻结后不再漂移。

### 5.1 防迎合约束

- 案例画像和合同正文由公开结构来源及业务场景驱动，不从 `_ELEMENT_PATTERNS`、LLM 提示词或测试断言生成。
- 至少 40% 的样本不使用“甲方/乙方”作为主体唯一称谓。
- 至少 30% 的样本不出现“合同金额：”这一固定标题。
- 至少 20% 的样本采用据实结算、单价合同或框架无固定总价，`amount` 可以为 `null` 或计价规则。
- 至少 20% 的样本将期限、付款或标的分散在正文与附件中。
- 至少 10% 的样本包含正文与附件、通用条款与专用条款之间需要按优先级解释的差异。
- 解析失败或得分不足后，不允许就地改写冻结样本；只能修复系统，或在原因充分时创建新数据集版本并保留旧版结果。

## 6. 六要素与复核边界

六个评测字段严格使用现有 Schema：

- `party_a`
- `party_b`
- `subject`
- `amount`
- `duration`
- `payment_terms`

生成器输出 `construction-truth.jsonl`，记录创建每份合同时使用的完整结构化事实和六字段评测投影。现实合同允许字段为空、按公式计价或散落于多个附件；构造真值必须如实记录 `null`、多方主体、计价规则和引用来源，不能为了适配当前六字段 Schema 强行补齐。

`construction-truth.jsonl` 不伪造 `reviewers`，因此不得直接输入强制双人复核的正式 `evaluation.cli elements`。技术预评测使用独立的 `precheck.py`，只复用字段归一化和计分函数，并在报告标题、状态和 manifest 中固定标记 `construction_truth_only`。

生成器同时输出 `gold-review-template.jsonl`，其中审核人和复核状态保持未完成状态，供两名真实审核人独立核对。只有在两名审核人确认并按现有 Schema 填写 `reviewers`、`review_status`，必要时完成第三人裁决后，才能生成 `gold.jsonl` 并对外声称“冻结金标准准确率”。

在人工复核完成前，报告只能表述为“对构造真值的技术预评测”，不得表述为“要素准确率达到 90%”。

`source-register.md` 保存权威公开结构来源及使用边界；`corpus-profile.json` 先验声明类型、格式、页数、角色、缺失字段、附件和风险分布；`cases.json` 保存固定案例事实和变化标签。生成脚本只读取这些已审定文件，不读取解析器源码，不联网，不调用 LLM。

```text
outputs/frozen-contracts-v1/
├── contracts/
├── supplemental/
│   └── intake-compatibility/

├── freeze-manifest.json
```

二进制合同和运行证据保留在已忽略的 `outputs/`，不提交到 Git。`freeze-manifest.json` 记录生成器提交号、案例定义哈希、每个文件哈希、字节数、文档类型和冻结时间。

## 8. 生成实现

- 使用项目现有 Python 环境，不安装或升级依赖。
- DOCX 使用 `python-docx` 生成 A4 中文合同，显式设置页边距、字体、标题、表格宽度和页脚。
- 文本型 PDF 使用 PyMuPDF 写入固定字体和固定元数据。
- 扫描型 PDF 先生成排版页，再以固定 DPI 栅格化，施加固定的旋转、压缩、对比度和边缘阴影参数，最终 PDF 不保留文本层。
- 所有时间、编号、金额、主体和条款变体来自 `cases.json`，生成过程不读取系统当前时间作为业务内容。
- 先审核 `corpus-profile.json` 和 `cases.json`，再生成文件并以 SHA-256 清单冻结，最后才能运行系统测试。
- 后续测试默认只验证哈希，不自动覆盖已有冻结文件；重新冻结必须生成新版本目录，不提供覆盖当前版本的 `--replace` 快捷方式。

## 9. 验证流程

### 阶段 A：数据集静态验证

1. 校验案例编号唯一、类型与格式分布准确。
2. 校验 50 个 valid 和 2 个 invalid，文件路径无重复。
3. 校验所有 SHA-256 与冻结清单一致。
4. 校验有效 DOCX/PDF 可打开、正文或 OCR 结果非空。
5. 扫描真实姓名、身份证号、银行卡号、真实印章和未替换占位符。
6. 校验页数、附件、多方主体、字段缺失、版本关系及防迎合比例满足 `corpus-profile.json`。
7. 计算正文相似度，拒绝只替换少量变量的重复模板。

### 阶段 B：解析与构造真值预评测

1. 调用生产解析器读取 50 份有效合同。
2. 记录解析方式、字符数、OCR 置信度和人工复核标记。
3. 在合同文件和哈希冻结后，才允许调用当前六要素提取入口生成 `predictions.jsonl`。
4. 使用独立预评测入口对 `construction-truth.jsonl` 计分，分别报告总体、合同类型和文档类型结果；正式 CLI 保持拒绝未经双人复核的数据。
5. 对扫描型 PDF 单独计算文本识别覆盖率；如实现字符错误率指标，必须明确归一化规则。

### 阶段 C：真实 50+2 API 批测

1. 启动 FastAPI、Redis 和 Celery worker，使用隔离的验收数据库与存储目录。
2. 获取法务或管理员测试账号令牌。
3. 使用现有 `python -m evaluation.cli batch` 一次提交 50 份有效文件。
4. 等待全部有效项进入 `done`，刷新后终态保持一致。
5. 两份异常文件分别提交并返回清单声明的 400。
6. 保存追加式 `batch-events.jsonl` 和原子写入的运行 manifest。

若本机缺少 Redis、Celery、LLM 凭据或其他外部条件，阶段 C 状态必须为 `blocked`，不能用单元测试替代真实 API 结论。

现有批次接口对整批文件只接收一个 `contract_type`。因此混合 50 份同批测试统一使用“综合业务合同冻结集”作为批次元数据，只证明吞吐、失败隔离和状态恢复，不证明类型化 RAG 审查正确。类型化审查必须另按实际合同类型分组执行，报告不得混用两类结论。

### 阶段 D：补充失败隔离

单独提交 `SX-001-nonempty-corrupt.pdf`，验证任务进入 `failed`、批次终态为 `failed`、失败原因安全可读、重试次数增加且有效批次证据不受影响。

## 10. 通过标准

| 验收项 | 通过标准 |
|---|---|
| 数据集构成 | 50 valid + 2 invalid，分布与设计一致 |
| 现实画像 | 类型、格式、页数、角色、附件、版本和缺失字段达到先验比例 |
| 冻结完整性 | 所有文件 SHA-256 匹配，无重复路径或重复内容 |
| 有效文件解析 | 50 份均返回非空文本；扫描件进入预期 OCR 路径 |
| 协议异常 | 两份异常样本分别返回 HTTP 400 |
| 批次终态 | 50 个有效项全部 `done`，`failed=0`，刷新后状态一致 |
| 技术预评测 | 报告真实结果，不预设必须达到 90% |
| 人工金标准评测 | 双人复核完成后，六要素宏平均 F1 不低于 0.90 |
| 隐私检查 | 不含真实个人、企业、账户、签章或密钥 |
| 证据 | 输入、清单、预测、Schema 和事件日志均有 SHA-256 绑定 |

若任何标准未满足，保留失败报告和最小复现案例，先诊断根因；不得修改金标准迁就当前预测结果。

## 11. 测试与回归

新增自动化测试覆盖：

- 案例定义及格式分布。
- 现实画像、防迎合比例和正文相似度阈值。
- 确定性编号和金额生成。
- 冻结清单哈希校验与拒绝静默覆盖。
- DOCX 表格、PDF 文本层和扫描 PDF 无文本层特性。
- 50+2 batch manifest 与现有加载器兼容。
- construction truth 到预测格式的字段映射。
- 技术预评测不会生成满足正式金标准 Schema 的伪审核记录。
- 异常样本的扩展名、空文件和预期状态码。
- 历史/加密/签名/图片等补充格式的支持或明确拒绝状态。
- 隐私模式及占位符扫描。

实现后先运行专项测试，再运行解析预评测，最后运行项目完整质量门禁。阶段 C 的外部服务型验收单独报告，不与默认门禁混淆。

## 12. 交付结论口径

完成阶段 A、B 后，可表述为：

> 已建立 50+2 高拟真合成冻结测试集，完成文件完整性、解析、OCR 和构造真值技术预评测。

只有阶段 C 真实执行通过后，才可表述为：

> 已在本次记录的服务环境中完成 50 份有效合同同批处理与 2 份异常文件隔离验收。

只有双人复核金标准完成并通过正式评测后，才可表述为：

> 合同要素抽取在本版本冻结金标准上的宏平均 F1 达到报告值。

所有结论必须同时附带数据集版本、运行 ID、提交号、环境边界和证据路径。

## 13. 专业审查结论

原设计可以验证项目现有能力，但不足以代表企业真实合同，主要偏差是 Word 文件过多、默认字段齐全、主体称谓标准化、缺少文档关系，以及混合批次类型结论不清。本版已将这些问题改为强制约束。

按本版规格生成的合同在结构、长度、文件形态、条款关系和非理想数据方面可以接近现实企业合同，适合作为产品预验收和回归测试集；但它仍是合成数据，不能替代企业授权脱敏样本。正式商用前至少还应在数据处理协议下，引入一批经授权、脱敏、按行业分层的历史合同进行独立外部验证。
