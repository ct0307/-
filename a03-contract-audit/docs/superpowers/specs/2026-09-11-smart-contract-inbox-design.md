# 智能合同收件箱设计

## 1. 背景与结论

当前合同审查页将“上传文件、确认合同类型、设置审查参数、启动审查”集中在同一个表单中。单份合同可以完成基本闭环，但在真实政企场景下存在以下问题：

- 单份上传与批量上传分成两套入口、两套状态，用户需要先判断该走哪条路径。
- 合同类型虽然已有基于文件名和解析结果的关键词建议，但不会自动填入，也没有置信度分级。
- 批量任务要求所有文件共用一个合同类型，无法自然处理混合类型合同。
- “归属部门”固定显示当前账号部门，但没有解释其用途，也未覆盖法务代业务部门上传的场景。
- 上传失败、解析失败和已审查合同都容易被用户理解为同一种“失败记录”，实际删除后果却完全不同。

本设计采用“智能合同收件箱”方案：先完成统一收件、逐文件预检和分类，再从已就绪合同创建审查批次。单份上传是批量上传只有一份文件的特例，不再维护独立流程。

## 2. 使用场景与角色

系统面向大型企业和政务单位，主要使用模式为：

1. 法务或合规人员集中处理多个业务部门提交的合同。
2. 业务人员上传本部门合同，由法务和财务协同审查。
3. 用户一次上传 50 份以上合同，其中可能包含多种类型、扫描件和异常文件。

因此，产品必须同时支持集中代办和部门自助，不能把上传者部门永久等同于合同的数据归属部门。

| 角色 | 数据范围 | 数据归属部门 | 主要操作 |
|---|---|---|---|
| 业务人员 | 本部门 | 自动取账号部门并锁定 | 上传、修改合同类型、移除自己的失败记录、查看结果 |
| 法务/财务 | 账号配置的授权部门集合，未配置时仅限本部门 | 代上传时允许在授权部门集合内选择或批量修改 | 批量确认、启动审查、处理异常 |
| 管理员 | 全部部门 | 可修改 | 跨部门处理、恢复软删除草稿、查看完整日志 |

## 3. 产品目标与非目标

### 3.1 产品目标

- 单份和批量合同使用同一个导入入口和待审队列。
- 系统自动识别每份合同的类型，并允许用户人工修改。
- 同一批文件可以包含不同合同类型，单份失败不阻塞其他合同。
- 普通用户不需要重复填写可由账号确定的部门信息。
- 失败项提供符合数据后果的重试、移出、删除草稿或作废操作。
- 上传、分类和部门变更可审计；已落库业务数据使用软删除或作废，支持按保留策略恢复。

### 3.2 首期非目标

- 大文件分片和断点续传。
- 自动拆分包含多份独立合同的扫描合订本。
- 多级部门会签流程。
- 用分类结果自动替代用户对低置信度结果的确认责任。

## 4. 页面结构与主流程

原“合同上传”和“批量合同上传”合并为一个“待审合同”工作区。

### 4.1 页面区域

1. **导入区**：支持点击选择、拖拽文件和选择文件夹；支持 PDF、DOCX、TXT。
2. **状态摘要**：显示文件总数、可审查、待确认、处理中和失败数量。
3. **待审队列**：按文件展示合同类型、数据归属部门、处理状态和可用操作。
4. **批量操作栏**：对选中项批量设置类型、部门和审查维度，并提交就绪项。
5. **详情预览**：查看解析文本、关键要素、识别依据和异常原因。

移动端将每行转换为纵向信息块，保留选择、类型修改、错误原因和主要操作。批量工具栏固定在可视区域底部，但不得遮挡列表内容。

### 4.2 用户流程

1. 用户一次选择一份或多份合同。
2. 客户端先校验扩展名、大小和同批重名。
3. 后端逐文件执行加密存储、文本解析、重复检测和合同类型识别。
4. 高置信度合同自动进入“可以审查”；中低置信度和特殊合同进入“待确认”。
5. 用户只处理待确认或失败项，也可人工修改任何未进入审查的合同类型。
6. 用户选中已就绪合同并启动审查；未就绪项继续保留在收件箱。
7. 系统创建独立审查批次，每份合同携带自身确认后的类型和归属部门。

## 5. 合同类型规则

### 5.1 自动识别与人工修改

识别结果包含建议类型、置信度和命中依据。首期按以下阈值控制交互，阈值集中在后端配置中，不散落在页面代码中；P3 再提供管理员可视化调节能力：

| 置信度 | 系统行为 | 用户要求 |
|---|---|---|
| 85% 及以上 | 自动选中建议类型，状态可直接就绪 | 可修改，不额外阻断 |
| 60% 至 84% | 自动选中建议类型，标记“待确认” | 审查前必须确认或修改 |
| 低于 60% | 不自动选中，显示候选类型 | 必须手动选择 |

用户每次人工修改都记录原类型、新类型、模型建议、置信度、操作者和时间。此数据可用于后续评估分类准确率，但首期不自动训练模型。

### 5.2 混合类型批次

合同类型是文件级属性，不是导入批次级属性。批量上传后每份合同独立分类，用户也可以选中多行进行批量覆盖。创建审查批次时，后端逐项接收并保存确认类型，不能再用一个 `contract_type` 覆盖整批。

### 5.3 复合合同与合并文件

需要区分两个概念：

- **复合合同**：一份合同同时具有多个交易属性，例如软件开发加运维服务。用户选择一个主类型，并添加零个或多个辅助类型标签；审查规则按主类型和辅助类型取并集，重复规则只执行一次。
- **合并文件**：一个文件包含多份法律上独立的合同。系统标记“疑似包含多份合同”并阻止直接审查，提示用户拆分文件，或明确确认其属于“主合同及附件”。首期不做自动拆分。

## 6. 数据归属部门

“归属部门”应改名为“数据归属部门”，并保留。它不是合同审查条件，而是以下能力的基础：

- 数据访问隔离。
- 部门维度报表。
- 审查任务分派和责任追踪。

普通业务人员上传时自动使用账号部门并锁定，不要求填写。法务和财务账号维护明确的授权部门集合，未配置时仅能访问本部门；代上传时只能在该集合内选择或批量设置。管理员可以访问全部部门。授权关系由管理员维护，所有接口均在服务端校验，不能只依赖前端隐藏选项。

跨部门合同仍只设置一个主归属部门，用于权限和统计；协作部门作为独立字段维护，不将主归属字段改成多选，避免权限边界含糊。首期若尚未实现协作部门，可仅保留主归属部门，不阻塞核心流程。

## 7. 状态与操作语义

### 7.1 导入项状态

| 状态 | 含义 | 允许操作 |
|---|---|---|
| 待上传 | 文件只在客户端选择列表中 | 移出列表 |
| 上传中 | 正在传输或等待服务端确认 | 查看进度；首期不支持中途删除 |
| 上传失败 | 后端未生成合同记录 | 重试、移出记录 |
| 解析中 | 文件已加密入库，正在解析 | 查看进度 |
| 解析失败 | 文件已入库但未形成可审查文本 | 重新解析、删除合同草稿 |
| 待确认 | 解析成功，但类型或业务信息需要确认 | 预览、确认或修改 |
| 可以审查 | 必填信息完整 | 选择、预览、修改、删除草稿 |
| 审查中 | 已进入审查任务 | 查看进度、取消任务；禁止删除 |
| 已审查 | 已产生审查结果 | 查看、作废、归档；禁止物理删除 |

### 7.2 删除规则

界面不统一使用含糊的“删除记录”，而是按数据后果显示操作：

- **移出列表**：仅移除客户端待上传项或未落库的上传失败展示，无需二次确认。
- **删除合同草稿**：对已落库但未进入审查的合同执行软删除；需要二次确认并记录审计日志。默认进入回收站 30 天，期间管理员可以恢复；期限由部署配置统一设置，到期后物理清理加密原文件，但永久保留不含合同正文的删除审计事件。
- **作废合同**：对已产生审查结果的合同标记作废，保留合同、结果和完整操作链。
- **归档合同**：从日常工作列表隐藏，但数据仍可查询和恢复。

批量“清除失败记录”只能清除未落库的失败展示，不得连带删除已成功上传的合同。

## 8. 系统与数据设计

### 8.1 批次边界

引入“导入批次”和“审查批次”两个独立概念：

- 导入批次负责文件收件、上传、解析、类型建议和人工确认。
- 审查批次只接收已就绪的合同，负责审查任务调度、重试和结果汇总。

导入批次中的部分合同可以创建审查批次，剩余合同继续处理。审查失败不改变导入结果，也不要求重新上传文件。

### 8.2 建议的数据调整

在不破坏现有 `Contract` 和 `AuditBatch` 语义的前提下，新增或扩展以下数据：

| 数据 | 关键字段 | 用途 |
|---|---|---|
| 导入批次 | `id`、`owner_id`、`department`、计数、状态、创建时间 | 恢复本次收件上下文 |
| 导入项 | `batch_id`、`contract_id`、文件名、状态、错误码、重试次数 | 每份文件独立处理 |
| 类型识别 | `suggested_type`、`confidence`、`evidence`、`confirmed_type`、`confirmed_by` | 支持建议、确认和评估 |
| 合同类型标签 | `contract_id`、`type`、`is_primary` | 支持复合合同 |
| 合同生命周期 | `deleted_at`、`voided_at`、`archived_at`、操作者 | 区分软删除、作废和归档 |
| 协作部门 | `contract_id`、`department` | 可选的跨部门协作能力 |

数据库迁移需要兼容已有合同：现有 `contract_type` 迁移为主类型；没有识别记录的历史数据视为人工确认结果。

### 8.3 接口原则

- 导入接口接收多文件，但逐文件返回或查询状态，单项失败不回滚整批。
- 文件上传使用幂等键；网络重试不得生成重复合同。
- 类型确认接口支持单项修改和批量修改，并执行部门权限校验。
- 创建审查批次时传入文件级 `contract_id + confirmed_type + dimensions`，服务端再次校验每项是否就绪。
- 草稿删除、作废和归档使用不同接口，不通过同一个通用删除接口猜测意图。
- 所有列表和详情响应返回稳定错误码，界面文案由错误码映射，不能依赖解析任意后端字符串。

## 9. 错误处理与恢复

| 异常 | 产品行为 |
|---|---|
| 客户端格式或大小不合法 | 上传前阻止，逐项显示明确原因，可直接移出 |
| 网络中断或响应丢失 | 使用原幂等键按文件重试，查询服务端确认结果 |
| 文件存储失败 | 不生成合同；其他文件继续处理 |
| 文本解析/OCR 失败 | 保留加密原文件，允许重新解析或删除草稿 |
| 类型置信度不足 | 进入待确认，不计为技术失败，不影响其他合同 |
| 页面刷新或重新登录 | 从服务端恢复导入批次与逐项状态，不依赖前端内存记录 |
| 审查任务失败 | 保留导入合同，只重试对应审查项 |
| 删除与任务并发 | 服务端校验状态和版本；审查中拒绝删除并返回稳定冲突码 |

## 10. 交付优先级

| 优先级 | 范围 | 价值 |
|---|---|---|
| P1 | 统一待审队列、文件级类型、置信度确认、混合批次、失败项移出、草稿软删除与恢复、角色化部门权限、服务端状态恢复、审计留痕 | 建立真实可用的上传审查闭环 |
| P2 | 批量设置与筛选、复合合同辅助类型、疑似合并文件提示、失败项批量清理 | 提升大批量处理效率和边界覆盖 |
| P3 | 人工修正率和处理耗时分析、分类阈值可视化管理、协作部门、多维运营指标 | 支撑持续优化和管理决策 |

## 11. 验收标准

### 11.1 正常路径

- 同一入口可上传 1 份或至少 50 份合同，无需切换单份/批量模式。
- 一个批次内的采购、软件开发、租赁等不同合同可得到各自类型，并在一次操作中提交审查。
- 高置信度结果自动就绪；用户可在审查前修改类型，最终审查使用修改后的值。
- 业务人员无需填写部门；法务代上传时可在授权范围内选择部门。

### 11.2 空状态与异常路径

- 无合同状态明确展示导入入口，不显示无意义的必填错误。
- 单份上传或解析失败不会使其他合同消失或停止处理。
- 上传失败项可直接移出；解析失败项显示重试和删除草稿，且文案说明后果。
- 软删除草稿在默认 30 天内可由管理员恢复；超过配置期限后原文件被清理，删除审计事件仍可查询。
- 页面刷新后仍能恢复批次状态；重复提交相同幂等请求不产生重复合同。
- 只有就绪项可被选入审查，待确认和失败项不会阻塞就绪项。

### 11.3 权限与审计

- 业务人员无法把合同改到其他部门，也无法查看其他部门合同。
- 法务、财务和管理员只能在授权范围内调整归属部门。
- 类型修改、部门变更、草稿删除、合同作废和归档均可追溯操作者、时间和前后值。
- 已审查合同没有物理删除入口；并发审查中的合同不能被删除。

### 11.4 响应式与可访问性

- 桌面端表格字段不重叠，长文件名截断后可查看完整名称。
- 移动端以纵向信息块展示，不出现横向页面溢出，底部操作栏不遮挡内容。
- 状态不能只依赖颜色表达；图标按钮有可访问名称和悬浮说明。
- 错误信息与对应文件绑定，用户无需从全局提示反推失败对象。

## 12. 测试范围

- **后端单元/接口测试**：文件级类型、阈值边界、幂等上传、权限校验、状态冲突、软删除和审计日志。
- **前端组件测试**：不同状态的操作可见性、类型确认、批量选择、错误码映射和移动端布局。
- **端到端测试**：单份上传、50 份以上混合批次、部分失败、刷新恢复、人工改类型后审查、跨部门权限和删除语义。
- **人工视觉验收**：桌面与移动端的正常、空、加载、错误和长文本状态。

性能与准确率结论必须基于真实数据实测。未运行真实 52 文件集、OCR 准确率或目标硬件能耗测试时，不得写成已经达标。
