# 契鉴协作验收包设计规格

## 1. 目标

生成一套可发送给老师和组员的协作验收包，使接收者能够在自己的 Windows 电脑上了解当前项目进度、启动项目、执行分工测试、填写统一结果，并补齐正式测试报告所需的人工材料与准确率证据。

验收包必须同时满足以下目标：

1. 不泄露密钥、Token、真实合同、个人信息或本机环境数据。
2. 接收者不依赖原开发者的虚拟环境和 `node_modules`，可按锁定依赖重新安装。
3. 所有人工测试结果使用统一模板，能够汇总为正式测试报告。
4. 准确率只依据人工复核并冻结的金标准计算，不使用演示数据或模拟数字替代。
5. 测试失败也必须保留日志和截图，不能只回传通过结果。

## 2. 交付范围

最终交付一个 ZIP 文件，解压后目录结构如下：

```text

├─ 00_请先阅读/
```

## 3. 文档设计

### 3.1 项目进度反馈

面向老师和组员，内容包括：

- 项目定位和赛题目标；
- 已完成的核心业务闭环；
- 当前自动化验证与已有证据；
- 尚未完成的参赛材料和外部验收项；
- 本轮协作测试目标；
- 需要老师和组员提供的人工材料；
- 后续里程碑、责任人和回传时间填写区。

文档必须区分“已由本机新鲜验证”“历史记录显示通过”“等待外部测试”三类状态，避免把历史结果写成本轮实测结果。

### 3.2 启动与测试指南

默认目标环境为 Windows 10/11，提供两条路径：

- 本地开发路径：Python 3.11、Node.js、SQLite、Vite；
- Docker 路径：供具备 Docker Desktop 的成员验证 PostgreSQL、Redis、Celery 和 Nginx 拓扑。

指南包括环境检查、依赖安装、配置复制、启动顺序、演示账号、自动化测试命令、人工测试步骤、常见错误、日志位置和结果回传规则。不得写入真实密钥，所有配置从 `.env.example` 复制后由测试者本机生成。

### 3.3 标注说明

要素准确率按照现有 `backend/evaluation/schema.json` 和 `docs/evaluation/element-accuracy-protocol.md` 执行，覆盖：

- 甲方；
- 乙方；
- 合同标的；
- 合同金额；
- 履约期限；
- 收付款节点。

每份合同至少由一人标注、一人复核。冻结后记录样本编号、文件名、合同类型、文档类型、标注人、复核人、版本和冻结日期。扫描件另需提供人工校对文本，供 OCR 字符准确率测试使用。

风险标注必须记录风险原文、风险类别、风险等级、建议法规依据和复核意见。风险准确率证据与要素准确率分开统计，不得混为同一指标。

## 4. 表格设计

### 4.1 测试任务分工

字段包括任务编号、优先级、测试模块、测试类型、负责人、协作者、目标机器、计划日期、状态、回传文件和备注。负责人、日期由团队人工填写。

### 4.2 功能测试用例

覆盖登录与权限、合同上传、文档解析、要素抽取、双 Agent 审查、RAG 证据、人工复核、整改闭环、报表导出、知识库、审计管理、批量任务、异常恢复、响应式和部署。每条用例包含前置条件、操作步骤、预期结果、优先级、自动化覆盖状态和证据要求。

### 4.3 测试结果填写模板

字段包括测试者、机器环境、版本提交、开始/结束时间、用例编号、实际结果、通过状态、缺陷编号、日志路径、截图路径和复测结论。统计页使用公式计算总数、通过数、失败数、阻塞数和通过率。

### 4.4 合同要素金标准模板

工作簿包括填写说明、样本清单、六项要素标注、双人复核和冻结检查。关键字段不能为空；状态未达到“已复核并冻结”的样本不得进入正式准确率计算。

### 4.5 风险标注模板

工作簿记录合同编号、条款位置、风险原文、风险分类、风险等级、法规名称、法规条款、人工判断、标注人、复核人和争议说明。该模板用于后续风险召回率、分类准确率和法规引用真实性评测，不在缺少复核时生成达标结论。

## 5. 人工材料清单

| 优先级 | 材料 | 最低要求 | 用途 |
|---|---|---|---|
| P0 | 脱敏合同测试集 | 建议 30 至 50 份，覆盖 PDF、DOCX、扫描 PDF | 功能与准确率测试 |
| P0 | 六项要素金标准 | 每份均有标注人与复核人 | 要素宏平均 F1 |
| P0 | 数据授权与脱敏确认 | 明确允许比赛测试和团队内部使用 | 数据安全 |

| P1 | 50 有效加 2 异常文件 | 文件集冻结并记录哈希 | 批量处理验收 |
| P1 | 扫描件人工校对文本 | 与扫描文件逐一对应 | OCR 字符准确率 |
| P1 | 风险与法规人工标注 | 风险原文、类别、等级、依据均复核 | 风险与 RAG 评测 |

## 6. 源码净化与安全边界

源码副本从 Git 跟踪文件和明确允许的未跟踪交付物生成，不直接复制整个工作目录。必须排除：

- `.git`、`.planning`；
- `.env`、Token、密钥和本机账号配置；
- `.venv`、`node_modules`、构建产物与缓存；
- `backend/storage`、项目根目录 `storage`、数据库文件和上传文件；
- Playwright 临时目录、截图缓存和日志；
- 未获授权的合同、姓名、联系方式和公司敏感数据；
- 指向本机的绝对路径和临时文件。

保留 `.env.example`、依赖锁文件、迁移、评测工具、测试代码、部署配置和必要的演示数据生成脚本。生成 ZIP 前输出文件清单，并执行密钥模式、绝对路径、数据库和大文件扫描。

## 7. 数据与证据流

```text
项目方生成脱敏验收包
  -> 老师/组员按任务分工测试
  -> 人工标注并双人复核金标准
  -> 回传表格、日志、截图和冻结数据
  -> 运行统一评测工具生成 JSON/CSV
  -> 汇总正式测试报告和准确率结论
```

任何缺少样本版本、复核人或数据集哈希的结果只作为探索性结果，不进入正式结论。

## 8. 错误与异常处理

- 依赖安装失败：记录完整命令、错误日志、Python/Node 版本和网络环境。
- 服务启动失败：记录端口占用、配置项、后端日志和浏览器控制台信息。
- 测试用例失败：不得修改预期结果规避失败，必须登记缺陷并保留证据。
- 标注存在争议：状态设为“待仲裁”，不进入冻结数据集。
- 合同无法脱敏：不得放入验收包，改用经授权样本。
- 无 Docker、OpenClaw、GPU 或功率数据：对应项目标记为“未测量”或“阻塞”，不得估算。

## 9. 验收标准

协作验收包只有在以下条件全部满足后才能交付：

1. ZIP 可正常解压，目录和入口文档完整。
2. Word 文档结构、中文编码、表格和分页经渲染检查。
3. Excel 工作簿公式无错误，关键表头、下拉选项和冻结窗格可用，所有工作表经渲染检查。
4. 源码副本通过密钥、绝对路径、数据库、上传文件和大文件扫描。
5. 本地启动路径至少完成一次实际启动与核心页面验证。
6. 后端测试、前端测试、类型检查和生产构建使用本轮新鲜命令记录结果。
7. 准确率模板与现有 JSONL schema 字段一致，并可转换为评测工具输入。
8. README 和进度反馈中的测试数量、日期和状态与本轮结果一致。
9. ZIP 文件生成 SHA-256，便于老师和组员核验传输完整性。

## 10. 非目标

本任务不负责虚构人工金标准，不替代法务专业复核，不承诺缺少样本时达到 90% 准确率，不安装或打包未经审计的新外部依赖，不部署到公网，也不修改生产环境。
