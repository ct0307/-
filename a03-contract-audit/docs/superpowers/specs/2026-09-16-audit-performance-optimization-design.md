# 合同审查性能优化设计

## 1. 背景

当前合同审查已形成“解析→法务 Agent→财务 Agent→RAG 依据校验→二次复核→发布”的完整质量链。近期完整审查记录显示，多数任务的 LLM 调用时延约占总时长的 `91%–97%`，主要耗时来自逐条 enrichment、逐条二次复核和串行窗口处理。

系统还存在两类可确定消除的重复计算：上传阶段已完成文档解析，审查阶段却重新解析同一文件；RAG 每次检索都重新加载全量知识切片并解析 JSON 向量。

本设计以不降低审查质量为前提，先减少模型调用数，再消除确定性重复计算，最后在明确的数据库写入边界内引入受控并发。

## 2. 目标

| 优先级 | 目标 | 验收方向 |
|---|---|---|
| P1 | 二次复核每批最多 5 条 | 逐项权限校验，正常调用数接近 `ceil(n/5)` |
| P1 | 同一审查窗口内 enrichment 每批最多 5 条 | 不跨窗口，失败项可单独回退 |
| P1 | 复用上传阶段完整解析结果 | 缓存命中与重新解析结果完全一致 |
| P2 | 建立可靠失效的 RAG 进程快照 | 知识未变时不重复全表加载和向量 JSON 解析 |
| P2 | 模型请求受控并发 2–3 | 法务到财务的依赖不变，数据库仍为单写者 |
| P2 | 建立质量和性能双门禁 | 不以降低风险、证据或复核覆盖率换取速度 |

## 3. 非目标

- 不并行法务 Agent 与财务 Agent；
- 不改变审查维度、风险等级、证据授权或人工复核标准；
- 不为降低调用数而增大单窗口的 8000 字上限；
- 不安装新的缓存、向量数据库或并发框架；
- 不把开发环境 SQLite 压测结果等同于生产 PostgreSQL 性能结论；
- 未完成真实模型 A/B 时，不宣称审查质量与速度已达到生产指标。

## 4. 总体方案

```text
加密合同文件
  -> 解析缓存查找
       -> 命中：校验并还原 DocumentParseResult
       -> 未命中/损坏：重新解析并原子替换缓存
  -> 法务 Agent
       -> 分窗口发现候选
       -> 同窗口批量 enrichment
       -> 失败项单条回退
  -> 财务 Agent（读取法务共享上下文）
       -> 同样的分窗口批量路径
  -> RAG grounding
       -> 按知识修订号复用不可变快照
       -> 每条风险仍独立验证证据支持关系
  -> 批量二次复核
       -> 逐 claim 校验证据白名单
       -> 失败项单条回退
  -> 主线程按确定顺序保存检查点、观测和最终结果
```

核心原则是将“计算并发”与“状态发布”分开：工作单元可并发请求模型，但数据库检查点和审查结果只能由调度线程串行写入。

## 5. enrichment 批量化

### 5.1 批次边界

- 只将同一 `ReviewWindow` 内、同一 Agent 和同一审查维度集合的候选放入同一批；
- 每批最多 5 条，不跨窗口重复拼接多段合同正文；
- 每条候选使用 `window_id + category + quote` 的确定性摘要作为 `candidate_id`；
- 请求仅携带一份窗口正文和候选列表，输出仅含 `candidate_id`、`reason` 和 `suggestion`。

### 5.2 逐项校验与回退

- 返回 ID 必须是请求集合的子集，且不得重复；
- 每项字段仍执行严格 Pydantic 长度、类型和额外字段校验；
- 缺失项、重复项或单项无效只标记相应 `candidate_id`，已通过的项不重试；
- 批量请求整体超时、被截断或无法解析时，未验证项回退到现有单条路径；
- 继续保留原有召回、截断恢复、分页和截止时间语义。

## 6. 二次复核批量化

- 复用已有 `SecondaryEnvelope.decisions` 最多 5 项的协议上限；
- 每个 `claim_id` 携带自己的 `authorized_evidence`，不建立批次级共享证据池；
- 确认决定必须引用至少一条该 claim 授权证据，证据 ID 不得跨 claim 使用；
- 返回未请求 claim、重复 claim 或自由文本理由时，相应项视为无效；
- 批量结果允许部分成功，缺失或无效项按剩余截止时间退回单条复核；
- 单条回退失败时仍转为 `manual_required`，不将未验证结论发布为已确认。

## 7. 解析结果缓存

### 7.1 数据模型

新建与合同一对一的 `contract_parse_caches` 表：

```text
contract_parse_caches
  id
  contract_id              唯一外键，删除合同时级联删除
  content_sha256           文件内容标识
  parser_signature         解析实现、依赖和参数标识
  payload                  序列化后的加密 DocumentParseResult
  created_at
  updated_at
```

`payload` 使用现有 `encrypt_bytes()`/`decrypt_bytes()`，不新增明文正文字段。未配置 `FILE_ENCRYPT_KEY` 的开发环境沿用项目现有明文兼容语义；生产环境仍由现有安全配置门禁强制有效密钥。

### 7.2 签名与失效

`parser_signature` 由以下内容的稳定序列化结果计算 SHA-256：

1. 解析缓存结构版本；
2. `extractor.py`、`ocr.py` 和 TXT 严格解码模块的代码字节哈希；
3. OCR 页数、像素、超时和置信度参数；
4. 影响解析结果的关键库版本。

查询时要求 `contract_id`、`content_sha256` 和 `parser_signature` 全部匹配。解密、JSON 解析、协议校验或匹配任一失败时，记录不含正文的安全告警，重新解析并原子替换缓存。

## 8. RAG 快照缓存

### 8.1 知识修订号

新建单行知识索引状态，维护单调递增 `revision`。所有知识新增、更新、删除、批量导入和同步入口必须在与知识变更相同的事务中递增修订号。事务回滚时修订号同步回滚。

### 8.2 不可变快照

每个进程按 `revision` 缓存：

- 作用域过滤所需的纯数据元组；
- BM25 分词语料、索引和文档 ID；
- 经模型和维度校验的 `float32` 向量矩阵；
- 文档 ID 与返回数据的映射。

每次检索只读取轻量修订号。修订号不变时复用快照；变化时在锁内单次重建，其他线程继续使用已完成的旧快照，直到新快照原子替换。修订查询或快照重建失败时，当次请求绕过缓存走现有数据库检索路径。

查询向量仍按查询实时生成，不在本期引入语义查询缓存。

## 9. 受控并发与单写者

### 9.1 并发范围

- 新增 `AUDIT_MODEL_CONCURRENCY`，默认为 2，只允许 1–3；
- 仅并发同一 Agent 内互不依赖的审查窗口请求；
- 法务 Agent 完成并生成共享上下文后，才能启动财务 Agent；
- 每个工作单元通过工厂获取独立 LLM 适配器，不跨线程共享请求客户端；
- 截止时间、限流退避和最大重试次数仍使用审查任务的全局预算。

### 9.2 单写者

工作线程只返回业务结果和不含合同正文的调用观测，不直接写入 `audit_window_runs`、`llm_call_logs` 或批次进度。调度线程按窗口原始顺序串行：

1. 保存模型调用观测；
2. 保存完整窗口检查点；
3. 更新进度；
4. 在全部质量决策通过后发布最终风险。

该模式同时用于 SQLite 和 PostgreSQL，不依赖 SQLite 的写并发能力。对 SQLite 仍执行真实并发压测，不以错误分类单元测试代替。

## 10. 配置与回滚

批量 enrichment、批量二次复核和模型并发分别具有可配置开关或参数。解析缓存和 RAG 快照在内部异常时自动回退原路径，不要求运维先修复缓存才能继续审查。

回滚顺序为：

1. 将 `AUDIT_MODEL_CONCURRENCY` 降为 1；
2. 关闭批量 enrichment 与批量二次复核，恢复既有单条路径；
3. 保留解析缓存表和知识修订数据，但在服务层绕过读取；
4. 数据库降级时删除新增缓存与索引状态表，不改写合同、风险或审计历史。

## 11. 安全与观测

- 缓存、日志、调用记录和异常文本不得记录合同正文、原始字节、密钥或本机绝对路径；
- 新增观测包括解析缓存命中/回退、RAG 快照修订与重建、批量大小、部分回退数、并发度和数据库写入失败数；
- 性能日志继续记录 `parse_ms`、Agent 耗时、`grounding_ms`、持久化耗时和总耗时；
- 批量协议版本参与窗口检查点身份，旧协议检查点不得误命中新协议。

## 12. 测试设计

### 12.1 enrichment

- 1–5 条候选只调用一次批量协议；
- 6 条候选拆成 5+1，不跨窗口；
- 候选 ID 重复、未知、缺失和字段无效时只回退相应项；
- 批量响应截断、非 JSON 和超时时恢复单条路径；
- 截止时间到达后不发起新回退调用；
- 窗口正文在一次批量请求中只出现一次。

### 12.2 二次复核

- 1–5 个候选正常返回逐 claim 决定；
- 任一 claim 引用其他 claim 证据时只使该 claim 失败；
- 批量缺项仅重试缺失 claim；
- 验证过的 reject、confirm 和 conflict 语义与现有单条实现一致；
- 最终失败项仍转为 `manual_required`。

### 12.3 解析缓存

- 同一文件和签名第二次审查不调用解析器；
- 文件哈希、代码哈希、OCR 参数或依赖版本变化时必须失效；
- 密钥不匹配、载荷损坏、字段缺失和未知协议版本都安全重建；
- 缓存命中与重新解析的 `DocumentParseResult` 序列化结果完全一致；
- 并发首次填充不产生两条当前缓存。

### 12.4 RAG 快照

- 修订号不变时不重复查询全量切片或解析存储向量；
- 任一知识写入路径成功提交后修订号递增，回滚时不递增；
- 新快照重建期间并发读取不见半成品；
- 缓存与直接数据库路径的检索结果、排序和 trace 一致；
- 缓存故障时现有 BM25/向量降级语义不变。

### 12.5 并发与回归

- 并发度 1 与 2 的结果顺序、风险 ID、证据和质量决策一致；
- 法务未完成时财务不启动；
- SQLite 真实文件数据库并发运行无未处理 `database is locked`，无重复检查点和重复风险发布；
- 限流、网络错误和截止时间下不超出全局重试预算；
- 运行审查、RAG、导入、评测、类型检查和前端回归，最后运行完整质量门禁。

## 13. 性能与质量验收

在相同合同集、相同模型、相同知识库修订和相同审查维度下对比：

| 指标 | 验收要求 |
|---|---|
| 风险发布完整性 | 没有因批量化或并发丢失已验证风险 |
| 证据授权 | 跨 claim 引用数为 0 |
| 人工复核安全边界 | 未验证结论自动发布数为 0 |
| 批量调用数 | 正常路径接近各阶段 `ceil(n/5)` |
| 解析重复调用 | 有效缓存命中时为 0 |
| RAG 全表加载 | 同一修订号每进程最多 1 次 |
| SQLite 写竞争 | 未处理锁错误为 0 |
| 审查耗时 | 记录 P50/P95 对比，不预先伪造改善数字 |

单元和模拟适配器测试通过只证明协议与回退边界正确。批量功能进入生产默认路径前，还必须完成真实模型 A/B，检查风险召回、错误风险、证据支持关系和人工复核比例。

## 14. 实施顺序

1. 先补充批量协议、逐项校验和回退测试；
2. 实现二次复核批量化，优先减少已占较高比例的模型调用；
3. 实现同窗口 enrichment 批量化和单项回退；
4. 新增解析缓存表、加密序列化和签名失效；
5. 新增知识修订状态，覆盖所有知识写入路径后再引入 RAG 快照；
6. 将检查点和调用日志收敛为调度线程单写入；
7. 开启并发度 2，执行 SQLite 压测和结果确定性回归；
8. 运行真实模型 A/B、相关回归和完整质量门禁，再决定批量开关的生产默认值。

并发放在最后，因为批量化本身会显著减少请求数。先批量、后并发能用更小的限流和数据库竞争成本获得主要收益。
