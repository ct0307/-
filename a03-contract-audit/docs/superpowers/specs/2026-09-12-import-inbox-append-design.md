# 合同收件箱连续追加设计

## 背景

当前前端在第一次上传后持续复用同一个 `Idempotency-Key`。用户再次选择文件时，后端把请求视为第一次上传的重试并返回旧批次，前端仍显示成功提示，但第二份合同没有保存。

本次修复将“添加合同”定义为：首次上传创建一个活动收件箱批次，后续上传向该批次追加合同。批次中的合同可同时确认、勾选并提交审查，刷新页面后仍可通过批次 ID 恢复。

## 目标

- 连续选择文件时，新合同追加到当前收件箱，新旧合同同时显示。
- 同一次网络请求重试保持幂等，不重复创建合同或失败记录。
- 不同文件错误复用幂等键时返回冲突，禁止返回旧批次并提示成功。
- 追加失败不清空当前列表、不丢失有效勾选状态。
- 单个收件箱批次累计最多包含 200 份文件。
- 保持现有确认、重试、删除、轮询、恢复和提交审查流程兼容。

## 不在范围内

- 不改变合同解析、分类或审查算法。
- 不合并不同用户或不同部门的收件箱。
- 不按文件内容去重；内容相同但文件名不同仍视为不同合同。
- 不调整页面视觉布局。

## 方案

采用显式追加接口：

- `POST /api/v1/imports`：创建新的收件箱批次。
- `POST /api/v1/imports/{batch_id}/items`：向已有批次追加文件。
- `GET /api/v1/imports/{batch_id}`：返回完整批次，继续作为页面恢复与轮询数据源。

不采用“前端聚合多个批次”，因为确认、删除、轮询和 URL 恢复都依赖批次 ID；维护多个活动批次会扩大状态复杂度。也不让创建接口通过可选参数兼任追加接口，避免接口语义含混。

## 后端设计

### 请求幂等

创建批次和每一次追加都是独立用户动作，每个动作使用新的幂等键。一次动作因超时等原因重试时复用原键。

后端为请求计算指纹，指纹包含目标部门，以及按顺序排列的文件名、大小和内容 SHA-256：

- 相同作用域、相同幂等键、相同指纹：返回当前完整批次，不重复写入。
- 相同作用域、相同幂等键、不同指纹：返回 `409 IDEMPOTENCY_CONFLICT`。

初始创建请求的指纹保存在 `import_batches.request_fingerprint`。追加请求使用独立的 `import_append_requests` 记录，字段至少包括 `batch_id`、`idempotency_key`、`request_fingerprint` 和创建时间，并对 `(batch_id, idempotency_key)` 建立唯一约束。

### 追加事务

追加接口按以下顺序执行：

1. 校验用户拥有该批次及目标部门权限。
2. 读取文件并计算请求指纹。
3. 检查幂等记录；冲突时终止，相同请求时返回当前批次。
4. 锁定批次并检查 `batch.total + files.length <= 200`。
5. 使用现有上传校验与加密存储逻辑创建合同和导入项。
6. 刷新批次统计、写审计日志和幂等记录，在同一事务中提交。
7. 提交后派发解析任务并返回完整批次。

数据库唯一约束负责阻止并发重复请求。事务失败时回滚数据库并清理本次已写入的文件。

### 文件边界

- 单次请求仍必须包含 1 至 200 个文件。
- 单批次累计最多 200 个导入项，超限返回 `409 IMPORT_BATCH_LIMIT_EXCEEDED`。
- 不支持格式、空文件、超大文件继续生成独立失败记录，不影响同批其他文件。
- 同一批次内同名文件生成 `DUPLICATE_FILENAME` 失败记录；不覆盖已保存文件。
- 同内容、不同文件名不做业务去重。

### 兼容与迁移

- 新字段允许旧批次的请求指纹为空；只对新请求执行严格指纹判断。
- 使用项目现有数据库初始化迁移机制补齐 SQLite 开发库字段和新表。
- PostgreSQL 目标环境依赖唯一约束和行锁保证并发一致性。

## 前端设计

`import-inbox` store 根据当前状态选择请求：

- 没有活动批次时调用创建接口。
- 已有活动批次时调用追加接口。

每次新的文件选择创建一个新的幂等键。该键保留到请求成功；请求失败时保留，供用户对同一选择执行重试。成功后立即清空，以便下一次文件选择生成新键。

接口返回完整批次后替换 `batch`。替换前已有的 `selectedIds` 不清空，仅过滤掉已经不再处于 `ready` 状态的项目。首次创建批次时清空旧选择。

成功提示使用本次选择的文件数量，并校验返回批次的项目增量；幂等重放时允许增量为零但不得误报为新增。冲突、超限和其他错误显示后端结构化错误消息，同时保留旧批次列表。

轮询始终针对当前批次。追加后如存在 `queued`、`parsing` 或 `auditing` 项，重新启动该批次轮询；已有轮询先停止，避免并行定时器覆盖新状态。

## 附带缺陷修复

| 优先级 | 缺陷 | 处理 |
|---|---|---|
| P1 | 幂等键跨用户动作永久复用 | 每次新选择生成新键，成功后清空 |
| P1 | 后端相同键、不同请求静默返回旧批次 | 保存请求指纹并返回 409 冲突 |
| P1 | 前端创建新批次会覆盖旧收件箱 | 已有批次改走追加接口 |
| P1 | 追加失败可能覆盖可见列表 | 仅在请求成功后替换 store 状态 |
| P2 | 成功提示只读取批次总数，不能证明本次新增 | 使用本次上传结果和增量生成提示 |
| P2 | 追加后旧轮询可能覆盖新数据 | 停止旧轮询后以同一批次重新启动 |
| P2 | 累计数量没有服务端边界 | 在事务内校验批次累计 200 份上限 |
| P2 | 跨追加请求的同名文件未检测 | 对当前批次全部文件名执行检测 |

## 测试设计

### 后端

- 首次创建后追加文件，返回同一个批次且项目总数增加。
- 相同追加键和相同文件重试，不创建重复合同或记录。
- 相同追加键但文件不同，返回 `409 IDEMPOTENCY_CONFLICT`。
- 创建接口相同键但不同文件同样返回冲突。
- 批次累计超过 200 份时拒绝追加，原批次不变。
- 跨追加请求同名文件生成失败记录。
- 无权限用户不能追加到他人批次。
- 存储或数据库失败时不留下半成品记录。

### 前端 store

- 第二次选择文件调用追加接口而不是再次创建批次。
- 每次独立选择使用不同幂等键。
- 失败重试复用该次请求的键。
- 追加成功保留仍有效的勾选项并启动轮询。
- 追加失败保留原批次和选择状态。

### 页面交互

- 上传第一份合同后继续添加第二份，两行同时可见且总数为 2。
- 刷新带 `import` 查询参数的页面后恢复两份合同。
- 追加无效文件时显示失败行，原合同仍存在。
- 后端冲突或超限时显示错误提示，列表不闪烁、不清空。
- 桌面和移动视口无新增溢出或遮挡，控制台无相关错误。

## 验收标准

用户在同一页面连续添加合同后，所有合同都显示在同一个待审收件箱中，可共同确认、勾选和提交审查；网络重试不会产生重复数据，不同请求不会因幂等键冲突产生假成功。
