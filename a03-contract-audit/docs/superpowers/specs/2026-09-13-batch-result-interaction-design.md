# 批次审查结果交互设计

## 背景与问题

批次审查完成后，当前页面只显示批次状态和文件列表。每份文件右侧只有无文字的查看图标，点击后进入审查历史页并填入合同编号，但用户仍需再次点击历史记录才能看到风险详情。该流程缺少明确的下一步，也没有做到“一次操作进入结果”。

## 目标

- 保留批次汇总，让用户先看到全部合同的完成或失败状态。
- 为每份已完成合同提供清晰的“查看审查结果”操作。
- 点击一次后直接展示对应合同的风险详情，并可继续人工复核。
- 失败项继续保留错误原因和重试入口，不允许进入不存在的结果。

## 方案选择

采用“保留汇总 + 单份结果直达”的方案。

未采用自动跳转：一个批次可能包含多份合同，自动打开第一份会打断用户查看整体结果，并且无法表达“应该先看哪一份”。未采用继续跳转到历史列表：历史列表会增加一次无必要的查找和点击。

## 交互设计

1. 批次状态为 `done` 或 `partial_failed` 时，继续显示进度、处理数量和文件列表。
2. 每个 `done` 文件项右侧显示带文字的“查看审查结果”按钮，替代仅有图标的圆形按钮。
3. 点击按钮后，当前页面加载该合同的审查会话，并在同页结果区域展示合同摘要、风险列表、全文批注入口和人工复核操作。
4. 加载期间按钮显示忙碌状态并禁止重复点击。
5. 加载失败时停留在批次汇总，显示明确错误提示，用户可以再次尝试。
6. `failed` 文件项不显示查看按钮，继续显示失败原因；批次存在失败项时保留“重试失败项”。

## 数据流与边界

- 输入：批次项中的 `contract_id`。
- 复用：`audit-session` store 现有的合同审查结果恢复能力，不新增结果页、不复制风险详情组件。
- 页面状态：批次汇总和当前单份审查结果可以同时存在，用户完成复核后仍能返回批次列表切换其他合同。
- 路由：不再通过 `/history?contract=...` 承担本流程的结果入口；历史页仍保留独立的历史查询职责。

## 验收标准

- 正常状态：完成项展示可识别的文字按钮，点击一次即可看到正确合同的风险详情。
- 多文件状态：可在不同完成项之间切换，内容与所选合同一致。
- 空结果状态：合同没有风险时展示现有空状态，不显示错误。
- 错误状态：结果加载失败时给出提示，批次汇总不丢失。
- 部分失败状态：完成项可查看，失败项可重试但不可查看。
- 响应式：桌面和移动端按钮文字不溢出，文件名和操作区不重叠。
- 回归：审查历史页、单份审查恢复、失败项重试保持可用。

## 测试范围

- 组件或端到端测试覆盖“完成项点击后直接加载结果”。
- 覆盖加载失败、无风险结果和部分失败批次。
- 运行前端相关测试、类型检查和构建，并进行桌面与移动端浏览器实测。
