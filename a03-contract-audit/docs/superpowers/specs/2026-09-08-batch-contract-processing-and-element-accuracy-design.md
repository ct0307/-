# 批量合同处理与要素准确率提升设计

日期：2026-09-08  
状态：待用户复核

## 1. 背景与结论

赛题要求同时满足三类硬指标：

- 合同关键要素提取准确率不低于 90%；
- 单批一次性上传并最终处理至少 50 份合同；
- 在相同模型、数据集和输出要求下，证明 OpenClaw 一体机相对传统 GPU 方案的性能或能效优势。

这三个指标不能通过“把 50 份合同拼进一次大模型请求”同时解决。批量规模是业务任务调度问题，4096 token 是单次推理的上下文预算，准确率则取决于解析质量、字段覆盖、切片召回、结构化抽取、校验和金标准评测。

本设计保留现有持久化批次、Celery 单合同任务、幂等、租约、失败隔离和重试能力，重点改造以下缺口：

1. 批量审查当前调用纯正则 `extract_elements()`，未复用 LLM 增强抽取。
2. 已实现字段少于赛题要求，且缺少字段级证据、位置和置信度。
3. 审查阶段直接截取合同前 8000 个字符，可能遗漏中后部关键条款。
4. `cross_checks` 只存在于同步响应或 Celery 返回值中，异步完成后不能可靠恢复。
5. 批量上传服务端先把整批内容读入内存，在接近 500MB 上限时存在内存峰值风险。
6. 当前代码能力尚未经过真实 50+2 合同集、冻结金标准或目标硬件验证，不能写成已经达标。

## 2. 目标与非目标

### 2.1 目标

- 单批稳定接收并最终处理 50 份以上合同，单文件失败不扩散到整批。
- 保持批次刷新恢复、幂等提交、失败项重试和启动补投能力。
- 对长合同按结构和 token 预算切片，不因固定字符截断漏掉尾部条款。
- 覆盖赛题要求的关键要素，并为每个非空结果保留原文证据、位置和置信度。
- 使用冻结金标准计算字段宏平均准确率，正式目标不低于 90%，内部发布门槛设为 93%，为样本波动留出余量。
- 保存风险、要素、跨 Agent 交叉验证和运行指标，使异步结果可恢复、可解释、可评测。
- 在公平约束下执行 OpenClaw/GPU 对照，结论只来自真实运行数据。

### 2.2 非目标

- 不把多个合同合并为一个 LLM prompt。
- 不通过无限扩大上下文替代合同结构解析。
- 不在缺少真实合同、金标准或目标设备时伪造准确率、吞吐或能耗结论。
- 不在本轮引入新的外部 npm 包或 Python 依赖；优先复用现有解析器、Pydantic、SQLAlchemy、Celery 和模型 Adapter。
- 不重做现有前端视觉体系，只补齐批次结果查看和必要状态。

## 3. 方案选择

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 多合同单 prompt | 表面调用次数少 | 上下文必然溢出、输出互相污染、失败影响整批、难重试和溯源 | 拒绝 |
| 单合同整篇 prompt | 实现简单，沿用现有任务模型 | 长合同仍会截断；4096 token 下输入与输出互相挤占 | 仅作为短合同降级路径 |
| 持久化批次 + 单合同流水线 + 条款切片 + 聚合校验 | 可恢复、可限流、长合同覆盖完整、单项可重试、准确率可评测 | 实现与测试成本较高 | 采用 |

## 4. 总体架构

```text
前端一次选择 50+ 文件
          |
          v
POST /batches -> 校验元数据、流式加密保存、创建批次与文件项
          |
          +--> 202 + batch_id（浏览器无需保持长连接）
          |
          v
Celery：每份合同一个可恢复任务，按目标设备设置受控并发
          |
          v
解析/OCR -> 结构化片段 -> 要素抽取与聚合 -> 一致性校验
          |                                      |
          |                                      +--> 要素值/证据/位置/置信度入库
          v
法务 Agent / 财务 Agent 分片审查 -> 风险聚合 -> 交叉验证
          |                                      |
          +--> 风险入库                          +--> cross_checks 入库
          |
          v
批次与文件项进入终态；前端轮询摘要并按合同懒加载详情
```

业务层只负责将任务拆到“单份合同”。vLLM 或 OpenClaw 推理服务负责在多个独立请求之间做 continuous batching。并发数、`max_num_seqs`、批量 token 上限和显存利用率必须通过目标设备压测确定，不能由前端上传数量直接决定。

## 5. 数据模型

### 5.1 合同要素

新增独立 `contract_elements` 表，不继续把正式结果只保存在 `contracts.elements_json` 中。每行表示一个合同字段或一个多值字段项：

| 字段 | 含义 |
|---|---|
| `contract_id` | 所属合同 |
| `field_name` | 稳定英文键 |
| `value_text` | 原始业务值 |
| `normalized_value` | 规范化值，JSON 文本 |
| `evidence_text` | 对应合同原文 |
| `page_number` / `section_path` | 页码与条款位置 |
| `confidence` | 0 至 100 |
| `source` | `rule`、`table`、`llm` 或 `merged` |
| `ordinal` | 付款节点等多值字段顺序 |
| `review_status` | `auto`、`pending`、`confirmed`、`corrected` |

唯一约束使用 `(contract_id, field_name, ordinal)`。重跑单份合同时，在同一事务内替换该合同的机器抽取结果；人工确认或修正记录保留审计轨迹，不被静默覆盖。

第一阶段字段覆盖：合同编号、合同名称、合同类型、甲方、乙方、统一社会信用代码、合同标的、金额、币种、税率、签订日期、生效日期、履行期限、付款节点、发票要求、交付地点、验收条件、违约责任、争议解决、联系人。

### 5.2 文档片段

新增 `contract_chunks` 表保存可定位的结构化片段元数据和解析文本：

- `contract_id`、`chunk_index`、`section_path`；
- 起止页码、片段文本、文本哈希；
- 估算 token 数和解析来源；
- 是否包含表格、OCR 及对应置信度。

片段文本属于敏感合同数据，沿用本地私有化与访问隔离要求。若数据库加密能力不足，实施时可只保存加密对象路径和定位元数据，正文通过受控存储读取；不能为方便调试把明文输出到日志。

### 5.3 交叉验证

新增 `audit_cross_checks` 表，保存 `from_agent`、`to_agent`、触发条件、动作、裁定、说明和类别，并关联合同及本轮审查运行。异步状态查询和协同页面必须从数据库恢复真实结果，不依赖 Celery result backend。

## 6. 单合同处理流水线

### 6.1 解析与质量门禁

1. 原生 PDF/DOCX 优先提取正文、表格、段落层级和页码映射。
2. 扫描页或低文本覆盖页进入 OCR，并保存页级置信度。
3. 密码保护、损坏、空文件和解析文本过短使用稳定错误码区分。
4. 解析质量低于门槛时进入人工复核，不得把“无法解析”解释成“无风险”。

### 6.2 结构切片

切片优先级为：标题/条款边界、段落、表格、句子。禁止按固定字符数直接截断。

- 使用目标模型 tokenizer 计算真实 token，不用字符数近似最终边界。
- 4096 token 模型需要为系统提示、字段 Schema、证据和输出预留预算；首版输入片段目标为约 1800 至 2200 token，最终值由请求日志和压测冻结。
- 相邻普通片段保留约 10% 重叠；表格、金额、付款、验收和争议解决条款不得从中间拆开。
- 每个片段携带合同 ID、片段 ID 和位置元数据，模型看到的是单合同单片段。
- 短合同在完整请求不超过预算时允许走单片段快速路径。

### 6.3 要素抽取

采用四阶段混合抽取：

1. **候选生成**：现有正则、表格解析和关键词定位产生高精度候选。
2. **片段级 LLM 抽取**：只在与字段相关的片段上使用严格 JSON Schema 输出，缺失字段必须为 `null`，不得猜测。
3. **确定性规范化与校验**：统一公司名称空白、日期、金额、币种、税率；校验大小写金额、付款比例和日期顺序。
4. **合同级聚合**：按证据位置、来源优先级、字段一致性和置信度合并候选；冲突候选进入人工确认队列。

要素抽取与风险审查分开持久化。风险 Agent 读取已经聚合的要素和相关合同片段，不重复承担完整字段抽取职责。

### 6.4 风险审查

法务和财务 Agent 继续保持独立请求及职责边界。对每个审查维度检索相关合同片段与可靠知识来源，片段级发现经过合同级去重、证据校验和等级聚合后入库。

模型调用必须显式设置输出 token 上限，并记录 prompt token、completion token、`finish_reason`、延迟、模型与提示词版本。输出被截断、JSON 无效或证据不在原文中时，本片段失败并按有限次数重试；超过次数后标记局部失败和人工复核，不能伪造降级结论。

## 7. 批次调度与资源控制

### 7.1 接入

- 单批业务上限维持 200，正式验收在同一批次提交 50 份有效合同和 2 份异常合同，扩展压力测试使用 100 份有效合同。
- 服务端逐文件读取、校验、计算哈希并加密保存，避免把最大 500MB 批次完整驻留内存。
- 只有批次和全部有效文件项成功持久化后才开始派发；派发失败保留可补投的 `queued` 状态。
- `Idempotency-Key` 与文件哈希共同约束重复提交，重复请求返回原批次，不重复创建风险。

### 7.2 调度

- 一份合同对应一个 Celery 主任务；合同内部片段按顺序或受限扇出执行，防止一个长合同占满队列。
- 交互式单合同队列优先于后台批量队列，但两者共享全局推理并发上限。
- 初始并发不写死为固定数字。目标设备从并发 1 开始阶梯压测，选择不发生 OOM、成功率满足要求且吞吐最高的稳定配置。
- 对超时、服务不可用、输出截断和结构校验失败分别统计；只对可恢复错误进行指数退避重试。
- 保留现有租约、启动补投和数据库去重，确保 Worker 中断后可恢复且不会重复落库。

## 8. API 与前端行为

保留现有 API 主形态：

- `POST /batches` 返回 `202` 和 `batch_id`；
- `GET /batches/{id}` 返回批次摘要及文件项状态；
- `POST /batches/{id}/retry` 只重试失败项；
- 合同详情接口按需返回要素、风险和交叉验证结果。

前端继续使用轮询即可满足当前比赛范围，暂不引入 WebSocket/SSE。批次完成项需要可点击进入合同结果，展示：

- 文件状态、解析来源与 OCR 质量；
- 关键要素、证据位置、置信度及待确认项；
- 风险列表与跨 Agent 交叉验证；
- 失败原因和单项重试入口。

批次接口不一次返回 50 份完整审查结果，避免大响应和无效重复传输。

## 9. 准确率评测设计

### 9.1 金标准

- 合同必须脱敏并覆盖 PDF、DOCX、扫描件和主要合同类型。
- 两名审核人独立标注，分歧由第三人仲裁；冻结后计算数据集 SHA-256。
- 开发集用于规则和提示词调整，冻结测试集只用于最终评测。
- 金标准使用与生产字段一致的 Schema，并保存证据位置。

### 9.2 指标

主指标沿用项目既定的字段宏平均口径，总体发布门槛为 93%，赛题最低门槛为 90%。报告同时输出：

- 总体字段宏平均准确率；
- 各字段 Precision、Recall、F1 或准确率；
- 甲乙方、金额、期限、付款节点的召回率和字段得分；
- 按文档格式、扫描/原生、合同类型分组的结果；
- 漏报、误报、冲突候选和低置信度案例清单。

缺失预测必须计为错误，不能从分母移除。人工修正不能回写覆盖本次机器预测，否则评测失真。

## 10. 50+2 与扩展容量验收

### 10.1 正式硬指标批次

- 同一批次提交 50 份有效合同和 2 份异常合同；50 份有效合同总页数不少于 500 页；
- PDF 与 DOCX 各不少于 20 份，扫描件不少于 10 份；
- 单份 5 至 30 页；
- 2 份异常合同分别覆盖文件损坏和密码保护，并在批次内进入明确失败终态；
- 冻结硬件上 30 分钟内完成；
- 有效文件成功率不低于 98%；
- 异常文件被正确隔离；
- 刷新后进度可恢复，重复提交不产生无关联记录。

### 10.2 扩展验证

正式批次通过后再执行 100 份容量测试，记录吞吐、P95、数据库连接、队列长度、CPU/GPU/内存峰值和失败率。200 份仅作为上限压力测试，不应在正式演示中牺牲稳定性和准确率。

## 11. OpenClaw/GPU 公平对照

两端必须冻结相同的模型哈希、量化方式、提示词版本、输出 Schema、上下文预算、数据集、并发和超时。每端预热 3 轮、正式运行 5 轮，记录：

- 单份总耗时 P50/P95；
- 批量合同/分钟与页/分钟；
- 成功率、输出截断率和 JSON 校验失败率；
- 平均功率、峰值功率和每份合同能耗；
- 均值、标准差与 95% 置信区间。

没有真实功率时序时能耗固定标记为 `not_measured`。任何一侧缺少同口径数据时，不生成“显著优于”的结论。

## 12. 错误处理与安全

- 错误码区分上传校验、加密、解析、OCR、模型超时、输出截断、JSON 校验、持久化和未知错误。
- 单片段失败不能直接让整批失败；单合同出现部分失败时进入人工复核并保留已完成证据。
- 日志只记录文件 ID、哈希、状态、token 和耗时，不记录合同正文、密钥、认证头或完整模型响应。
- 合同详情与批次查询继续执行部门数据隔离。
- 数据库迁移必须支持升级与回滚；生产验收使用 PostgreSQL，SQLite 仅作为开发环境。

## 15. 验收结论边界

代码和自动化测试完成后，只能表述为“机制已实现并通过自动化验证”。只有真实冻结合同集、目标数据库和目标设备产生完整原始记录后，才能分别表述“要素准确率达到 90%”“稳定处理 50 份以上”和“OpenClaw 显著优于传统 GPU”。
