# 合同导入与解析可靠性增强设计

日期：2026-09-14
状态：待实施

## 1. 背景与结论

`测试合同` 冻结集包含 50 份有效合同和 2 份无效输入。现状测试表明：50 份有效文件的静态结构均正常，但实际解析只有 41 份成功，9 份纯扫描 PDF 全部因运行环境缺少 RapidOCR 而失败；非空损坏 PDF 会先创建合同草稿再异步失败；合同类型识别存在高置信度误判；六要素构造真值技术预评测 overall F1 仅为 0.0333。

本次采用“原系统生产化增强”方案，不重写框架。保留 Vue 3、FastAPI、SQLAlchemy、Celery、`Contract`、`ImportBatch`、`ImportBatchItem`、`extract_document()` 以及现有上传、解析、审查主流程，在现有模块边界内补齐可靠性、错误语义、质量门和回归测试。

实现策略是“生产化骨架、渐进质量目标”：当前先保证每份文件有明确、可恢复、可测试的处理结果；OCR、分类和六要素输出必须诚实表达质量，不用虚假的高置信度制造演示效果。PostgreSQL 高可用、常驻 OCR 服务、GPU 优化和极限容量调优留到后续生产化阶段。

## 2. 方案比较

| 方案 | 结论 | 主要取舍 |
|---|---|---|
| 重写独立导入与解析框架 | 不采用 | 理论边界更整齐，但会复制现有批次、状态、权限和审查逻辑，风险和工期不可控 |
| 只修复 9 份扫描件 | 不采用 | 能改善比赛演示，但无法解决损坏文件入库、高置信度误判、六要素不可用和错误不可诊断 |
| 在现有架构上做纵向可靠性增强 | 采用 | 改动集中，可分阶段验证，同时保留后续替换 OCR 或抽取引擎的接口 |

## 3. 目标、优先级与非目标

### 3.1 目标

| 优先级 | 目标 | 完成定义 |
|---|---|---|
| P1 | 可复现解析环境 | 新建环境可按锁定清单安装；启动预检能识别 OCR 缺失；中文路径下 API、Celery 和 OCR 子进程可启动 |
| P1 | 有效合同结果闭环 | 50 份有效合同逐项得到 `parsed` 或 `review_required`，9 份扫描件不再因 `OCR_UNAVAILABLE` 失败 |
| P1 | 分类防误放行 | 未经校准的结果不得以高置信度自动就绪；冻结集中高置信度错误自动放行数为 0 |
| P1 | 六要素达到可用基线 | 每个非空结果带原文证据；构造真值宏 F1 不低于 0.80，且六个字段均不能出现 F1 为 0 |
| P2 | 非法输入同步隔离 | 空、伪装、损坏、加密、超限文件在创建合同草稿前得到稳定错误码 |
| P2 | 错误可诊断、可操作 | API 返回稳定脱敏错误；日志保留阶段、任务 ID 和根因类别；前端提供对应处理动作 |
| P2 | 回归可持续 | 50+2 冻结集和非空损坏样本纳入统一质量门禁，批次单项失败不阻塞其他文件 |

### 3.2 非目标

- 不替换 Vue、FastAPI、SQLAlchemy、Celery 或现有数据库模型体系。
- 不在本次完成 SQLite 到 PostgreSQL 的历史迁移、高可用部署或跨区域容灾。
- 不新增常驻 OCR 微服务，不承诺 GPU 推理、能耗或 50 并发性能指标。
- 不自动拆分包含多份独立合同的合订本。
- 不把构造真值 F1 当作正式法律准确率。正式 F1 不低于 0.90 的结论必须基于双人法务复核金标准。
- 不让 LLM 无证据补全缺失字段，也不把低置信度识别包装成解析成功。

## 4. 总体架构与兼容边界

导入链路保持单向、逐文件隔离：

```text
客户端轻量检查
  -> 后端同步内容预检
      -> 不合法：返回逐文件错误，不创建 Contract
      -> 合法：加密存储并创建/复用 Contract、ImportBatchItem
          -> extract_document
              -> 原生解析
              -> PyMuPDF 兼容回退
              -> 扫描页 OCR 子进程
          -> 解析质量门
              -> 技术失败：failed + 稳定错误码
              -> 低质量：review_required + 证据和原因
              -> 质量合格：parsed
          -> 类型候选与置信度校准
          -> 六要素候选、规范化、校验和证据锚点
          -> ready 或待人工确认
```

兼容原则：

- `extract_document(file_path) -> DocumentParseResult` 继续作为核心解析接口，`extract_text()` 继续作为兼容包装。
- 现有成功 API 字段保持兼容；新增质量、错误和证据字段采用可选字段或版本化内部模型。
- `ImportBatch` 负责收件，`AuditBatch` 负责审查，不合并两个生命周期。
- 单项失败只更新对应 `ImportBatchItem`；批次汇总从逐项状态计算，不因一个文件回滚整批。
- 网络重试复用幂等键和已有合同，不重复创建 `Contract`。

## 5. 可复现运行环境与启动预检

### 5.1 环境重建

当前 `.venv` 的创建路径含乱码，不能作为可复现环境继续修补。实施时按项目固定 Python 版本重新创建本地虚拟环境，再按已锁定版本安装依赖。安装前必须单独取得用户确认，并对 RapidOCR、ONNX Runtime 及其传递依赖执行来源、许可证、已知漏洞和包哈希审计；不得把开发机已有 site-packages 拼接进生产路径。

环境验收至少覆盖：

- Python 解释器和 `pip check` 正常。
- `rapidocr==3.9.2`、`onnxruntime==1.28.0` 可以导入并加载模型。
- 位于中文目录时，FastAPI、Celery worker 和 OCR 子进程均能启动。
- 依赖清单和锁定结果可由干净环境复现，不提交 `.venv`、模型缓存或本机路径。

### 5.2 OCR 就绪状态

复用现有健康检查体系，在严格预检中增加 `ocr` 检查项：

- `/health/live` 仍只表示进程存活。
- `/health/ready` 不因 OCR 不可用而摘除仍可处理文本合同的实例，但返回 `ocr.ready=false` 和稳定错误码。
- `/health/preflight` 在部署声明支持扫描件时要求 OCR 引擎、模型和子进程冒烟检查全部通过，否则返回 503。

启动预检不得处理真实合同，只使用内置的最小无敏感内容测试图。日志只记录版本、加载耗时和错误类别。

## 6. 后端同步内容预检

预检位于加密存储和 `Contract` 创建之前。客户端校验用于即时反馈，服务端校验才是可信边界。

### 6.1 检查规则

| 类型 | 检查 | 失败错误码 |
|---|---|---|
| 通用 | 文件名、扩展名、非空、大小上限、扩展名与内容签名一致 | `EMPTY_FILE`、`FILE_TOO_LARGE`、`UNSUPPORTED_FILE_TYPE`、`FILE_TYPE_MISMATCH` |
| PDF | `%PDF-` 签名、解析器可打开、交叉引用/页面树可读取、至少一页、未加密或已明确拒绝 | `PDF_CORRUPT`、`PDF_EMPTY`、`PDF_ENCRYPTED` |
| DOCX | ZIP 容器可打开、无危险路径、`[Content_Types].xml` 与 `word/document.xml` 存在且可读取 | `DOCX_CORRUPT`、`DOCX_STRUCTURE_INVALID` |
| TXT | 编码可判定、解码后存在有效字符 | `TEXT_ENCODING_ERROR`、`TEXT_EMPTY` |

容器校验必须使用格式解析 API，不使用字符串搜索猜测结构。预检只验证“可安全进入解析队列”，不在同步请求中执行完整 OCR 或六要素抽取。

### 6.2 原子性与数据后果

- 预检失败时不写原文件、不创建 `Contract`，只在导入项中保留文件名、错误码和安全说明；若现有导入模型要求先有批次，可创建批次和失败项，但 `contract_id` 必须为空。
- 存储或数据库写入失败时回滚该文件的元数据和存储对象，不影响同批其他文件。
- 预检成功后的网络重试使用客户端幂等键查询原结果，禁止重复落库。

## 7. 文档解析与 OCR 质量门

### 7.1 解析策略

解析顺序保持现有能力并明确质量判定：

1. DOCX/TXT 使用原生解析器；PDF 首先提取原生文本。
2. PDF 字体映射不可靠时使用既有 PyMuPDF 候选比较策略，只有候选页数完整且质量更好时替换。
3. 无文本页或扫描页通过现有独立 OCR 子进程识别，继续执行页数、像素、时间和输出协议限制。
4. 原生页与 OCR 页合并为 `DocumentParseResult`，保留 `native`、`ocr` 或 `mixed` 来源、页级文本和 OCR 质量信息。
5. OCR 低置信度或文本完整性不足不是技术失败，返回 `review_required`；引擎不可用、超时、资源超限或协议错误才进入技术失败状态。

### 7.2 稳定错误模型

内部异常统一映射，不再由通用 `except Exception` 覆盖根因：

| 错误码 | 含义 | 默认动作 |
|---|---|---|
| `OCR_UNAVAILABLE` | 引擎、模型或运行库不可用 | 管理员修复环境后重新解析 |
| `OCR_TIMEOUT` | 超出单文件强制时限 | 允许有限次自动重试，之后人工重试 |
| `OCR_LIMIT_EXCEEDED` | 页数、像素或资源超过配置 | 提示拆分或压缩文件 |
| `OCR_PROTOCOL_ERROR` | 子进程输出不完整或非法 | 记录任务诊断并允许重试 |
| `PDF_TEXT_EMPTY` | PDF 可打开但未产生可用文本 | 尝试 OCR；OCR 后仍为空则人工处理 |
| `PARSE_INTERNAL_ERROR` | 未分类的内部异常 | 保留关联 ID，禁止回传堆栈 |

异步任务按“可重试、不可重试、需人工处理”分类。自动重试必须有次数上限和退避，不得重复建合同。API 返回 `{ code, detail, action, correlation_id }`；`detail` 和 `action` 为脱敏中文说明。日志保留阶段、异常类型、合同/任务关联 ID、耗时和重试次数，不记录合同正文、结构化字段值、密钥、本机绝对路径或第三方响应全文。

## 8. 合同类型识别

### 8.1 识别边界

分类器输出 `suggested_type`、`confidence`、候选列表和证据摘要，不直接替代人工责任。配置中的 14 种合同类型必须全部可成为候选；无法可靠区分的类型返回待确认，不能静默归到五个既有规则族。

首期使用可解释的分区加权分类：

- 文件名、文档标题、首部交易名称和定义条款为高权重。
- 主体、标的、服务范围、交付物等主交易特征为中权重。
- 保密、违约、争议解决等通用条款为低权重，不能单独把普通合同判为保密协议。
- 补充协议、订单和附件先识别与主合同的关联信号；无上下文时进入待确认。

### 8.2 置信度校准与放行

沿用现有 85%/60% 交互阈值，但阈值仅在验证集校准后生效。高置信度区间的精确率低于 95% 时，必须提高阈值或关闭该类型的自动就绪，优先降低覆盖率而不是容忍错误放行。

在完成校准前，所有机器建议最多进入“待确认”。人工修改记录原建议、候选、置信度、证据、最终类型、操作者和时间，用于离线评估，不在本期自动训练。

## 9. 六要素抽取与证据

### 9.1 输出模型

保持现有六要素 API 名称，内部将每个字段升级为结构化结果：

```text
value            规范化值
raw_text         原文片段
page             一基页码；DOCX/TXT 可为空
start/end        在规范化全文中的字符区间
confidence       经过字段校验的置信度
source           rule 或 llm
validation       valid、ambiguous 或 invalid
```

兼容响应继续提供原有字符串值；新证据对象作为附加字段返回。没有可定位证据的字段必须为空或标记 `ambiguous`，不能输出高置信度值。

### 9.2 抽取流水线

1. 按标题、定义、签约方区、价款、期限和付款条款生成多个候选。
2. 对主体名称、币种金额、日期区间和付款条件分别规范化。
3. 使用字段级校验器排除明显冲突，例如把违约金当合同总价、把法定代表人当乙方、把质保期当合同期限。
4. 候选唯一且校验通过时输出；多个高分候选冲突时标记 `ambiguous` 并进入人工复核。
5. 规则不足时可调用现有 LLM 适配层进行结构化候选生成，但必须通过同一证据定位和字段校验；LLM 不可用时规则路径仍能运行。

付款节点允许返回有序列表，每项包含触发条件、比例或金额、时间条件及证据。合同标的优先返回可审查的主交易摘要，不直接复制整段服务条款。

## 10. 状态、前端反馈与恢复

沿用智能合同收件箱的状态语义：

- `failed`：技术上未完成，显示具体错误、重试或文件处理建议。
- `review_required`：已完成机器处理，但 OCR、分类或字段质量需要人工确认；它不是解析失败。
- `ready`：解析质量合格，类型已确认，审查必需信息完整。

前端逐文件展示阶段、错误说明和可用动作，不只依赖 toast。OCR 不可用时提示“扫描件识别服务未就绪，请联系管理员后重新解析”；文件损坏时提示重新获取原件；低置信度时直接定位待确认字段。用户重新解析时复用原 `contract_id`，页面刷新后从服务端恢复状态。

正常、空、错误、处理中和移动端状态必须分别验证。状态不能只靠颜色表达，长文件名和错误说明不得挤压主要操作。

## 11. 测试与验收

### 11.1 自动化分层

| 层级 | 覆盖范围 |
|---|---|
| 单元测试 | PDF/DOCX/TXT 预检、异常映射、重试分类、OCR 质量门、14 类候选、字段规范化和证据区间 |
| API/服务测试 | 预检失败不建合同、幂等重试、单项隔离、错误契约、`review_required`、健康检查 |
| 冻结集评测 | 50+2 逐文件解析状态、OCR 失败分布、分类放行、六要素字段级指标 |
| 前端测试 | 逐文件状态、稳定错误码映射、重试、人工确认、刷新恢复、空和错误状态 |
| 浏览器验收 | 1440x900 与 390x844 下的正常、空、加载、错误、长文本和混合批次 |

冻结集测试只把合同作为不可信数据，不执行文档内任何指令。测试产物写入 `outputs/`，不提交合同原件、抽取正文、数据库或日志。

### 11.2 当前阶段通过标准

- 50 份有效合同全部得到 `parsed` 或 `review_required`，不存在无法解释的丢失或永久 `queued`。
- 9 份扫描 PDF 不再出现 `OCR_UNAVAILABLE`；OCR 低质量可以进入 `review_required`。
- 两个既有无效输入以及新增的非空损坏 PDF、损坏 DOCX 在同步预检阶段被拒绝，且不创建合同。
- 同批单项失败不阻塞其他项；重试不重复创建合同或导入项。
- 冻结集中高置信度错误自动放行数为 0；校准前机器分类全部要求确认。
- 六要素构造真值宏 F1 不低于 0.80，六个字段均不能为 0；每个非空预测都有可验证证据位置。
- 相关后端测试、前端测试、类型检查、生产构建和 `scripts/quality_gate.ps1` 全部通过。
- 浏览器实测覆盖正常、空、错误和响应式状态，控制台无新增错误。

### 11.3 指标边界

冻结集构造真值仅用于工程回归和比较，不能对外宣称法律准确率。正式“六要素 F1 不低于 0.90”、OCR 准确率、吞吐、PostgreSQL、GPU 和能耗指标必须另行建立合格数据或目标环境并实测。未实测的指标在文档、界面和比赛材料中统一标记为“待验收”。

## 12. 实施顺序与回滚

实施计划按可独立验证的纵向切片组织：

1. 修复可复现环境并增加 OCR 预检，不改业务状态。
2. 增加同步内容预检和稳定错误映射，锁定“失败不建合同”。
3. 打通 OCR 结果、质量门和逐文件恢复。
4. 修复分类覆盖与置信度校准，先关闭未经验证的自动就绪。
5. 重构六要素为候选、校验和证据输出，按字段逐项提高指标。
6. 接入冻结集门禁，完成前端状态和浏览器验收。

每个切片保留兼容接口并独立提交。数据库调整必须使用增量迁移且提供回滚；配置开关默认采用保守行为。若分类或抽取新逻辑回归，可回退到“全部人工确认”或旧字符串字段读取，不影响原文件和已存在的审查结果。

本设计是以下既有设计的整合与增量补充，不取代其已确认边界：

- `2026-09-09-contract-upload-reliability-design.md`：保留 PDF 字体兼容、上传五态和安全错误展示。
- `2026-07-26-ocr-quality-timeout-design.md`：保留 `DocumentParseResult`、OCR 子进程、强制超时和人工复核语义。
- `2026-09-11-smart-contract-inbox-design.md`：保留导入批次/审查批次分离、文件级类型和失败项恢复。
- `2026-09-10-synthetic-frozen-contract-dataset-v3-design.md`：复用 50+2 冻结集，但明确构造真值与法务金标准的边界。

如本设计与早期设计在自动就绪阈值上存在表面冲突，以“验证集高置信度精确率达到 95% 后才允许自动就绪”为新增安全前提；其余既有设计继续有效。
