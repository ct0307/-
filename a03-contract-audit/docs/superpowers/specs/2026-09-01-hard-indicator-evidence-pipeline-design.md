# 硬指标证据流水线设计

日期：2026-09-01  
状态：已批准，待实施计划

## 1. 背景与目标

阶段二不继续堆叠功能，而是把现有能力转化为可重复、可审计、不可误报的验收证据。当前代码已经具备要素指标统计、基准统计和批次业务能力，但仍有以下缺口：

- `schema.json` 没有在要素评测入口强制执行，非法金标准仍可能参与评分。
- 金标准只记录单个审核人，不能证明经过双人复核。
- 性能模块只做统计，没有负责预热、正式轮次、调用和原始日志的执行器。
- 缺少 50 份有效文件加 2 份异常文件的批量验收执行器。
- PostgreSQL 目前只有代码与 SQLite 烟雾证据，不能标记为已完成真实环境验证。

本阶段建立模块化命令行证据流水线。真实合同集、Docker、PostgreSQL、OpenClaw 和 GPU 环境不齐备时，工具仍应完整可测，但报告必须明确标记为 `blocked`，不得推断达标。

## 2. 范围

### 2.1 本阶段包含

1. 强制校验冻结金标准并计算要素准确率。
2. 执行并记录 50 份有效文件和 2 份异常文件的批量验收。
3. 在相同口径下执行 OpenClaw 与 GPU 基准。
4. 生成统一运行清单、追加式原始事件和可再生汇总报告。
5. 修正硬指标矩阵中证据状态与实际验证范围不一致的描述。

### 2.2 本阶段不包含

- 制造或伪造真实合同、人工标注、硬件测量值及 PostgreSQL 实测结果。
- 为了跑通验收而降低接口校验、缩小样本数或减少基准轮次。
- 改造业务前端、重写批次服务或更换模型适配层。
- 将原始合同、密钥、完整模型响应或大体积运行目录提交到 Git。

## 3. 总体架构

采用模块化 CLI。各命令可以独立执行，共享证据模型、运行目录和退出状态。

```text
冻结输入与环境配置
        |
        v
  preflight 前置校验
        |
        +--> elements：Schema、双人复核、字段评分
        +--> batch：50 份有效文件同批 + 2 份异常文件隔离
        +--> benchmark：OpenClaw/GPU 各 3 次预热 + 5 次正式轮次
        |
        v
 evidence：manifest + 追加式 JSONL + 汇总报告
```

建议命令入口：

```powershell
python -m evaluation.cli elements ...
python -m evaluation.cli batch ...
python -m evaluation.cli benchmark ...
python -m evaluation.cli report ...
```

模块边界：

| 模块 | 职责 | 不负责 |
|---|---|---|
| `elements` | 金标准验证、预测集对齐、准确率计算 | 调用业务模型生成预测 |
| `batch` | 上传、轮询、超时、隔离失败、记录事件 | 改写批次业务规则 |
| `benchmark` | 调用目标端点、控制轮次、采样、对比 | 伪造缺失的功率或成本数据 |
| `evidence` | 运行清单、事件追加、脱敏、报告生成 | 判定业务指标口径 |
| `cli` | 参数解析、子命令分派、退出码 | 承载指标算法 |

## 4. 证据模型与目录

每次执行创建唯一 `run-id`，默认写入本地 `evaluation-runs/<run-id>/`。实施时将该原始运行目录加入项目忽略规则。正式入库的证据只能是人工检查后的脱敏摘要、配置和索引。

```text
evaluation-runs/<run-id>/
├── manifest.json
├── elements.jsonl
├── batch-events.jsonl
├── benchmark.jsonl
└── report.md
```

所有结构化记录至少包含：

- `schema_version`
- `run_id`
- UTC 时间戳
- Git 提交号与工作区是否干净
- 命令参数的脱敏副本
- 配置与输入文件 SHA-256
- Python、操作系统、服务版本及可用硬件信息
- 状态、错误类别和不含密钥的错误摘要

原始 JSONL 只追加并及时刷新，不覆盖历史事件。`report.md` 只能从 `manifest.json` 和 JSONL 重新生成。报告不得保存合同正文、密钥、认证头或完整模型响应。

运行状态统一为：

- `passed`：所有前置条件、执行步骤和阈值均满足。
- `failed`：执行完成但质量、成功率或性能阈值未满足。
- `blocked`：缺少数据、Docker、PostgreSQL、设备或目标端点，无法执行真实验收。
- `error`：输入、配置或程序异常导致运行无效。

## 5. 要素准确率评测

### 5.1 金标准契约

现有 `schema.json` 升级为版本化契约，并由 CLI 对 JSONL 每一行强制校验。由于当前尚无冻结数据集，可以直接采用明确的双人复核结构：

- `reviewers` 必须是恰好两个不重复的非空审核人标识。
- `review_status` 只能是 `agreed` 或 `adjudicated`。
- 当状态为 `adjudicated` 时必须提供 `adjudicator`。
- `document_kind`、`gold.payment_terms` 和附加字段严格遵循 Schema。
- `case_id` 必须唯一；预测中的重复或未知 `case_id` 使运行无效。

审核人使用内部编号或化名，避免个人信息进入证据。数据集哈希基于规范化后的完整金标准记录计算，绑定内容、版本和复核信息。

### 5.2 评分规则

沿用现有六字段宏平均口径。缺失预测作为漏报计零分并单独计数，不能从分母移除；未知预测记录直接拒绝。报告必须同时给出：

- 总体 Precision、Recall、F1 和样本数。
- 按字段、合同类型、文档类型的结果。
- 缐失预测、错误案例和逐案例结果。
- 数据集、预测集、Schema 与评测代码版本哈希。

只有冻结金标准通过强校验且总体指标达到预设阈值时，才允许标记 `passed`。

## 6. 50+2 批量验收

批量执行器读取一份清单，清单必须声明恰好 50 个 `valid` 样本和 2 个 `invalid` 样本及其预期错误类别。执行流程如下：

1. 前置检查文件存在、类型、大小、SHA-256 和样本数量。
2. 将 50 份有效文件放在同一批次提交，证明单批容量，而不是拆成多个小批次。
3. 按服务端批次与文件状态轮询，直到完成、失败或达到总超时。
4. 两份异常文件分别提交，验证失败隔离，不能污染有效批次。
5. 记录每个文件的状态迁移、重试、耗时、错误类别和最终状态。
6. 重新查询完成批次，验证刷新恢复、幂等或去重行为及审计记录。

执行器按文件流式打开并使用受控并发，不预先把 52 份文件全部读入内存。若现有接口仍需一次请求承载 50 份文件，则客户端只保留该请求所必需的数据；实施时同时记录客户端与服务端可获得的内存峰值，发现不可接受的峰值再单独设计业务接口改造，不在本阶段隐式扩展范围。

通过条件至少包括：50 份有效文件均到达预期终态、2 份异常文件均被明确拒绝或隔离、无跨文件失败扩散、无永久卡住状态、事件记录完整。任何样本缺失都不能生成通过报告。

## 7. OpenClaw/GPU 基准

### 7.1 公平性契约

两端必须使用完全相同的模型哈希、提示词版本、冻结数据集哈希、上下文长度、并发数和输出 Schema 哈希。认证信息通过环境变量注入，只记录变量是否配置，不记录值。

每个目标执行 3 个完整数据集预热轮次和 5 个完整数据集正式轮次。预热结果保留为事件但不进入统计；少于规定轮次或只传单个样本时，运行无效。

### 7.2 指标与结论

正式轮次记录请求级延迟、成功状态和轮次总耗时，并汇总：

- 成功率
- P50/P95 延迟
- 吞吐量
- 均值、标准差和 95% 置信区间
- 可选能耗与成本

能耗只接受功率计或设备导出的时间序列；缺少采样时固定标记 `not_measured`。成本必须注明来源、币种和计算时间，否则标记 `not_available`。

报告只陈述实测结果。OpenClaw 未在预先声明的主指标上胜出时，应标记硬指标未达，而不是修改口径或选择性隐藏结果。

## 8. 错误处理与退出状态

CLI 使用稳定的非零退出状态区分失败类别：输入或配置无效、执行异常、指标未达、外部环境阻塞。具体数字在实施计划中固定，并由测试锁定。

关键规则：

- 前置校验失败时不启动外部调用。
- 中途失败仍保留已写入事件，并在 `manifest` 记录终态。
- 超时必须包含目标、阶段和已耗时，禁止无限轮询。
- 密钥、合同正文和认证头在异常信息中统一脱敏。
- 报告生成器发现事件缺失、哈希不一致或轮次不足时拒绝生成 `passed`。

## 9. 测试与验收分层

| 层级 | 自动化范围 | 目的 |
|---|---|---|
| P1 单元测试 | Schema 边界、双人复核、哈希、状态机、统计、退出状态 | 防止错误输入产生有效报告 |
| P1 组件测试 | 使用本地伪端点验证批次轮询、超时、失败隔离、3+5 轮次 | 无真实设备时验证执行器逻辑 |
| P1 回归测试 | 现有要素、批次、OCR、报表隔离和硬指标测试 | 防止破坏现有业务能力 |
| P1 真实验收 | 冻结金标准、50+2 文件、OpenClaw/GPU 原始运行 | 形成最终竞赛证据 |
| P2 环境验收 | Docker Compose、PostgreSQL 16 迁移/回滚/恢复 | 将代码就绪状态升级为已实测 |

真实验收必须保留完整命令、提交号、输入哈希和原始事件。自动化测试通过只能证明工具正确，不能替代真实数据、真实数据库或真实设备结果。

## 10. 硬指标矩阵状态规则

实施开始时先将 PostgreSQL 从“已验证”修正为“代码就绪待实测”。以后只有满足以下条件才能升级状态：

1. 在目标环境完成约定命令。
2. 原始事件、配置和输入哈希齐全。
3. 报告生成器判定 `passed`。
4. 人工检查报告不存在敏感内容和口径偏差。

矩阵中的测试命令、代码结构或 API 上限只能作为能力证据，不能替代真实验收证据。

## 11. 实施顺序

| 优先级 | 阶段 | 完成定义 |
|---|---|---|
| P1 | 要素契约与证据核心 | 非法金标准被拒绝，合法评测生成版本化证据 |
| P1 | 50+2 批量执行器 | 伪端点组件测试覆盖完整状态流和异常隔离 |
| P1 | OpenClaw/GPU 执行器 | 强制 3+5 完整轮次并拒绝不可比结果 |
| P1 | 报告与矩阵修正 | 报告不可误报，矩阵状态与证据一致 |
| P2 | 真实环境执行 | 数据、Docker、PostgreSQL 和设备到位后形成最终证据 |

## 12. 专业审批结论

本设计通过。它优先解决“有代码但没有可信验收证据”的根因，同时不伪造当前缺失的数据与环境。实施阶段不得把真实验收阻塞解释为代码缺陷，也不得用自动化测试结果替代真实硬指标结论。
