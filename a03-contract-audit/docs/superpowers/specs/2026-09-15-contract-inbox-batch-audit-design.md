# 待审合同批量审查交互设计

日期：2026-09-15  
状态：待实施

## 1. 背景与结论

当前待审合同列表只允许用户逐行勾选 `ready` 状态的合同；未勾选时，主按钮“审查就绪项”不可用。批量导入后，用户即使希望审查全部就绪合同，也必须重复勾选，增加了无意义操作。

本次采用“双模式主操作”：零选择代表审查全部就绪合同；存在选择时只审查所选合同。逐行勾选继续用于排除或挑选少量合同，表头增加“全选就绪合同”以支持显式批量选择。

## 2. 方案比较

| 方案 | 结论 | 主要取舍 |
|---|---|---|
| 默认自动勾选全部就绪合同 | 不采用 | 表面省事，但异步解析新增就绪项时，选择状态和用户认知容易不一致 |
| 仅增加表头全选 | 不采用 | 减少点击次数，但审查全部合同仍多一次不必要操作 |
| 零选择审查全部、有选择审查所选 | 采用 | 默认路径最短，同时保留精确选择能力；需要清晰文案避免误解 |

## 3. 交互规则

| 列表状态 | 主按钮 | 点击结果 |
|---|---|---|
| 没有就绪合同 | “暂无就绪合同”并禁用 | 不发起请求 |
| 有就绪合同且未勾选 | “审查全部 N 份就绪合同” | 提交当前全部 `ready` 合同 ID |
| 已勾选合同 | “审查选中的 N 份合同” | 只提交选中的 `ready` 合同 ID |
| 请求处理中 | 保持当前文案并显示加载状态 | 防止重复提交 |

补充规则：

- 操作栏提示“待确认和失败合同不会进入审查”，明确自动排除范围。
- 表头复选框只控制 `ready` 状态合同；非就绪合同保持禁用。
- 全部就绪合同均已选时，表头复选框为选中；部分已选时为半选。
- 就绪项因轮询变为其他状态时，从选择中移除；新变为就绪的合同不自动加入已有显式选择。
- 点击“审查全部”时，以点击瞬间的就绪 ID 快照为准，避免请求范围在提交过程中变化。

## 4. 数据流与组件边界

`import-inbox` store 继续拥有批次、就绪 ID 和显式选择状态。它新增全选/清空能力，并提供本次操作的目标 ID：存在显式选择时返回选择集，否则返回当前就绪集。

`ContractInbox.vue` 只根据 `readyCount`、`selectedIds` 和 `loading` 渲染表头复选框、提示和动态按钮文案，不自行复制业务筛选规则。

`AuditView.vue` 在用户点击时获取目标 ID 快照并调用既有批量审查接口。若目标为空则不调用接口；后端仍负责校验合同是否允许进入审查，前端选择不能绕过状态校验。

## 5. 异常与反馈

- 提交前就绪项变为不可审查时，沿用后端错误反馈并刷新收件箱，不静默扩大审查范围。
- 部分合同被后端拒绝时，保留既有批次错误处理；不得将未成功创建审查任务的合同显示为“审查中”。
- 审查请求失败后保留仍有效的显式选择，方便用户重试。
- 主按钮不能只依靠禁用态解释原因；无就绪合同时显示明确文案。

## 6. 验收标准

| 优先级 | 验收项 |
|---|---|
| P1 | 有就绪合同且零选择时，一次点击提交全部就绪合同 |
| P1 | 有显式选择时，只提交所选合同 |
| P1 | 待确认、失败、解析中和审查中合同不会进入提交集合 |
| P1 | 没有就绪合同时按钮禁用且文案明确 |
| P2 | 表头支持全选、取消全选和半选状态，且仅影响就绪合同 |
| P2 | 请求中禁止重复提交；失败后仍可重试 |
| P2 | 桌面端和移动端的按钮、提示及选择控件不重叠、不溢出 |

自动化测试覆盖 store 的目标 ID 计算和选择状态，以及正常、零选择、部分选择、无就绪项、状态变化和请求失败场景。前端完成后运行相关单元/E2E 测试、类型检查和构建，并在浏览器实测正常、空、错误与响应式状态。

## 7. 非目标

- 不修改合同解析、类型识别或审查算法。
- 不让待确认合同自动进入审查。
- 不改变后端审查权限和状态校验。
- 不新增依赖，不修改数据库结构。
