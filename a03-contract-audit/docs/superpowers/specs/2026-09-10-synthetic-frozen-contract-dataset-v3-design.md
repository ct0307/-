# 50+2 真实企业合同冻结集 v3 设计

## 1. 目标与边界

v3 用于构造一批接近企业日常合同形态的合成合同，服务于合同解析、风险识别、版本关系、附件关联和批量处理回归测试。目标是让合同的业务事实、条款体系、附件和文档形态先符合真实交易逻辑，再提供稳定可复现的测试输入。

v3 是全新版本，独立使用 `frozen_contracts_v3` 包和 `outputs/frozen-contracts-v3` 输出目录。不得修改、覆盖或重新解释 v1、已冻结 v2 的源文件、输出文件和哈希。所有文件均为合成数据，不能冒充真实企业合同、真人审核结果或法律意见。

本版本不承诺真实 API、OCR、PostgreSQL、Redis/Celery、GPU/能耗或双人真人复核结果。未执行的环境能力必须在报告中标记为 `not_measured` 或 `blocked`。

## 2. 版本组成

### 2.1 数量与文件形态

- 50 份有效合同，编号 `F3-001` 至 `F3-050`。
- 2 份无效样本，编号 `FX3-051`、`FX3-052`，分别覆盖空/损坏文件和伪装扩展名。
- 1 份不计入 50+2 的补充失败样本，用于非空损坏文件重试路径。
- 目标格式分布保持 v2 的测试覆盖：14 DOCX、21 文本 PDF、15 扫描或混合 PDF。
- 每个有效样本只对应一个明确的源案例定义；运行时不得随机改变主体、金额、期限、条款或扫描参数。

### 2.2 目录隔离

代码放置于：

```text
backend/evaluation/datasets/frozen_contracts_v3/
  __init__.py
  models.py
  cases.py
  clauses.py
  annexes.py
  content.py
  renderers.py
  ooxml.py
  generate.py
  validate.py
  build_predictions.py
  precheck.py
  corpus-profile.json
  README.md
backend/tests/test_frozen_contract_dataset_v3.py
outputs/frozen-contracts-v3/
```

生成器只读取 v3 显式定义的数据，不读取 v1/v2 的案例作为事实来源，不联网，不调用 LLM，不从测试断言反向生成正文。

## 3. 逐案事实模型

50 个有效案例在 `cases.py` 中以不可变结构逐案声明，不允许通过序号循环从其他版本派生。每案至少包含：

- 交易场景、合同类型、合同名称和起草风格；
- 甲乙方或多方主体的合成名称、角色、签署信息和通知地址；
- 标的描述、数量/规格、计价单位、含税规则或明确的计价公式；
- 履行地点、起止日期、里程碑、交付物和验收条件；
- 付款节点、发票条件、质保/服务期和保证金（无此项时显式为 `None`）；
- 违约责任、责任上限/例外、保密、数据和知识产权安排；
- 适用附件及其版本、优先级和引用位置；
- 风险层级、冲突双值、优先规则以及 DOCX 修订/批注（如该案需要）。

每个字段都必须有稳定的业务含义。金额可以是固定总价、单价结算、按里程碑结算或无固定总价的框架协议，但不得为了填充统一 Schema 而伪造固定金额。

50 案例覆盖八类现实业务：采购/供货、技术与软件服务、运维/咨询/培训、房屋设备场地租赁、建设装修与监理、人力与员工服务、数据处理与知识产权、框架订单与多方合作。每一类至少有多个主体结构、付款方式和附件组合。

## 4. 合同正文生成

### 4.1 内容来源与结构

正文由“案例事实 + 场景条款模块 + 风格措辞库 + 风险/冲突配置”组合生成。页数不是输入变量，禁止使用目标页数计算重复段落、空白页或同构业务记录。渲染后页数只作为验收结果记录。

普通合同应形成完整的真实条款体系，例如：定义与解释、交易范围、规格/服务范围、交付与验收、价格与付款、变更、质量/服务等级、知识产权、数据与保密、合规、安全、违约、责任限制、期限与终止、通知、不可抗力、争议解决、其他和签署页。短式订单只保留与交易匹配的核心条款，不强行套用全部章节。

### 4.2 篇幅和密度门槛

- 短式订单：正文及其必要表格合计约 1,200–1,800 个中文字符；
- 普通合同：正文合计至少 2,500 个中文字符，通常为 2,500–4,000；
- 长合同、主协议或含复杂技术/工程附件者：正文合计至少 6,000 个中文字符；
- 每个正文页必须达到最低非空字符密度，最低阈值由渲染报告按纸张和字体配置计算，不得依靠声明页数放宽；
- 空白比例、重复段落比例和单一模板段落占比均需在校验报告中给出，超过阈值即失败。

正文中的合成标识只能出现在封面/页脚或明确的测试说明处，不得伪造成真实印章、个人证件、银行账号或可识别真人信息。

## 5. 12 种起草风格

每种风格必须拥有独立的章节顺序、段落组织、句式和风险关注点，并由测试验证实质差异：

| 风格 | 真实使用定位 | 结构特征 |
|---|---|---|
| `buyer_standard` | 采购方标准合同 | 采购控制、验收、质保和扣款优先 |
| `supplier_standard` | 供应商标准合同 | 交付边界、变更计价和责任上限优先 |
| `business_draft` | 业务部门初稿 | 商务条款先行，技术与法务条款较简 |
| `legal_redline` | 法务修订稿 | 修订痕迹、批注、定义和例外条款完整 |
| `model_contract` | 行业示范文本 | 条款编号规范，权利义务相对平衡 |
| `online_terms` | 平台在线条款 | 接受方式、账号/订单生效和电子通知突出 |
| `framework_order` | 框架协议/订单 | 主协议、订单、价格表和订单优先级关联 |
| `master_supplement` | 主协议补充协议 | 引用既有协议，明确变更范围和继续有效条款 |
| `project_conditions` | 项目专用条件 | 项目现场、里程碑、变更单和现场签证突出 |
| `industry_template` | 行业模板 | 行业术语、监管/安全义务和标准引用突出 |
| `customer_template` | 客户方模板 | 客户审核、供应商配合和信息安全义务突出 |
| `short_order` | 订单/确认单 | 标的、数量、价格、交期和验收的短式表达 |

测试不得只比较标题。每种风格须至少比较章节顺序、义务集合、附件顺序、关键句式和风险条款分布；同一风格内也必须由案例事实产生差异。

## 6. 场景专属附件

附件由场景决定，具有独立字段和真实业务用途，不得统一生成“记录项目/责任方/业务凭证”三列表格：

- 采购/供货：设备或物料清单、规格参数、交期、包装运输、验收标准、质保；
- 技术/软件服务：SLA、里程碑、交付物、接口清单、验收用例、缺陷等级；
- 运维/咨询/培训：服务目录、响应时限、人员资历、培训计划、报告模板；
- 工程/装修/监理：工程量清单、进度计划、施工界面、变更单、付款节点、安全要求；
- 租赁：资产清单、交接确认、使用限制、能耗承担、维修保养和返还标准；
- 数据/IP：数据目录、处理目的、保存期限、跨境/委托处理说明、成果归属和许可范围；
- 人员服务：岗位、人数、服务边界、替换机制、劳动合规和考勤/结算规则；
- 框架/多方合作：订单模板、价格表、主体加入/退出规则、授权矩阵和优先级。

附件必须在正文中被引用，附件版本、签署状态和与正文冲突时的优先规则必须可追溯。

## 7. 文档渲染与版本痕迹

- DOCX 使用现有项目文档工具生成 A4 中文合同，保留必要的表格、页眉页脚、签署页和附件分页；法务修订样本使用真实 OOXML `w:ins`、`w:del`、批注关系和范围标记。
- 文本 PDF 从完整排版正文生成，保留可检索文本层。
- 扫描/混合 PDF 先生成完整排版页，再用固定 DPI、压缩、轻微倾斜和边缘阴影栅格化；混合样本明确哪些页保留文本层，哪些页仅保留图像层。
- 所有渲染参数写入 manifest，使用固定种子，确保重复生成哈希稳定。
- 若 Word COM、LibreOffice、OCR 或 Poppler 不可用，只记录阻塞证据并运行可用的结构校验，不把替代检查写成完整视觉通过。

## 8. 校验、测试与验收

### 8.1 必须自动化检查

1. 案例编号、数量、格式和风格分布正确，50 valid/2 invalid 完整。
2. 每案字段完整且事实独立；无从 v1/v2 继承事实的隐式路径。
3. 正文达到对应篇幅和字符密度阈值；无空白页填充、连续重复模板段落或无意义附件。
4. 风格差异通过章节顺序、义务集合、措辞和附件顺序检查。
5. 附件类型与业务场景匹配，正文引用、版本和优先规则一致。
6. DOCX/PDF 可打开；扫描件按能力记录 OCR 文本覆盖率；混合 PDF 的文本层状态符合案例定义。
7. 冲突双值、修订集、无效样本和隐私占位符符合预期。
8. 生成文件 SHA-256、字节数、字符统计和渲染参数写入冻结清单，禁止静默覆盖已冻结目录。

### 8.2 测试顺序

先新增 v3 专项测试并确认其能够识别 v2 的稀疏正文、重复风格、页数驱动填充和非逐案定义问题；再实现生成器和校验器；之后执行静态校验、文档解析、渲染抽样和构造真值技术预评测。真实 API/OCR/数据库/真人复核另行报告，不与本地测试混为一谈。

### 8.3 通过标准

只有静态结构、正文真实性门槛、附件匹配、渲染可读性和哈希冻结全部通过，才能称为“v3 技术冻结集通过”。在没有真实企业合同授权样本和真人法律复核前，只能称为“合成、接近真实业务结构的测试集”，不得称为现实合同金标准。

## 9. 交付与回滚边界

v3 所有实现和输出独立提交。任何校验失败都保留失败报告和最小复现样本，不修改已冻结 v1/v2。若后续发现内容真实性问题，必须创建 v4 或更高版本，禁止对已发布 v3 进行就地改写。
