# 大模型合同审查精确可靠与成本控制设计

## 1. 背景

当前合同审查链路为法务 Agent、财务 Agent 串行审查，合同按条款窗口送入兼容 OpenAI 协议的模型接口。线上核查得到以下事实：

- 当前 `LLM_MAX_OUTPUT_TOKENS` 实际值为 `1600`，不是 `2048`；
- 最近真实批次的模型调用均达到 `1600` tokens，且 `finish_reason=length`；
- 截断被转换为 Agent 降级提示，但任务仍可标记为 `done`；
- 使用短合成合同测试时，`1600` 和 `2048` 两种输出上限都发生截断；
- 单纯增大输出上限会增加耗时，但不能保证形成完整、合法、可验证的风险结果。

因此，问题不是单一配置错误，而是生成约束、截断恢复、结果校验、状态语义和质量评测没有形成闭环。

## 2. 目标

本设计以审查精确可靠为第一目标，在达到质量门槛后再优化模型 tokens、调用次数、延迟和费用。

目标包括：

1. 完整覆盖合同审查计划中的所有窗口和维度；
2. 防止截断、格式错误或 Agent 降级结果被标记为正式完成；
3. 每条正式风险都能回溯合同原文，并对法律依据进行独立校验；
4. 对金额、比例、日期等确定性问题使用代码计算；
5. 仅对高风险、证据不足和冲突结论增加深度模型调用；
6. 用可重放的 A/B 评测选择满足质量门槛后成本最低的配置。

## 3. 非目标

- 不通过单纯提高 `max_tokens` 声称问题已经解决；
- 不把单元测试通过等同于真实法律审查准确率达标；
- 不在缺少人工金标准时对外宣称准确率、召回率或成本优势；
- 不在本设计阶段更换模型供应商、安装依赖或修改部署架构；
- 不允许真实敏感合同未经授权发送到公网模型端点。

## 4. 方案比较

| 方案 | 准确可靠性 | 运行成本 | 开发成本 | 结论 |
|---|---:|---:|---:|---|
| 单纯提高输出上限和超时 | 低 | 高且不可控 | 低 | 不采用 |
| 所有条款由多个 Agent 全量复核 | 高 | 很高 | 高 | 仅适合极少数高风险场景 |
| 选择性级联审查 | 高 | 中等且可控 | 中等 | 采用 |
| 纯规则引擎 | 中低 | 低 | 中等 | 作为确定性校验补充 |

选择性级联方案复用现有条款切片、双 Agent、RAG、任务状态和评测基础。正常结果不增加不必要复核，只对不能满足质量门禁的局部内容追加调用，因此是当前项目最合理的候选方案。是否达到最优性价比，仍须通过 A/B 评测证明。

## 5. 总体架构

```text
合同解析
  -> 条款结构化与审查计划
  -> 紧凑候选风险提取
  -> 确定性校验
  -> 法规证据独立检索与验证
  -> 高风险/证据不足/冲突项选择性复核
  -> 合并去重与质量门禁
  -> done / review_required / audit_failed
```

### 5.1 条款结构化与审查计划

- 保留稳定的 `clause_id`、原文字符范围和相邻条款关系；
- 初始窗口继续按完整条款组合，避免无条件缩小窗口导致调用数激增；
- 根据合同类型和用户选择的维度生成明确的 Agent 审查计划；
- 路由只决定审查维度，不得静默排除未检查条款；
- 只有发生截断、格式失败或窗口内容过密时，才拆分当前窗口。

### 5.2 紧凑候选风险提取

每次模型调用只承担一个角色、一个窗口和一组相关维度。输出统一为 JSON 对象，避免顶层数组在兼容接口中的约束差异：

```json
{
  "risks": [
    {
      "category": "付款条件风险",
      "level": "high",
      "quote": "合同原文",
      "reason": "风险解释",
      "suggestion": "修改建议"
    }
  ],
  "has_more": false
}
```

生成约束包括：

- 单次最多返回 5 条风险；
- 限制 `category`、`quote`、`reason` 和 `suggestion` 的最大长度；
- 禁止 Markdown、解释性前后缀和模型自行生成正式法规依据；
- 优先使用供应商支持的 JSON Schema 或结构化输出能力；
- `has_more=true` 时对当前窗口继续分页，不丢弃剩余候选风险；
- `max_tokens` 作为保护上限，而不是质量控制手段。

输出上限不在设计中写死为 `2048` 或 `4096`。不同模型可能将推理 tokens 计入完成量，最终数值由真实 A/B 评测确定。

### 5.3 确定性校验

模型结果进入正式风险集合前必须通过：

1. JSON Schema 校验；
2. `finish_reason` 非 `length`；
3. `quote` 能在合同原文中精确定位；
4. 风险维度属于当前 Agent 职责范围；
5. 金额、付款比例、日期、期限和大小写金额由代码重新计算；
6. 重复风险按合同位置、类别和语义标识合并。

模型负责发现候选问题和生成解释，确定性代码负责能够计算或精确比对的事实，不让大模型替代计算器或字符串校验器。

### 5.4 法规证据核验

- 先根据候选风险重新执行 RAG 检索，再将授权候选证据交给模型判断支持关系；
- 模型只能返回系统提供的 `evidence_id`，不能自由填写法规名称或条号；
- 系统校验证据来源、版本、有效日期、适用合同类型和条文内容；
- 无有效证据的结论可以作为待核验风险保留，但必须进入 `review_required`，不得伪装成已有法规支持。

### 5.5 选择性深度复核

只有以下内容进入第二 Agent 或更强模型复核：

- `high` 风险；
- 原文无法精确定位；
- 法规证据不足或相互冲突；
- 法务与财务结论冲突；
- 确定性计算与模型结论不一致；
- 模型显式给出低确定性信号。

两个 Agent 结论不一致时，系统保留分歧并转人工复核，不通过多数投票自动生成法律结论。

## 6. 截断、超时与恢复

| 异常 | 处理策略 | 最终状态 |
|---|---|---|
| `finish_reason=length` | 将当前窗口按完整条款二分后重试，最多两轮 | 仍失败则 `review_required` |
| `has_more=true` | 以同一窗口和游标继续提取 | 完整后进入校验 |
| JSON 不合法 | 使用同一输入和严格结构提示重试一次 | 仍失败则 `review_required` |
| 网络瞬时失败或模型超时 | 指数退避重试，最多两次，保持幂等 | 仍失败则按覆盖程度决定失败状态 |
| 单个非关键窗口失败 | 隔离局部结果，其他窗口继续 | `review_required` |
| 必需 Agent 全部失败 | 不发布正式风险 | `audit_failed` |
| 任务达到整体硬时限 | 停止新增调用，保存诊断信息 | `review_required` 或 `audit_failed` |

每次重试必须带稳定调用标识，避免网络不确定时重复写入结果。已通过校验的窗口结果应持久化，任务恢复后只重跑缺失或失败的窗口。

## 7. 状态语义与发布规则

任务状态为：

```text
queued -> parsing -> reviewing -> validating
                                  -> done
                                  -> review_required
                                  -> audit_failed
```

只有同时满足以下条件才能标记 `done`：

- 审查计划中的窗口和必需 Agent 全部完成；
- 所有响应均未截断；
- 所有正式风险均通过结构和原文定位校验；
- 确定性复算无未处理冲突；
- 所有正式风险的法规证据均已完成验证；无证据或待人工核验的风险必须使整体状态进入 `review_required`；
- 不存在“审查引擎降级”提示冒充正式风险。

`review_required` 表示系统形成了部分可用结果，但存在局部失败、证据不足或结论冲突。`audit_failed` 表示模型不可用、任务超时或没有形成任何可用结果。

## 8. 可观测性

每次模型调用至少记录：

```text
contract_id
window_id
agent
dimension
attempt
prompt_tokens
completion_tokens
finish_reason
latency_ms
validation_status
error_code
```

日志不得保存完整合同原文、完整提示词、密钥或模型响应。管理侧应能按模型、Agent、合同类型和失败原因聚合截断率、降级率、调用次数和 tokens。

## 9. A/B 评测

### 9.1 对照组

- A：当前 `1600 tokens` 基线；
- B：仅提高输出上限；
- C：选择性级联、受控输出和截断拆分。

三组必须使用相同模型版本、提示版本、知识库版本、合同集、温度和运行环境。每个配置保留可重放清单和原始指标证据。

### 9.2 质量门槛

| 优先级 | 指标 | 内部目标 |
|---|---|---:|
| P1 | 高风险召回率 | >= 95% |
| P1 | 错误成功率 | 0 |
| P1 | 最终截断率 | 0 |
| P1 | 原文引用可定位率 | 100% |
| P1 | 无效法规引用率 | 0 |
| P2 | 整体风险召回率 | >= 90% |
| P2 | 风险精确率 | >= 85% |
| P2 | JSON 合法率 | 100% |
| P3 | P95 耗时、tokens 和 API 成本 | 在通过 P1/P2 的方案中选择最低者 |

这些数字是内部验收目标，不是当前实测结论。若比赛规则或法律专家确定更严格门槛，以更严格口径为准。

### 9.3 金标准要求

- 使用冻结合同集进行技术预评测；
- 由两名法律人员独立标注风险、等级、原文位置和适用证据；
- 分歧由第三人裁决；
- 人工复核完成前只能表述为“合成数据技术预评测”；
- 自动化测试通过不能替代真实模型质量评测。

## 10. 成本选择原则

性价比不是单独比较总 tokens，而是在质量门槛全部通过后比较：

- 每份成功合同的模型调用次数；
- 每份成功合同的 prompt/completion tokens；
- 每条有效风险的模型成本；
- P50/P95 完成时间；
- 截断、重试、降级和失败比例；
- 人工复核工作量。

如果更便宜的配置未达到高风险召回率、原文定位率或错误成功率门槛，则不属于可选方案。

## 11. 安全边界

- DeepSeek 等公网模型只用于无敏感信息的合成比赛数据；
- 真实合同默认使用私有化模型端点；
- 如需使用公网模型，必须获得明确授权并完成脱敏、数据出境和供应商留存策略评估；
- 提示词、日志、数据库和评测产物不得泄露合同全文或密钥；
- 未执行私有模型、目标 GPU、PostgreSQL、真实 52 文件或人工准确率评测时，不得写成已经达标。

## 12. 实施边界

后续实施应聚焦以下模块：

1. LLM 适配器的结构化输出、调用标识和完成原因处理；
2. 审查器的候选提取、分页、局部拆分和选择性复核；
3. Runner 与任务服务的窗口级持久化、恢复和状态发布门禁；
4. 模型调用日志的窗口、尝试次数和校验结果字段；
5. 前端对 `review_required`、局部失败和重试进度的准确展示；
6. 单元、集成、真实模型 A/B 和人工金标准评测。

不进行与该可靠性目标无关的架构重构，不安装新依赖，不改变现有合同上传和权限边界。

## 13. 验收结论口径

只有在真实 A/B 评测完成后，才能从通过全部 P1/P2 门槛的配置中选取成本最低者，并称其为当前环境下最具性价比的方案。未经评测，只能表述为“选择性级联是当前首选候选架构”。
