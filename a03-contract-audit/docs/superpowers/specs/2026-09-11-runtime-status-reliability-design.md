# 模型运行状态可靠性设计

日期：2026-09-11  
状态：待用户确认

## 1. 背景与目标

页面顶部的运行状态徽标曾出现“模型服务离线”，但后端实际已经能够调用 DeepSeek。当前原因是：运行时探活将所有异常归类为 `offline`，前端一次失败就更新为离线，后端还会缓存结果 30 秒；同时开发机可能同时运行多套前后端端口，导致用户难以判断页面实际连接的服务。

目标：

- 让状态显示反映真实的运行阶段，而不是一次网络抖动的结果。
- 让运维人员可以区分鉴权、超时、地址、模型不存在和网络错误。
- 让配置变更在启动阶段被校验，避免服务启动后才发现配置无效。
- 统一本地开发服务入口，避免重复进程和端口错配。
- 用自动化测试锁定失败、恢复、刷新和配置校验行为。

## 2. 方案选择

| 方案 | 结论 | 说明 |
|---|---|---|
| 只修改前端文案 | 不采用 | 只能隐藏症状，不能识别后端真实错误 |
| 只增加重试 | 不采用 | 仍无法区分 API Key、模型名和地址错误 |
| 后端分类探活 + 前端容错 + 启动校验 | 采用 | 覆盖故障源、显示层和运行环境，改动集中且无需新依赖 |

## 3. 后端运行状态

### 3.1 响应契约

`GET /api/v1/runtime/status` 保留登录保护，响应增加以下字段：

- `status`：`checking`、`online`、`degraded`、`offline` 或 `unknown`。
- `error_code`：稳定的机器可读错误码，可为空。
- `detail`：不包含密钥和合同内容的中文诊断信息。
- `provider`、`model`、`endpoint`：实际生效的模型配置，其中 endpoint 必须脱敏。
- `latency_ms`：最近一次探活耗时。
- `checked_at`、`last_success_at`：状态时间戳。

兼容性要求：旧前端仍能读取 `status`、`provider` 和 `model`；新增字段均为可选字段。

### 3.2 探活规则

探活只调用配置端点的 `/models`，不发送合同内容。对单次请求最多进行一次短重试，并将异常映射为稳定错误码：

- HTTP 401/403：`auth_failed`
- HTTP 404：`endpoint_not_found`
- 请求超时：`timeout`
- 连接异常：`network_error`
- 响应中找不到配置模型：`model_not_found`
- 其他响应或解析错误：`probe_failed`

缓存仍保留，但缓存对象包含错误码和时间戳。缓存命中只用于降低请求频率，不隐藏最近一次失败原因。

### 3.3 就绪接口

增加不需要登录的：

- `GET /health/live`：进程存活即返回 200。
- `GET /health/ready`：检查实例继续接收流量所需的数据库等必要依赖；必要依赖不可用时返回 503。模型供应商波动作为 `degraded` 检查项返回，但不摘除仍可提供上传、查询和任务恢复能力的实例。
- `GET /health/preflight`：严格检查数据库连接、模型配置和模型探活；模型不可用时返回 503，供部署前预检使用，不应直接作为编排流量摘除探针。

原有 `GET /health` 保持兼容，仅表示进程可响应，不代表模型已就绪。

## 4. 前端状态机

前端徽标状态流转为：

`checking -> online`

`online -> degraded`（单次失败，保留最近一次在线模型）

`degraded -> online`（探活恢复）

`degraded -> offline`（连续两次失败）

页面刷新时先显示 `checking`，不立即显示离线。轮询周期保持 30 秒；请求失败时展示“正在重试”及安全错误摘要，避免把鉴权失败误报为模型离线。前端不显示 API Key、完整 URL 查询参数或后端堆栈。

## 5. 配置与进程治理

- 后端启动时校验 provider、base URL、model；DeepSeek 模式必须配置 API Key。
- 启动日志只记录 provider、model、脱敏 endpoint 和配置指纹，不记录密钥。
- 增加统一本地启动入口，固定前端 `5173`、后端 `8000`，启动前检测端口占用并提示已有进程。
- `.env` 变更必须重启后端；前端代理地址通过单一环境变量传入，禁止代码内出现第二个默认端口。

## 6. 测试与验收

后端单元测试：

- 各类 HTTP、超时、连接和模型缺失错误的映射。
- endpoint 脱敏和响应字段兼容性。
- `/health/live`、`/health/ready` 的 200/503 行为。
- DeepSeek 配置缺失时启动校验失败。

前端测试：

- 初始检查、单次失败、连续失败、恢复和刷新状态。
- 错误码映射为可读文案且不泄露敏感配置。
- 5173 页面代理到 8000，移动端无溢出。

验收标准：

- DeepSeek 可用时页面显示 `DEEPSEEK · deepseek-v4-pro`。
- 单次探活失败不再直接显示“模型服务离线”。
- 连续失败时显示明确错误类别和重试状态。
- `/health/preflight` 能在部署前阻断无效模型配置；`/health/ready` 不因共享模型供应商波动摘除整套副本。
- 完整质量门禁、前后端相关测试、类型检查和生产构建通过。

## 7. 边界

本次不修改模型供应商、不更换 API Key、不上传真实合同、不引入 Prometheus/Celery 等新基础设施。生产环境的告警和指标接入作为后续运维工作，不影响本次运行状态可靠性改造。
