# 证据支持关系校验设计

## 目标与边界

本阶段解决“检索到可信来源不等于来源支持风险结论”的问题。系统继续允许模型提出候选风险，但正式依据由后端检索和校验。规则校验器只做保守判断，不声称替代法务论证或自然语言推理模型。

## 状态模型

每条风险记录增加：

- `support_relation_status`: `supported`、`unclear` 或 `contradicted`；旧数据和无法判断的数据默认 `unclear`。
- `support_validation_reason`: 面向人工复核的短原因。
- `support_validator_version`: 规则版本，用于审计和回放。

只有以下条件同时满足，证据状态才允许为 `supported`：

1. 来源具有可信作用域；
2. 风险原文已在合同正文中核验；
3. 支持关系规则明确判断来源内容与风险类别/原因具有足够语义重叠；
4. 风险不是仅由“条款缺失/全文未检出”产生的否定性发现。

任一条件不满足都必须人工复核。矛盾或规则无法判断时保留来源和原因，不删除候选风险。

## 数据流

```text
模型候选风险
  -> 原文存在性核验
  -> 逐风险 RAG 检索
  -> 支持关系规则校验
  -> evidence_status 映射
  -> tier / requires_manual_review
  -> API 与前端展示
```

## 兼容策略

保留 `level`、`confidence`、`basis` 和现有 `evidence_status`。旧记录通过迁移默认标记为 `unclear`、需要人工复核；前端对缺失字段按未知状态处理。不给现有消费者施加一次性破坏性变更。

## 测试策略

- 先写失败测试，覆盖明确支持、否定性缺失、无关键词重叠、矛盾/异常来源和旧记录默认值。
- 接入主链路后运行后端全量测试。
- 前端补充状态文案测试和审查页服务型 E2E。
- 最终运行质量门禁、迁移冒烟和 `git diff --check`。
