## 2. 审查范围与结论边界

当前审查覆盖以下链路：

```text
权威法源/业务知识导入
  -> 文本清洗与结构化切片
  -> Embedding 生成与索引修订
  -> 作用域和时效过滤
  -> 精确条号路由 / BM25 / 向量召回
  -> RRF 融合 / 可选 Cross-Encoder
  -> Claim 查询规划与受控改写
  -> 证据支持关系验证
  -> 风险决策、证据持久化与前端追问
  -> 离线评测与质量门
```

已验证的事实：

- 项目存在真实 RAG 模块，不是仅将知识文本拼入提示词的“伪 RAG”。
- 法源导入、切片、混合召回、检索轨迹和证据持久化均有专项实现。
- 2026-09-29 运行 15 个 RAG/法源/证据专项测试文件，共 `151 passed`、`0 failed`、`1 warning`。
- 已用最小动态反例复现 RAG-001、RAG-002 和 RAG-003。

尚未验证的边界：

- 没有双人复核并冻结的真实检索金标，因此不能声称 Recall@K、Precision@K、MRR 或 nDCG 达标。
- 没有真实证据支持关系金标，因此不能声称三分类 Macro F1 或自动采信准确率达标。
- 没有在 PostgreSQL/pgvector、真实 Cross-Encoder、生产并发和真实合同规模下完成性能实测。

## 3. 优先级与状态定义

### 3.1 优先级

| 优先级 | 定义 |
|---|---|
| P1 | 可能导致错误法律依据、错误自动采信、数据越权或生产阻断，必须在上线前解决 |
| P2 | 明显影响召回质量、评测可信度、扩展性或核心用户体验，应在本轮集中改进 |
| P3 | 工程质量、可观测性或长期维护问题，可在核心风险解决后优化 |

### 3.2 状态

```text
待确认 -> 已复现 -> 方案确定 -> 待实施 -> 已实施 -> 已验证
```

补充状态：

- `暂缓`：问题成立，但当前批次明确不实施，必须记录原因和重新评估条件。
- `不处理`：经过评审确认不需要修改，必须保留决策依据。
- `重新打开`：关闭后出现回归或新证据。
- `部分实施`：仅完成明确子范围，未完成的验收条件仍保留，不等于整个问题关闭。

## 5. 问题详情

本节保留排查时的现象、状态和反例作为历史证据；当前实施状态以第 4 节、第 15 节为准。

### RAG-001 普通知识的可检索作用域被错误等同于来源可信

| 字段 | 内容 |
|---|---|
| 优先级 | P1 |
| 状态 | 已复现 |
| 责任域 | 知识治理、检索结果模型、证据验证 |
| 相关文件 | `backend/app/schemas/contract.py`、`backend/app/api/v1/endpoints/knowledge.py`、`backend/app/services/rag/retriever.py`、`backend/app/services/audit/evidence_validation.py` |

**现象**

普通知识导入默认使用 `scope_mode="global"`。检索结果随后仅根据 `scope_mode in {global, scoped}` 设置 `reliable=True`。这把两个不同概念混在了一起：

- `scope_mode` 只回答“该知识可用于哪些合同或维度”；
- `reliable` 应回答“该来源是否经过授权、校验和审批”。

**动态复现证据**

构造普通上传来源 `普通用户上传.txt`，内容为“违约金为合同金额50%，该比例绝不过高且无需调整”。系统输出：

```text
reliable=True
status=supported
reason_code=EVIDENCE_SUPPORTS_CLAIM
```

**根因**

`KnowledgeChunk` 没有独立的来源信任状态、审批状态和可信来源引用。普通上传与经过 manifest、官方域名、SHA-256、条数校验的权威法源最终共用同一 `reliable` 推导逻辑。

**推荐改进**

1. 在知识模型中新增独立的来源治理字段，例如：
   - `trust_status`: `unverified / approved_internal / authoritative / rejected`
   - `provenance_type`: `official_legal_source / approved_rule / template / user_upload`
   - `approved_by`、`approved_at`、`approval_version`
2. `scope_mode` 仅参与适用范围过滤，不再决定可信度。
3. `reliable` 改为服务端根据来源治理记录、完整性、适用性和审批状态计算，不接受导入请求直接指定。
4. 普通上传默认 `unverified`，可以参与搜索预览，但不得支撑自动采信。
5. 权威法源必须能追溯到 `LegalSource.source_id`；企业规则必须经过审批工作流。

**验收标准**

- 普通 `legal` 用户上传的 `global` 内容检索结果仍为 `reliable=False`。
- 未审批来源只能让 Claim 进入 `manual_review`，不能进入 `accepted`。
- 权威法源和已审批企业规则可通过来源可信门禁。
- 对信任状态升级、降级和撤销均有审计日志。
- 新增 API、服务层、迁移和端到端回归测试。

### RAG-002 语义支持验证缺席时仍返回 supported

| 字段 | 内容 |
|---|---|
| 优先级 | P1 |
| 状态 | 已复现 |
| 责任域 | 证据支持关系、风险决策 |
| 相关文件 | `backend/app/services/audit/evidence_validation.py`、`backend/app/services/audit/auditor.py`、`backend/app/services/audit/decision.py` |

**现象**

`verify_support()` 的 `semantic_verifier` 是可选参数，生产调用没有注入验证器。当前逻辑只要原文已定位、来源被标记为可信、时效可用，并且风险文本与来源存在至少两个中文二元片段重叠，就返回 `supported` 和“五层证据支持校验通过”。

该规则只能证明词面重叠，不能证明来源支持 Claim，更不能识别否定、例外、条件不满足和法律后果相反。

**根因**

- 语义关系门禁被设计成可选增强项，而决策层把缺少语义验证的结果当成完整通过。
- `facts` 阶段把多个来源拼成一个字符串，词面片段可能来自不同来源。
- 返回文案和实际执行的门禁数量不一致。

**推荐改进**

1. 改为 fail-closed：没有启用且验证通过的语义判断器时，最高只能返回 `unclear`。
2. 语义验证输入采用结构化 Claim 与单条候选证据，不使用任意拼接文本。
3. 明确输出 `supported / contradicted / unclear`，并返回可审计的主体、行为、条件、例外和法律后果对齐结果。
4. 先用专家金标验证语义判断器，再允许其参与自动采信。
5. 删除“五层通过”等与实际门禁不一致的描述，改为记录每一层真实状态。

**验收标准**

- 未配置语义判断器时，任何 Claim 都不能仅凭词面重叠自动进入 `accepted`。
- 明确否定 Claim 的证据返回 `contradicted`。
- 条件或适用主体不一致的证据返回 `unclear` 或 `contradicted`。
- 真实双人复核金标报告 Macro F1、各类别 Precision/Recall 和混淆矩阵。
- 决策层测试证明 `contradicted` 必须拒绝，`unclear` 必须人工复核。

### RAG-003 精确条号检索未绑定法源身份

| 字段 | 内容 |
|---|---|
| 优先级 | P1 |
| 状态 | 已复现 |
| 责任域 | 查询解析、精确检索 |
| 相关文件 | `backend/app/services/rag/query_planner.py`、`backend/app/services/rag/retriever.py`、`backend/resources/legal_sources/manifest.json` |

**现象**

精确检索只解析并比较 `article_number`。多个法源存在相同条号时，候选按父记录、切片序号和数据库 ID 排序后取第一条，没有校验查询中出现的法规名称。

**动态复现证据**

在同时存在《中华人民共和国民法典》和《民法典合同编通则解释》第十条的条件下，查询：

```text
《合同编通则解释》第十条
```

实际返回《中华人民共和国民法典》第十条。

**根因**

精确路由键只有条号，没有 `source_id` 或规范化法源别名；查询规划器虽然能提取包含书名的字符串，但底层检索丢失了书名信息。

**推荐改进**

1. 查询规划器输出结构化 `LegalReference(source_name, source_id, article_number)`。
2. 建立受控法源名称和别名表，解析后映射到唯一 `source_id`。
3. 精确检索使用 `(source_id, article_number)` 联合键。
4. 查询只给条号且存在多个法源候选时，不允许静默取第一条：
   - 审查链路回退到语义检索并标记歧义；
   - 面向用户的查询链路返回候选法源供选择。
5. 检索轨迹记录解析到的法源、条号和歧义状态。

**验收标准**

- 覆盖至少两个法源相同条号的交叉测试矩阵。
- 指定法规名称时只返回对应法源。
- 仅提供条号且候选不唯一时不进入 `exact` 单结果短路。
- 法规简称、全称和书名号差异可稳定映射。

### RAG-004 多路、多轮检索结果合并后整体校验

| 字段 | 内容 |
|---|---|
| 优先级 | P1 |
| 状态 | 已复现 |
| 责任域 | 查询执行、证据选择、证据绑定 |
| 相关文件 | `backend/app/services/rag/query_executor.py`、`backend/app/services/audit/auditor.py`、`backend/tests/test_rag_grounding.py` |

**现象**

查询执行器把首轮多路查询和一次改写检索的结果累积到 `merged`，然后将全部结果一起送入支持关系校验。最终 `rag_sources` 又保留全部标记为可信的来源，而不是只保留真正支持该 Claim 的来源。

现有测试固定了如下行为：第一轮返回“合同应采用书面形式”的无关规则，改写后返回正确违约金法条，最终两者都进入同一风险的 `rag_sources`。

**根因**

- 缺少“逐证据判定”和“最终证据选择”两个独立阶段。
- 验证器接收的是来源集合，允许关键词片段跨来源拼接。
- 查询改写成功后没有淘汰首轮失败证据。

**推荐改进**

1. 每条候选来源独立运行权威性、适用性和语义关系验证。
2. 保存 `supporting / contradicting / contextual / rejected` 四类证据关系。
3. 只有 `supporting` 证据进入 `basis` 和 `evidence_ids`。
4. 首轮失败、改写成功时保留完整检索轨迹，但不把失败候选写入正式依据。
5. Claim 的最终状态由最小充分证据集决定，禁止跨来源拼接片段形成支持关系。

**验收标准**

- 无关来源可以出现在 `retrieval_attempts`，但不能出现在正式 `rag_sources`。
- 每个 `evidence_id` 都有该 Claim 专属的关系判定记录。
- 跨 Claim 或跨来源拼接支持数量为零。
- 改写后命中正确证据时，首轮无关证据不会污染 `basis`。

### RAG-005 缺少真实检索金标与自动预测流水线

| 字段 | 内容 |
|---|---|
| 优先级 | P2 |
| 状态 | 已确认 |
| 责任域 | 离线评测、质量门 |
| 相关文件 | `backend/evaluation/retrieval_metrics.py`、`backend/evaluation/cli.py`、`docs/evaluation/rag-retrieval-protocol.md`、`scripts/quality_gate.py` |

**现象**

项目已实现 Recall@K、Precision@K、MRR 和 nDCG@K 计算器，也规定了评测协议，但仓库没有真实金标和真实预测产物。当前 CLI 只读取外部提供的预测文件，没有从当前 `retrieve()`、当前知识版本和当前配置自动生成预测的 runner，也没有接入完整质量门。

**根因**

指标计算、预测生成和发布门禁仍是三个分离环节，缺少可重复执行的端到端评测流水线。

**推荐改进**

1. 建立脱敏、双人复核、版本冻结的查询-依据金标。
2. 新增预测 runner，记录代码版本、知识库修订号、模型、阈值、召回模式和 reranker 配置。
3. 固定运行四组消融：BM25、向量、RRF、RRF + Cross-Encoder。
4. 在质量门中加入基线对比和退化阈值，不只检查绝对 Recall。
5. 分层报告：精确条号、同义表达、OCR 错字、缺失条款、跨条款和难负样本。

**验收标准**

- 一条命令可从金标生成预测、计算指标并输出可审计报告。
- 缺失预测按零分计算，不能过滤失败案例。
- 知识、模型或检索配置变化会生成新的评测身份。
- 质量门能阻止 Recall、MRR、nDCG 或难负样本精度显著退化。

### RAG-006 风险追问接口信任客户端提交的风险上下文

| 字段 | 内容 |
|---|---|
| 优先级 | P2 |
| 状态 | 已确认 |
| 责任域 | 追问 API、数据授权、引用溯源 |
| 相关文件 | `backend/app/api/v1/endpoints/chat.py` |

**现象**

风险追问接口由客户端提交 `category`、`original_text`、`basis`、`suggestion` 和 `confidence`，服务端直接写入 system prompt。接口没有根据 `risk_id` 从数据库重新加载风险，也没有验证当前用户对所属合同的访问权限，更没有按追问内容重新执行 RAG。

因此客户端可以伪造“法规依据”或风险上下文；即使响应内容语言流畅，也不具备服务端证据可追溯性。

**推荐改进**

1. 请求只提交 `risk_id`、问题和受限历史 ID，不接受客户端提交正式依据。
2. 服务端加载 Risk、合同、证据关系和当前用户权限。
3. 追问按风险 Claim 与问题生成独立检索计划，复用可信来源和适用性门禁。
4. 返回结构化引用和检索轨迹，明确区分历史审查依据与本次追问新增依据。
5. 对历史消息执行服务端持久化或签名，避免客户端任意改写上下文。

**验收标准**

- 修改客户端 `basis` 不再影响模型 system prompt。
- 无合同访问权限的用户请求返回 403。
- 回复中的引用可以追溯到服务端 Evidence ID。
- RAG 不可用时明确降级，不生成伪造法律引用。

### RAG-007 默认无真实精排且检索仍受内存全量计算限制

| 字段 | 内容 |
|---|---|
| 优先级 | P3 |
| 状态 | 已确认 |
| 责任域 | 排序、索引架构、性能 |
| 相关文件 | `backend/app/core/config.py`、`backend/app/services/rag/retriever.py`、`backend/app/services/rag/reranker.py` |

**现象**

- 默认 `RERANK_BACKEND=disabled`，所谓 `deterministic_evidence_v1` 只记录覆盖度分数，实际保持 RRF 顺序。
- 检索快照已经避免每次重复解析全部向量，但仍将所有文档和向量加载到进程内，通过 NumPy 做全量余弦计算。
- 多进程部署时每个进程持有独立快照和模型，数据量扩大后会增加内存和重建成本。

**推荐改进**

1. 先完成 RAG-005 金标评测，再决定是否启用本地 Cross-Encoder，不凭经验直接改阈值。
2. 对 Cross-Encoder 做模型来源、安全和许可证审计，并验证延迟预算。
3. 中期在 PostgreSQL 使用 pgvector/HNSW 或经过验证的向量服务，SQL 层先做作用域过滤再执行 ANN。
4. 保留 BM25 与向量两路召回和 RRF，不把 ANN 替换误写成质量必然提升。
5. 增加快照大小、构建耗时、查询 P50/P95、候选数、降级率和内存占用指标。

**验收标准**

- 在同一金标上提供无精排和真实精排的消融结果。
- 在目标知识规模和并发下满足明确的 P95 延迟与内存预算。
- 向量索引不可用时继续安全降级到 BM25，并在结果中如实标记。

| 验收标准 | 审查员在列表首屏可判断风险来源、证据状态和是否阻断；列表与详情/报告的 Evidence ID 集合一致。 |
| 依赖与风险 | 依赖 RAG-001 至 RAG-004 的证据治理；字段过多可能增加首屏密度，需要响应式折叠但不能隐藏阻断状态。 |

### UX-008 AI 数值建议缺少来源和适用条件

| 字段 | 内容 |
|---|---|
| 优先级 | P2 |
| 状态 | 已复现，方案确定，待实施 |
| 责任域 | 建议生成、法源核验、企业规则配置 |
| 现象 | AI 建议中出现 `0.05%`、`10%`、`15/30 日` 等数值，列表层没有明确说明是法规、企业配置还是谈判示例。 |
| 根因假设 | 建议文本允许自由生成，数值没有结构化来源、适用条件和核验状态。 |

| 兼容与迁移 | 历史自由文本数值标为 `legacy_unstructured`，不得自动升级为已核验；企业配置迁移需版本化并保留生效时间。 |

| 验收标准 | 每个数值都有来源类型和核验状态；未核验数值不会进入“确定结论”；人工确认有审计记录并可追溯到版本。 |
| 依赖与风险 | 依赖真实法源金标和企业规则审批；复杂条件不能被简单正则误判，需保留原文和人工复核入口。 |

## 14. 多维报表产品改进方案（产品经理 + 研发工程师）

本节是目标方案。本轮仅交付同一授权快照内的当前运营指标、部门分母、合同下钻和整改入口；金额治理、历史趋势、AI 摘要及新版报告排版仍为后续范围。

### 14.1 产品定位与改进目标

现有“多维报表”已经具备合同选择、风险聚合、证据查看和 Excel/Word 导出能力，但实际更接近“合同审查证据报告生成器”，无法完整支撑管理层比较经营风险、部门负责人接收任务和法务/财务完成复核。

本次改造采用“双层报表”定位：

```text
管理总览（一屏决策）
  -> 风险热力地图（定位异常）
  -> 合同清单（筛选与比较）
  -> 合同详情 / 风险证据（判断）
  -> 整改任务 / 待办行动（执行与闭环）
```

目标不是增加图表数量，而是让每个聚合指标都能回到合同、证据和责任人，并保证页面、导出文件和审查结果使用同一数据口径。

### 14.3 首屏产品方案：管理总览

首屏固定为“范围栏 + 四个 KPI + 热力地图 + AI 摘要 + 待办行动”，不再把逐条证据明细放在首屏。

#### 四个核心 KPI

| KPI | 定义 | 必须显示 |
|---|---|---|
| 合同金额敞口 | 当前筛选范围内、金额已标准化且通过最低置信度门槛的合同金额合计 | 金额、币种、纳入合同数、缺失金额数、环比 |
| 重大风险合同 | 至少存在一条高风险且证据状态允许进入管理汇总的合同 | 合同数、金额占比、未复核数、证据不足数 |
| 近 30 天到期 | 付款、履约、续签、终止等节点在未来 30 天内到期的节点 | 节点数、涉及合同数、责任部门、最早日期 |
| 逾期整改 | 截止日期早于当前日期且状态未关闭的整改任务 | 任务数、涉及合同数、最长逾期天数、责任人 |

所有 KPI 都必须显示统计时间范围、数据更新时间和口径说明。缺失、失败、未复核数据不得静默混入汇总。

#### 风险热力地图

默认维度为“部门 × 风险等级”，单元格主值显示金额敞口，辅助值显示合同数/风险条数/整改项数。用户可以切换第二维度：

- 风险等级：高、中、低；
- 整改状态：未分派、进行中、逾期、已关闭；
- 金额区间：按企业配置的金额档位；
- 合同类型：采购、销售、服务、软件等。

点击单元格必须把部门、风险等级、金额区间、整改状态和时间范围带入合同清单；合同清单再进入合同详情、证据链和整改任务。颜色不是唯一编码，必须同时显示数字和文字状态。

#### AI 管理摘要

AI 只解释当前报表快照，不生成新的法律结论。输出契约固定为：

```text
结论 -> 变化幅度 -> 影响范围 -> 数据依据 -> 建议动作
```

示例：

> 采购中心重大风险金额较上期上升 12%，涉及 3 份合同、5 个高风险条款，其中 2 份尚未完成人工复核。建议优先处理金额最高的合同 C-103，并在 10 月 8 日前完成复核。

每条摘要返回 `metric_ids`、`contract_ids`、`risk_ids`、`as_of`、`data_scope` 和 `confidence`。没有可靠数据时返回“无法判断”，不得把“无高风险”表述为“合规确认”。

### 14.4 角色化页面和权限

| 角色 | 默认视图 | 重点信息 | 允许操作 |
|---|---|---|---|
| 管理层 | 管理总览 | 金额敞口、重大风险、到期节点、逾期整改、部门趋势 | 查看授权聚合、下钻合同清单、导出脱敏摘要 |
| 部门负责人 | 部门执行台 | 本部门合同、责任人、截止日、整改状态 | 分派负责人、调整截止日、批量导出本部门台账 |
| 法务人员 | 风险复核台 | 高风险条款、法规依据、原文定位、复核状态 | 确认/忽略/修改风险，补充复核意见 |
| 财务人员 | 付款与金额台 | 金额、币种、付款节点、发票/税务风险 | 校验金额和付款口径，标记待确认节点 |

聚合视图默认脱敏，进入合同详情前再次校验权限。前端按钮状态不得作为权限依据；服务端能力接口必须返回 `can_view`、`can_export`、`can_assign`、`can_review` 及拒绝原因码。

### 14.5 数据模型和口径改造

#### 合同金额

在现有合同要素之外增加结构化字段：

```text
amount_value: Decimal | null
currency: CNY / USD / EUR / OTHER
amount_basis: fixed_total / unit_price / estimated / framework / unknown
tax_included: true / false / unknown
amount_confidence: high / medium / low / unknown
amount_source_evidence_id: string | null
```

金额无法标准化时保留 `amount_raw`，但不进入金额敞口汇总；跨币种汇总必须使用明确汇率日期和汇率来源，否则只展示分币种结果。

#### 履约和付款节点

不要继续把付款节点作为一段原文字符串展示。新增节点实体，至少包含：

```text
contract_id, event_type, due_date, condition, percentage,
base_amount, currency, status, source_evidence_id, confidence
```

#### 历史指标快照

新增 `report_metric_snapshot` 或等价事实表，按组织、部门、时间粒度和口径版本保存 KPI。快照必须记录：

- `snapshot_id`、`as_of`、`period_start`、`period_end`；
- `metric_version`、`data_scope`、`knowledge_version`；
- 合同数、金额敞口、风险数、整改数及缺失/未复核计数。

没有历史快照时，趋势组件必须显示“历史数据不足”，不能使用固定档位标签伪装成真实趋势。

#### 风险与整改关联

主风险、证据和整改任务必须使用稳定 ID 关联。报表统计默认按 `risk_cluster_id` 去重；来源命中数作为辅助指标，不得重复计入主风险数。

| `GET /reports/actions` | 返回到期节点、逾期整改和责任人待办 |
| `POST /reports/summary-explanation` | 基于快照 ID 生成结构化 AI 摘要，不接受客户端提交的指标值 |
| `GET /reports/export` | 接受快照 ID 和筛选条件，导出页面同口径数据并记录审计日志 |

所有接口返回 `schema_version`、`report_id`、`as_of`、`data_scope` 和 `warnings`。前端不再自行计算正式 KPI、部门排行和趋势；`computed` 只负责格式化接口结果。

#### 前端模块拆分

- `ReportScopeBar`：时间、部门、类型、金额、相对方和权限范围；
- `ReportKpiGrid`：四个 KPI、环比、缺失提示和下钻；
- `RiskHeatmap`：热力地图、图例、无障碍等价表和单元格下钻；
- `ManagementSummary`：AI 摘要、依据和刷新状态；
- `ActionQueue`：到期、逾期、责任人和快捷处理；
- `ContractDrilldownTable`：合同清单、列配置、排序、分页和导出；
- `EvidenceDrawer`：原文定位、依据状态、Evidence ID 和复核动作。

### 14.7 导出改造

Excel 仍作为可操作台账，Word 改为管理汇报件，二者不再使用同一个“证据报告”定位。

**Excel：**

- `管理摘要`：四个 KPI、筛选条件、数据更新时间、口径和警告；
- `合同清单`：标准金额、币种、部门、风险、到期和整改状态；
- `风险台账`：主风险、证据 ID、复核状态和责任人；
- `付款节点`：结构化日期、比例、基数和来源定位；
- `整改跟踪`：负责人、截止日、逾期天数、状态和备注；
- `口径说明`：字段定义、排除规则、版本和脱敏说明。

Excel 应使用正式表格对象、冻结表头、筛选、日期/金额格式和必要的数据验证；空的整改表必须说明“当前范围无任务”而不是只输出表头。长文本仍可分段，但必须保留主风险 ID 和证据 ID，避免人工无法归并。

**Word：**

1. 一页决策摘要；
2. 部门/金额/风险热力摘要；
3. 到期与逾期整改行动清单；
4. 重大合同清单；
5. 证据附录和逐项风险明细。

Word 首页不放 44 条风险全文；完整证据放附录，正文只保留重大风险和行动建议。报告标题、文件名和页面口径统一使用“合同风险运营报告”，需要证据留档时另命名为“合同审查证据附录”。

## 16. 2026-09-29 Agent 工作流增量

本轮没有引入 LangGraph、Dify 或新的编排基础设施，复用现有 Python 状态机、窗口检查点、任务代次和人工复核权限：

- `workflow-v1` 为每次审查记录合同正文指纹、知识修订号、规则/提示词源码指纹、模型配置和预算；提示词、正文或知识变化后窗口检查点不复用。
- 法务和财务观点按“同类别 + 同原文”保守归并为主风险，保留各 Agent 的 claim、等级、建议和证据视图；不同类别不做猜测式合并。
- 规则冲突产生定向复查任务，由目标 Agent 只能引用授权候选和合同原文；输出不完整、引用越界、预算耗尽或模型失败均转人工，不提升证据状态。
- 新增工作流快照和终审接口。终审要求风险逐项处理、冲突逐项裁决、解析质量问题有说明，并通过代次、版本和快照指纹并发校验；终审不会清除机器或 OCR 复核标记。
- 协同页展示主风险、定向复查、预算和终审状态；最终发布仍由法务或管理员执行。

收尾补强：窗口唯一约束包含运行指纹，保留维度哈希原有含义；指纹同时绑定固定提示词和动态合同要素/参考资料输入。SQLite 旧库补列及约束升级保留历史检查点，支持重复执行。定向复查要求每条候选都能定位原文，不能用部分候选的原文替整组候选背书。人工风险状态不变但意见更新时，旧终审也会失效。

本轮收尾专项证据：后端工作流、终审、检查点迁移、二次复核、授权及既有审查回归合计 170 项通过；前端 Playwright 12 项通过，覆盖终审发布、取消质量说明、未处理风险阻断、失败重试、历史快照空状态及 390×844 窄屏。浏览器使用接口桩，不代表真实模型与真实合同端到端验收。Alembic 单头为 `20260929_04`；生产 PostgreSQL 迁移未实测。

预算边界：`AUDIT_MAX_MODEL_CALLS` 和 `AUDIT_MAX_TOKEN_BUDGET` 限制一次 `audit_contract()` 执行内的审查 chat 调用；预算为输入 UTF-8 字节数加输出上限的保守估算，与供应商实际用量取较大值，不是精确费用。检索 embedding、解析及任务重试之间的累计费用不在此额度中。`AUDIT_DIRECTED_MAX_CALLS` 限制定向复查次数，设为 0 时直接保留人工待办。当前只有一轮定向复查，未引入自由循环的 Agent 编排。

业务发布边界：人工终审是绑定审查快照的业务记录，不代表模型证据已获得验证，也不会自动清除 OCR/机器复核标记。真实语义模型、专家金标、跨进程预算累计和生产数据库并发仍需后续验收。
