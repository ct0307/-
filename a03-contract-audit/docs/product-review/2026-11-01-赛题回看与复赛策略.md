# 契鉴：原始赛题回看与复赛产品策略

产品经理分析稿｜2026年11月1日｜依据A03原题与当前本地证据

分析范围：用户所附截图；本地赛题手册A03完整页（PDF物理第16页、印刷第11页）；项目代码、历史验收与2026年10月31日对照材料。原题作为需求来源，其中技术描述不当作已验证事实。本文的优先级、测试方法、样本建议和演示时长属于产品建议，不是官方评分规则。[S01]

用户已确认：复赛前无法取得指定OpenClaw一体机，只能展示适配与已有测试。因此，指定硬件运行及能效指标仍有实质缺口；无法自行宣布替代达标或豁免。本稿不实施新功能，也不改动业务代码。

## 1. 先重新定义：契鉴究竟交付什么

赛题同时提出两个业务结果：减少人工审查中的遗漏，以及把金额、期限、违约责任等合同内容转成管理决策可用的结构化信息。仅能“上传合同、生成风险列表”还没有完整回应题目；报表也不能只停在风险等级饼图。[S01]

建议产品定位：**契鉴面向企业合同审查，把合同转成法务可复核的风险、财务可核对的履约信息，以及管理者可跟进的待办和报表。** 指定OpenClaw设备是原题要求的计算平台，当前仅完成通用协议层面的适配准备。

产品验收应沿同一条数据链展开：合同原文→关键要素→法务与财务检查→冲突及证据状态→人工决定→结构化报表。每一步都要能回查前一步，不能出现页面上判为失败、报表却显示已完成，或看板和导出统计范围不同。

三类用户各有一个应被回答的问题：法务关心“哪里有问题、依据和建议是什么”；财务关心“金额、条件、节点是否一致，哪些尚不能确认”；管理者关心“哪些合同和整改需要先处理、由谁处理”。外部实付、发票、预算等数据未接入时，只能分析合同约定，不能宣称完成了真实账务对账。

## 2. 赛题基本要求：必须完成什么，怎样才算有证据

P1表示原题明确要求或演示成立的必要条件；P2表示增强可信度与使用价值；P3表示后续扩展。这里的P1是团队工作优先级，不代表官方扣分或淘汰规则。

| 优先级 | 原题要求 | 最小可验收结果 | 主要证据 |
|---|---|---|---|
| P1 | 指定OpenClaw一体机开发与运行 | 指定设备实际承载相应任务，说明模型、运行路径和配置 | 设备记录、部署记录、真实调用及输出；目前缺失 |
| P1 | PDF、Word合同解析 | 两类文件可进入同一后续审查流程，结构、表格与来源可核对 | 样本清单、解析结果、后续审查记录 |
| P1 | 漏项识别 | 按合同类型与交易背景识别应有信息缺失，并说明待补内容 | 问题样本、无问题对照、人工裁决 |
| P1 | 逻辑矛盾识别 | 能指出相互冲突的原文及冲突条件，而非泛泛提示 | 两处或多处原文、核算过程、处理建议 |
| P1 | 民法典相关风险与修改建议 | 指出问题、依据与适用条件，建议可执行且需人工核验 | 原文、法源版本、理由、修改建议 |
| P1 | 法务与财务Agent协作 | 职责有区分，能够交接事实、复核联动问题并保留分歧 | 同一案例的两侧输出、交接及复核记录 |
| P1 | 元数据与Excel或看板 | 甲方、标的、收付款节点等可用，结果进入报表 | 原文与字段对照、报表回读和统计范围 |
| P1 | 关键要素提取准确率≥90% | 固定字段与计分口径，独立标注测试集上报告结果 | 冻结真值、预测、逐字段结果和失败分析 |
| P1 | 一次上传50份以上、支持批处理 | 一次提交达到数量要求，后续任务状态与结果可核查 | 单请求记录、逐文件状态、失败与重试记录 |
| P1 | 显著优于传统GPU的能效比 | 可比质量与任务条件下比较真实能量消耗及有效产出 | 两设备功率时序、任务结果、重复试验统计 |

### 2.1 六个容易误读的地方

**90%约束的是关键要素提取，不是整体法律审查正确率。** OCR字符准确率、引用定位率、风险召回率也各自独立。测试工具通过或风险条数多，都不能替代90%的业务结果。[S01][S02]

**原题要求的是能效优势，不只是速度优势。** 延迟更低不必然耗能更少；API兼容、CPU本地运行、普通模型调用都不能证明类脑芯片加速。原题没有规定节能倍数或“显著”的统计门槛，应向命题方确认。[S01]

**原题写的是Excel“或”可视化看板。** 两者都做有交付价值，但不必为展示更多形式牺牲字段质量和正常流程。现有Excel和Word导出可以保留，复赛主讲重点应是报表回答的业务问题。

**漏项、矛盾、疑似违法应分别处理。** 未约定争议解决或某项商业保护，并不当然违法；付款比例相加异常，需要先确认是否同一计价基数、独立分期，排除违约金、重复表述及可选方案。商业不利也不自动等于民法典禁止事项。

**财务Agent必须有可验证任务，但原题未强制接ERP、银行和真实发票。** 可先做合同内金额、币种、付款条件、比例及收款主体一致性核验；涉及真实付款、预算或价格公允性的结论必须依赖外部数据。

**扫描件OCR、权限、审计、私有化部署属于重要产品支撑。** 原题并未给出OCR准确率、指定数据库或容器部署的独立量化门槛。若团队已经承诺支持这些能力，则应兑现；它们也不能取代三项明确技术指标。长合同处理来自原题背景，需要有跨页或跨窗口案例，但不能自行添加官方页数、时限。

### 3.1 双Agent实验应怎样影响产品决策

10月31日有20份合成测试合同、三组各3次重复；S1为通用单轮，S2为通用两轮，D2为法财独立首审。300次请求中294成功、6超时。随后同一被测模型参与AI角色模拟标注及裁决；它不具备独立专家金标的地位。[S06]

AI参考覆盖观察值为S1 61.0%、S2 65.3%、D2 59.4%；分母372是124项AI参考在3次重复下的实例数，不是372份合同。该观察没有显示D2整体覆盖优势，但也不足以断言真实法律效果优劣；正式人工Precision、Recall和F1仍未测量。[S06]

产品含义是：保留赛题要求的法财分工，停止把“两个角色”本身包装成“更准确”。将注意力转到职责是否漏项、交接事实是否有用、分歧是否合理，以及人工是否更容易核验。现有对照未覆盖完整交叉复核链，不能据此证明或否定完整链路收益。

## 4. 不取得指定硬件时，怎样处理硬缺口

这是原题符合性风险，不能通过更换宣传语把它消除。建议准备一页能力边界：协议适配和软件测试已有证据；指定设备部署、类脑加速、低延迟协同收益及能效对照均未验收。[S01][S07]

需要由团队向组委会或命题方确认三件事：是否有统一设备或远程接入机会；复赛是否允许以适配方案和替代环境展示；替代验收需要什么材料及能效比较口径。保留书面答复。在取得正式口径前，不能推断这项要求不再影响评审，也不能推断必然取消资格。本次只提出确认事项，不代发消息。

建议答辩表述：**“我们完成了兼容协议适配和软件侧验证，但复赛前未获得指定OpenClaw设备，因此本次不报告指定设备性能或能效达标结果。现场展示来自已注明的测试环境，硬件验收项单独列明。”** 通用API兼容仍需目标设备联调，不能直接说设备可交付。[S07]

若以后获得设备，建议以“相同质量门槛下每个合格完成任务的能耗”衡量：每任务能耗＝完整测量窗口总能量÷合格完成任务数；能效＝合格完成任务数÷总能量。失败和重试消耗包含在分子中，不能只挑成功调用的功耗。

比较需说明模型与量化、数据、提示词、输出长度、并发、预热、测量边界和重复次数。优先比较整机能耗；若只能测芯片或板卡，两侧口径必须一致并明确局限。同模型不可得时，只能按同一业务质量门槛比较系统方案，不能把差异全归因于芯片。P50/P95、吞吐与成功率是辅助指标，不能取代功率积分。[S07]

## 5. 答辩演示：用同一个合同解释完整价值

建议以一份采购或服务合同贯穿法务、财务和报表，另用少量辅助样本补足三类审查。避免在多个合同间跳转，造成风险、统计和报表不是同一对象。所有演示样本都须明确为合成或经授权脱敏数据。

### 5.1 演示案例应具备的条件

主案例宜有金额、清晰付款分期、验收触发条件和可定位的跨条款矛盾。例如正文约定验收后付款、附件却给出先付款条件，法务判断义务安排，财务核对节点与适用范围；只有确认两处针对同一笔款项、条件不兼容，才能标为冲突。

如果使用“60%+50%+10%=120%”示例，三笔必须明确属于同一合同总价的独立分期，不包含违约金或备选路径。它适合作为可复算的确定性检查，不能仅靠相加结果宣称法律违法。补一个30%+60%+10%=100%的无问题对照，检验系统不会机械报错。

法律风险辅助样本可采用表述清楚的疑似违法免责条款，展示原文、对应法源、适用限制与建议。法源是否适用仍需人工专业判断。漏项样本则应展示“缺什么、为何需要、怎样补”，不要伪造不存在条款的原文位置。

长合同补充案例应把关联条款放在正文与附件或相距较远的章节，检查两处来源、审查覆盖和结果一致性；不要只用一页短合同证明长文档能力。此案例应先实际彩排，再纳入主讲。

### 5.2 建议6分钟演示顺序

以下时长为策划示例，拿到正式赛制后按比例压缩。

| 时段 | 展示动作 | 评委应看到的结果 |
|---|---|---|
| 0:00—0:30 | 说明企业审查与汇总痛点，上传主合同 | 任务对象、数据来源和测试环境明确 |
| 0:30—1:15 | 查看解析与六要素，回查原文 | 字段有来源，缺失和待确认状态可见 |
| 1:15—2:15 | 展示三类问题中的代表项 | 漏项、矛盾、疑似违法没有混为一谈 |
| 2:15—3:15 | 展示一个法财联动问题 | 角色贡献、核算事实、交接和分歧可查 |
| 3:15—4:15 | 打开证据并人工复核 | 原文、依据、建议、状态和处理理由连贯 |
| 4:15—5:15 | 切换看板并导出Excel | 谁先处理什么，合同字段和整改与原结果一致 |
| 5:15—6:00 | 展示批次证据与指标卡 | 样本、版本、分母和硬件缺项一目了然 |

模型等待较长时，可先讲解已完成的同版本审查记录，再回到当前任务。历史结果、录屏、现场实时调用必须分别标注。不能把预置演示数据伪装成刚刚生成的结果。

### 5.3 报表必须回答的问题

法务视角：哪些高风险条目还未确认、依据缺在哪、应由谁核验。财务视角：哪些金额与付款节点已提取、来源是否可靠、哪些条件尚不能确定。管理视角：哪些合同需优先处理、整改是否逾期、责任人和统计日期是什么。

可以展示合同总价原文、履行期限和违约责任关联项；未归一币种、计价基数或未核验的金额，不应直接相加成风险敞口。合同约定付款日不是实际付款日，整改逾期不是账款逾期。缺少实际履约数据时，不要画“实际现金流”或真实应收应付余额。[S08]

现有运营报表已明确拒绝未核验金额汇总，且提示跨Agent风险尚未完成人工归并。继续沿用这些边界，不能把原始风险记录条数说成独立问题数或合同数。[S08]

## 6. 创新：在赛题动作之上，找到有机制、有价值的差异

PDF/Word导入、双Agent、元数据和报表已是原题明确要求；RAG也是常见技术路线。可以讲技术选型，但仅报这些名词不足以证明创新。真正值得主讲的是：为什么这样组织工作、解决了什么具体难题、效果能否独立验证。

建议比较三条准备路线：继续扩展全生命周期平台会增加范围和不稳定性；聚焦模型或芯片优化目前缺设备与效果证据；**围绕现有功能深化可信审查与法财联动，最符合当前复赛条件。** 第三条应作为主路线，平台扩展与硬件优化保留为后续计划。

| 优先级 | 候选创新 | 当前基础 | 需要证明的价值 |
|---|---|---|---|
| P1 | 法财联合的履约一致性核验 | 职责分离、结构化交接、确定性财务检查已有机制 | 联动问题是否被正确发现，人工核验是否更快 |
| P1 | 带核验状态的风险证据卡 | 原文、依据标识、决策与人工记录已有基础 | 来源定位和缺证识别是否方便，错误引用能否暴露 |
| P2 | 从审查结果到管理待办的可追溯报表 | 同范围快照、整改与报告机制已有基础 | 字段和统计是否一致，管理者能否据此安排工作 |
| P2 | 按证据缺口指导补充材料 | 可利用当前待复核状态，完整效果待设计验证 | 是否减少无效追问与一次复核所需操作 |
| P3 | 增量再审、行业包及硬件调度优化 | 作为独立后续设计 | 增量覆盖、成本与能效收益，均需实测 |

### 6.1 主创新一：法财联合的履约一致性核验

问题：同一履约安排分散在价格、付款、验收与违约章节，单条阅读容易忽略关联。机制：法务检查义务与条件，财务抽取并核算金额与节点，双方只交接结构化事实和定位，对不确定关系保留分歧。金额和比例交给确定性计算，不让模型凭空心算。[S09]

演示要给出“两个角色各自贡献什么、交接后新增了什么核验信息”。建议测试同一问题的不同表达、无问题对照、跨页附件和条件例外。比较法财分工与同预算通用两轮，记录高风险漏检、误报、调用耗时和人工复核时间。没有独立结果前，将其称为应用与工作流机制创新，不宣称算法首创或准确率提升。[S06]

### 6.2 主创新二：带核验状态的风险证据卡

问题：风险结论流畅，但使用者不知道它是否来自合同、依据是否支持。机制：一项风险关联合同片段、来源位置、检索依据、建议及处理记录，把“原文已定位”“法源可查”“支持关系已核验”“人工已确认”分别展示。[S09]

默认manual_only意味着不能宣传自动完成法律语义验证。创新落点是便于发现缺证、核验与接管，不是“RAG保证法律正确”。漏项类结论还应关联适用的检查清单和检索范围，而非为缺失条款伪造引文。可用随机抽样的来源定位正确率、引用可访问率、每项风险核验耗时，以及缺证时是否正确转人工来验证。

### 6.3 辅助创新：报告直接连接处理动作

问题：导出的风险清单容易变成静态附件，管理者仍要二次整理。机制：在同一审查快照中整理待复核、待修改、责任人、期限和证据入口，并说明统计范围。正文和导出字段能回到同一个合同及风险对象。[S08]

这里的差异是“可以跟进处理的交付”，而不是“支持Excel”。若要作为主创新，需补充实际使用任务对照，例如使用者查找最高优先级问题及其依据所需时间。没有真实使用者实验时，只展示机制与产物，不宣称企业成本下降。

### 6.4 现在不宜扩展的方向

不建议为了复赛新增大量Agent角色、全套OA/ERP/电子签章、自动法律裁决、未经验证的自学习、宏大知识图谱或芯片级调度。它们会挤占核心验收时间。自动修改合同正文、增量再审也不应临时接入主流程；可以在后续路线中说明适用条件与验证计划。

## 7. 最小补证方案：让有限时间产生有效证据

### 7.1 90%要素指标

复用现有评测工具和六字段定义，分别固定甲方、乙方、标的、金额、期限和付款节点，另外核查背景提到的违约责任如何进入风险与报表。不要为提高分数只选择容易提取的字段。[S02]

建议在已有合成集之外，增加经授权且由独立人员选取的异源文档，覆盖DOCX、文本PDF、扫描或混合PDF、表格和条件式付款；先冻结标注再运行。两人独立标注、分歧裁决，不用同一模型自评替代人工。数量与比例依可得数据安排，原题没有规定样本量。

主指标同时给出严格字段匹配率，分字段、合同类型和文档类型报告；付款节点可另报集合Precision/Recall/F1。现有协议将五个标量严格匹配与付款节点F1汇为六字段宏平均，它是团队既有操作口径，并非官方定义。正式90%验收应说明口径，并尽量同时报告全字段严格匹配，避免称混合分数为统一的法律准确率。

解析失败、缺预测和漏字段保留在分母，适用与不适用字段规则事先冻结；单独报告待人工确认比例。值提取正确与自动可采信不同。测试版本、数据来源、样本散列和逐项错误保留，以便复现。[S02][S03]

### 7.2 三类风险与法财协作

采用少量但明确的独立标注问题，覆盖漏项、跨条款矛盾、疑似违法，并提供相似的无风险对照；加入表述改写和计价基数例外。先区分法律问题与商业建议，再统计命中、漏检和误报，不能用总输出条数替代召回率。

单列“法财联动问题”，说明哪个角色首审发现、交接提供什么信息、复核是否修正、最终为何转人工。当前默认首审顺序执行，若不改实现就如实展示。并行化不是获得协作价值的前提，也不能凭架构图宣称低延迟收益。[S06][S09]

### 7.3 批量与最终演示环境

在最终电脑上用一次请求提交52份有效合同；记录接收、解析、类型确认、排队、审查、待复核、失败的数量和耗时，保持分母清楚。另加损坏件、重复件和模型失败进行失败隔离测试，不从成功率中删去失败输入。

原题括号明确了一次上传数量；支持批量处理还需要说明后续任务确实能处理。现有52份历史证据仅到待类型确认，复赛应尽量补完整批次模型审查与结果回读。人工终审可挑代表合同实做，不自行扩张为官方要求52份都人工终审。[S03]

先确保单份成功闭环，再做大批次。现场只短暂展示批次状态和已完成记录，无需让评委等待整个批次。断网、超时、低质量扫描、零风险结果、空报表和刷新恢复都要彩排；无风险必须与未审查或审查失败区分。[S05]

|---|---|---|---|

负责人是职责建议，不指派具体个人。时间安排建议：先冻结范围与证据台账，再补单份闭环和关键字段，再做批量及对照，最后整理材料和彩排。赛前最后一个稳定版本起停止新增架构与功能，保留修复阻断演示问题的窗口。

若时间只够三件事：完成一次真实成功闭环；让90%与52份的每个数字都能解释分母和范围；演示一个法财联动问题如何进入人工决定与报表。硬件条件无法改变时，立即明确边界并确认规则，不能持续投入软件包装试图替代硬件证据。

## 9. 答辩高频追问的建议回答

**为什么需要两个Agent？** 原题要求法财协作，我们将两类职责、结构化交接与人工分歧处理分开实现。两者可共用同一底层模型；当前首审为顺序执行。协作机制有实现证据，效果提升还需要独立评测。

**你们准确率是否达到90%？** 历史35份合成原生文档的210个字段中严格匹配198项，为94.3%；不含扫描件、OCR或独立人工金标。真实业务范围的达标结论需正式冻结集验证。法律风险识别效果不是这个数字。

**52份是否都审查完成？** 已有记录证明单请求上传及解析52份，终态是待类型确认，不能称为52份模型审查完成。若复赛前补测，应以新批次的实际状态、成功率和耗时更新回答。

**OpenClaw比GPU节能多少？** 本次没有拿到指定设备，没有真实能效对照，不能给节能百分比。兼容接口与评测工具已经准备，设备联调和能效验收单独列为缺项。

**有法规来源就代表正确吗？** 不代表。来源可查、原文可定位、依据支持关系、适用条件和人工确认是不同环节；系统分别展示状态，不能凭检索命中作最终法律决定。

**财务对账的数据从哪里来？** 当前主要核对合同内金额、币种、分期与付款条件。没有接入实际交易数据时，不主张核对真实收付款、发票或预算执行。

**创新到底在哪里？** 我们主张的是法财履约一致性核验、带核验状态的风险证据关联，以及与处理动作相连的报表交付，属于应用与工程机制创新。是否提升准确率、节省多少人工时间，需要独立试验证明。
