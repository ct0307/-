# 冻结合同集 v1 专业真实性审查

审查日期：2026-09-10

审查对象：`outputs/frozen-contracts-v1/` 对应生成器、案例画像、冻结清单及测试证据

审查结论：**不批准作为企业级高拟真合同基准；可保留为技术预检基线。**

## 1. 结论摘要

v1 在文件形态、业务类型、主体称谓、计价方式和合成数据安全边界方面达到技术预检要求，也没有根据解析结果回改冻结样本。但它尚未完整兑现设计规格中的“真实非理想条款、正文附件冲突和法务修订痕迹”，因此不能表述为已经接近企业真实合同的正式验收集。

| 优先级 | 发现 | 影响 | 处置结论 |
|---|---|---|---|
| P1 | 6 个案例声明存在条款冲突，实际附件只包含通用占位内容，未写入可比对的冲突值 | 无法验证系统能否识别正文与附件、主合同与补充协议的冲突 | 新建 v2 后实施，不回改 v1 |
| P1 | 4 个 DOCX 标记为“法务修订稿”，实际 OOXML 无修订记录、批注或水印 | 文档状态标签与文件真实结构不一致，不能验证修订稿解析 | 新建 v2 后实施，不回改 v1 |
| P2 | 多数 `risk_tags` 被转换为均衡的风险防范条款，而非现实中的失衡、模糊或单方条款 | 可测试要素提取，但不足以验证法律风险识别能力 | v2 应显式生成风险原文及期望风险标签 |
| P2 | 各场景复用相同的通用法律条款和履约控制清单，最高正文相似度为 0.855545 | 文件并非简单复制，但起草风格仍偏统一，低于真实企业来源的差异度 | v2 应增加供应商模板、业务自拟、法务模板等起草风格 |
| P2 | 8 份纯扫描 PDF 因缺少 RapidOCR 无法形成解析文本 | 当前环境不能完成扫描合同能力验收 | 配置 OCR 后原样重测 v1，不修改样本 |
| P2 | 服务型 50+2 批测缺少令牌、Redis、Celery worker 和运行中的后端 | 无法证明真实 API 批次终态、异常隔离和刷新一致性 | 环境具备后继续执行 |

## 2. 已达到的现实性

- 50 份有效合同覆盖 8 类企业业务，包含双方和三方文本。
- 格式分布为 14 DOCX、21 文本 PDF、15 扫描或混合 PDF。
- 25 份签署定稿、8 份扫描归档、8 份内部草稿，并包含供应商版本和在线订单文本。
- 16/50 使用“甲方/乙方”，10/50 使用“合同金额”，保留企业常见写法同时避免统一模板化。
- 16 份无固定金额真值，23 份字段分散，45 份引用附件，15 份目标页数超过 12 页。
- 50 份有效文件均可打开；53 个二进制样本 SHA-256 全部唯一；未检出身份证、银行卡、真实机关签章等隐私模式。

## 3. 测试证据及边界

| 项目 | 结果 | 证据等级 |
|---|---:|---|
| 静态验证 | passed；50+2 数量和格式分布正确 | 自动化技术证据 |
| 生产解析器 | 42 份得到文本，8 份纯扫描件失败 | 当前本机环境实测 |
| 构造真值技术预评测 | 六字段宏平均 F1 = 0.06 | `construction_truth_only`，非正式准确率 |
| 专项测试 | 9 passed；批次相关回归 28 passed | 自动化回归证据 |
| 完整质量门禁 | evaluation 59 passed；backend 313 passed、1 skipped；frontend 17 passed、12 skipped；类型检查和构建通过 | 代码质量证据，不等于业务验收 |
| 真实 API 50+2 | blocked | 未配置 `A03_EVAL_TOKEN`，且缺少 Redis/Celery 环境 |

## 4. 企业使用结论

v1 可以用于验证文件读取、格式处理、要素抽取弱点和冻结机制，但不能作为“合同风险审查能力已达到企业真实使用要求”的证据。正式商用前至少需要完成：

1. 生成保持 v1 不变的 v2，补齐真实风险条款、明确冲突值和 DOCX 修订结构。
2. 由两名真人独立复核合同内容与六要素，形成正式金标准。
3. 在具备 OCR、Redis、Celery 和测试令牌的环境中执行真实 50+2 API 批测。
4. 引入经授权、脱敏并按行业分层的企业历史合同，进行独立外部验证。

## 5. 冻结纪律

本审查发生在 v1 已生成并取得系统结果之后。为避免测试结果影响样本设计，所有内容修订必须进入新版本；v1 的合同、清单、哈希、预测和失败证据均不得覆盖。
