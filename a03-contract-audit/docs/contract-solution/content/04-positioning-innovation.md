# 第四章 产品定位、创新点与总体目标

## 4.1 产品定位

契鉴定位为面向大型企业和政府单位的合同合规审查与风险数据智能平台。系统以企业安全域内的合同文件和治理知识为基础，为法务、财务、业务和管理者提供“读懂合同、发现风险、核验依据、协同决策、推动整改、沉淀数据”的一体化能力。

产品不以生成一份审查报告为终点，而以风险是否被理解、确认、整改和关闭为结果；不以单个模型的回答能力为核心壁垒，而以专业协同、证据约束、知识治理、责任闭环和企业部署能力形成可持续价值。

## 4.2 价值主张

| 价值维度 | 传统方式的限制 | 契鉴的目标价值 |
|---|---|---|
| 作业效率 | 逐页阅读、重复摘录、人工查找依据 | 批量解析、结构化抽取、风险优先级排序 |
| 专业质量 | 依赖个人经验，法务财务意见分散 | 专业 Agent 分工、统一规则和交叉验证 |
| 结果可信 | 结论与原文、法源和版本脱节 | 逐风险证据链、置信度与人工状态 |
| 协同执行 | 审查建议难以转化为责任任务 | 复核、分派、整改、再审和关闭闭环 |
| 管理决策 | 合同信息沉睡在文件与台账中 | 多维合同、风险和履约数据分析 |
| 安全治理 | 公网传输或过度授权增加风险 | 私有化、最小权限、加密脱敏和全程审计 |

## 4.3 五项核心创新

### 4.3.1 可解释双 Agent 协同

法务专家 Agent 与财务会计 Agent 分别承担专业职责，编排器控制上下文、调用顺序和输出契约。法务结果中的付款、违约与履约条件可作为财务审查上下文，财务发现的金额、税率或付款矛盾也可触发法务交叉验证。两者结论不一致时，不由模型投票决定，而是形成结构化冲突，展示各自原文、依据和推理边界，交由对应主管处理。

创新不在于使用两个模型名称，而在于把跨专业审查转化为可追踪的协同协议：谁先判断、共享什么、何时复核、如何合并、怎样升级人工。该机制使跨条款、跨专业风险能够被显式发现。

### 4.3.2 逐风险可验证证据链

每条风险由风险分类、合同原文、位置、事实说明、依据引用、适用性信息、修改建议、置信度、知识版本、模型版本和人工状态组成。检索查询围绕“风险分类 + 原文事实”生成，依据需通过来源等级、法域、合同类型、业务维度和有效期检查。

若没有可靠来源，系统可以保留“建议关注”的候选风险，但必须限制置信度并提示人工补充依据。该设计把模型的自然语言输出转化为可核验业务对象，使评审、用户和审计人员能够沿同一路径复查结论。

### 4.3.3 人机责任闭环

系统将 AI 输出明确标记为待复核意见。高风险、低置信度、Agent 冲突、规则与模型矛盾、知识过期和关键字段缺失等情形自动进入人工队列。人工可以确认、忽略或发起整改，但必须在高风险忽略和风险关闭时提供理由或证据。

责任闭环同时保留时间、角色、版本和前后值，使“机器发现了什么、谁作出判断、合同如何修改、为何关闭风险”可以完整还原。该机制符合专业服务场景中辅助决策而非替代决策的原则。[S08]

### 4.3.4 多维合同数据治理

合同不再只是文件，而是由主体、标的、金额、币种、税率、期限、付款节点、交付验收、风险和整改等对象组成的数据资产。每个字段保留原文证据和质量状态，人工修正记录前后值。报表使用统一指标字典，允许按部门、合同类型、相对方、金额、时间、风险和状态分析。

结构化数据与风险闭环共享同一合同版本，避免审查报告、Excel 台账和管理看板之间口径漂移。对未经确认的字段，报表显示数据质量标记，不用模型猜测填补关键经营数据。

### 4.3.5 企业私有化与可演进架构

文件、结构化字段、向量、审查结果和日志默认保留在企业安全域，支持本地模型和离线 Embedding。模型通过统一适配层接入，编排逻辑依赖稳定数据契约而非供应商专有格式。目标架构允许从模块化单体与单节点部署演进到异步任务、独立对象存储、关系数据库、向量检索和监控组件，不以过早拆分微服务增加交付风险。

私有化能力不仅是部署位置，还包括身份对接、密钥管理、备份恢复、模型替换、知识迁移、日志保留和故障降级。该创新直接回应合同商业秘密与个人信息的保护需求。[S05][S06]

## 4.4 总体目标体系

| 编号 | 总体目标 | 核心衡量方式 |
|---|---|---|
| G-01 | 建立合同审查业务闭环 | 上传至归档各状态可追踪，风险可复核并进入整改 |
| G-02 | 建立可度量的抽取与识别能力 | 冻结样本、明确公式、分层阈值与错误分类 |
| G-03 | 建立可信证据与知识治理体系 | 正式依据来源可靠、适用范围明确、版本连续 |
| G-04 | 建立企业级数据安全能力 | 最小权限、加密脱敏、审计、备份和删除策略可验证 |
| G-05 | 建立经营分析数据基础 | 字段与风险口径统一，筛选、钻取和导出一致 |
| G-06 | 建立可复制的交付与演进路径 | 四阶段交付物、依赖、退出标准和运维边界清晰 |

## 4.5 产品非目标

- 不提供无边界的通用聊天入口，不让用户绕过合同、风险和权限上下文调用模型。
- 不自动判定合同有效或无效，不预测诉讼结果，不替代律师、法务或财务作最终专业判断。
- 不自行提供电子认证、印章控制或资金支付服务，仅通过受控接口与相关平台协同。[S07]
- 不在首期覆盖全部合同类型、全部法域或所有行业知识，适用范围由知识元数据和发布策略明确管理。
- 不将模型生成内容直接写入正式法规库，不让用户反馈未经审核自动改变生产规则。
- 不以单次演示速度、临时数据量或无法复现的准确率作为长期产品承诺。

## 4.6 成功判定

项目成功需要同时满足业务、技术和治理三类条件。业务上，用户能够完成从合同提交到风险关闭与报表更新的闭环；技术上，解析、抽取、审查、检索和部署具备明确接口与降级路径；治理上，知识、模型、数据和人工决策均可追踪。任何一类缺失都会使系统退化为单点工具，无法承担企业合同风险运营职责。
